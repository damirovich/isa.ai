## 1. Термины, определения и сокращения

| Термин / сокращение | Определение |
|---|---|
| **АС** | Автоматизированная система. |
| **Ядро (core)** | Доменно-нейтральная часть системы (движок): RAG, интеграция с моделями, грунтовка, ingestion, документы, персистентность, аудит, оболочка хоста. Не содержит знаний о конкретном ведомстве. |
| **Профиль (profile)** | Сменная доменная вертикаль (для данного внедрения — «Инспектор»): корпус НПА, типы документов, доменные сущности, критерии, роли, набор модулей, промпты, привязка моделей. |
| **Модуль** | Функциональная единица профиля, отображаемая в интерфейсе (например, «Генератор», «Архив»). |
| **НПА** | Нормативный правовой акт (закон, приказ, положение, инструкция, регламент). |
| **RAG** | Retrieval-Augmented Generation — генерация ответа модели на основе предварительно извлечённых релевантных фрагментов корпуса. |
| **Грунтовка (grounding)** | Контроль, при котором каждая ссылка/цитата в выводе модели обязана присутствовать в фактически извлечённых RAG фрагментах; иначе фрагмент помечается как непроверенный. |
| **Эмбеддинг** | Векторное представление текста для семантического поиска. |
| **Чанк (chunk)** | Фрагмент документа фиксированного размера, единица индексации и извлечения. |
| **Редакция** | Версия НПА; имеет статус (действующая / утратила силу) и дату. |
| **Гриф** | Категория конфиденциальности материала (в т.ч. ДСП). |
| **Допуск** | Уровень полномочий пользователя на доступ к материалам определённого грифа. |
| **ДСП** | «Для служебного пользования». |
| **Изолированный контур (air-gap)** | Сеть без подключения к сети Интернет и иным внешним сетям. |
| **On-premise** | Размещение и обработка данных исключительно на инфраструктуре заказчика. |
| **vLLM** | Локальный сервер инференса LLM, предоставляющий OpenAI-совместимый API. |
| **LLM** | Большая языковая модель. |
| **Multi-instance** | Развёртывание отдельного экземпляра системы под каждый отдел/контур (вместо мультиарендности). |
| **СрЗИ / СКЗИ** | Средства защиты информации / средства криптографической защиты информации. |
| **At-rest** | Состояние данных при хранении (на диске/в БД), в отличие от данных при передаче. |
| **СЭД** | Система электронного документооборота. |
| **ТУ** | Территориальное управление. |
| **HITL** | Human-in-the-loop — обязательная проверка результата человеком до его официального использования. |
| **p50 / p95** | Медиана и 95-й перцентиль (для показателей задержки). |
| **ADR** | Architecture Decision Record — запись об архитектурном решении и его обосновании. |
| **Рабочий этап** | Этап разработки системы, обозначается **Э0…Э7** (раздел 6.2). |
| **Фаза внедрения** | Укрупнённая фаза поставки ценности заказчику, обозначается **Ф1/Ф2/Ф3** (соответствует «этапам 01/02/03» презентационных материалов). Соответствие фаз и рабочих этапов: Ф1 ↔ Э1–Э5; Ф2–Ф3 ↔ Э6. |

> **Соглашение о слове «этап».** Во избежание неоднозначности «этап» употребляется только в значении «рабочий этап» с обозначением Э0–Э7. Укрупнённые фазы поставки обозначаются Ф1/Ф2/Ф3. Голые ординалы («этап 1», «этап 3») в тексте не используются.

## 2. Общие сведения

**2.1.** Полное наименование: интеллектуальная платформа ведомственного внутреннего контроля ISC.AI. Первый разворачиваемый профиль — «ИнспекторAI» для Главной инспекции.

**2.2.** Основание для разработки: решение заказчика о создании инструмента внутреннего контроля с применением ИИ. Настоящее ТЗ — основной нормативный документ разработки.

**2.3.** Плановые сроки: определяются календарным планом (раздел 6). Заявленные в презентационных материалах сроки фаз внедрения рассматриваются как ориентировочные и подлежат пересмотру по результатам оценки трудозатрат (см. 6.2).

**2.4.** Порядок оформления и предъявления результатов: результаты предъявляются заказчику по рабочим этапам (раздел 6) и принимаются по критериям раздела 7.

**2.5.** Принципиальное положение. Все решения, оценки и юридически значимые выводы остаются за сотрудниками. Система обеспечивает скорость, полноту и системность подготовки материалов, но **не принимает решений** и **не является источником права**. Любой генерируемый документ — проект, требующий проверки и утверждения человеком (HITL).

## 3. Назначение и цели создания системы

### 3.1. Назначение

Система предназначена для информационно-аналитической поддержки внутреннего ведомственного контроля: подготовки документов, поиска и анализа НПА, ведения архива проверок, выявления рисков, мониторинга устранения нарушений, подготовки материалов для руководства.

### 3.2. Цели создания (с измеримыми показателями и трассировкой)

| Код | Цель | Показатель достижения | Реализующие требования и проверка |
|---|---|---|---|
| Ц-01 | Сократить долю рутинного делопроизводства инспектора | Время подготовки типового документа снижено относительно ручного процесса. Базовая величина «как есть» фиксируется на обследовании (Э1, см. 4.3 и ТН-001); целевой коэффициент сокращения согласуется с заказчиком. | ТФ-ГЕН-*, ТФ-РЕД-*, ТФ-МЕТ-01; проверка — сопоставление с базовой величиной обследования (Э1). |
| Ц-02 | Перейти от реакционного контроля к системному | Реестр рисков ведётся непрерывно; мониторинг устранения нарушений с сигнализацией о просрочке (базовый — фаза Ф1; полная эскалация — фаза Ф2). | ТФ-РСК-01, ТФ-МОН-01 (Ф1), ТФ-СОВ-02 (Ф2); проверка — сценарий «просроченный пункт порождает сигнал». |
| Ц-03 | Сохранить институциональную память | История проверок и закономерности доступны независимо от ротации сотрудников. | ТФ-АРХ-*; проверка — наличие истории и аналитики в архиве. |
| Ц-04 | Обеспечить достоверность правовых ссылок | Доля проверенных грунтовкой ссылок и доля ошибочных ссылок на утратившие силу редакции — в пределах порогов приёмки. | ТБ-040, ТФ-НПА-02, ТО-инф-04; проверка — КИ-01, КИ-02, GATE-2, GATE-3. |
| Ц-05 | Обеспечить переиспользуемость платформы | Подключение нового профиля не требует изменения ядра. | ТС-002, ТС-003, ТС-006, ТС-009; проверка — архитектурный тест ТС-009. |

### 3.3. Критерий «не-цель»

Система **не** заменяет экспертное суждение, **не** выносит оценок и решений автоматически, **не** публикует данные вовне и **не** работает при наличии внешних сетевых подключений в режимном контуре.

## 4. Характеристика объектов автоматизации

**4.1.** Объект автоматизации — деятельность Главной инспекции по внутреннему контролю и связанные с ней процессы: подготовка документов, работа с корпусом НПА, проведение проверок, ведение архива, управление рисками, контроль исполнения поручений.

**4.2.** Объекты контроля: территориальные и линейные подразделения (по презентационным материалам — 7 ТУ и 6 линейных подразделений; точный перечень и иерархия вплоть до райотдела уточняются на этапе обследования Э1).

**4.3.** Существующая ситуация («как есть»): документы готовятся вручную из прежних образцов; история проверок разрознена; причины нарушений системно не анализируются; реестр рисков отсутствует; контроль устранения — периодическими проверками. Подробное обследование процессов «как есть» и фиксация базовых величин (для Ц-01) выполняются на рабочем этапе Э1 (раздел 6).

**4.4.** Окружение объекта автоматизации (смежные системы и источники данных): корпус НПА (документы ведомства), источники сканов (бумажные документы под OCR), в перспективе — СЭД заказчика (интеграция на фазе Ф3). Полный перечень смежных систем, форматов и характера взаимодействия **подлежит уточнению при обследовании (Э1)**.

**4.5.** Условия эксплуатации: изолированный контур ведомства, без доступа в Интернет; режим обработки материалов до грифа ДСП включительно (при соответствующей настройке и согласовании, см. 5.1.6).

## 5. Требования к системе

### 5.1. Требования к системе в целом

#### 5.1.1. Требования к структуре и функционированию

| Код | Требование | Проверка |
|---|---|---|
| ТС-001 | Система реализуется как **модульный монолит** — одно разворачиваемое приложение. Микросервисная декомпозиция не применяется. | Анализ архитектуры, сборка. |
| ТС-002 | Применяется **многослойная архитектура (Clean Architecture)** с единым правилом зависимостей: зависимости направлены внутрь, к контрактам (`Abstractions`). Ядро не зависит от профиля. | Архитектурный тест (ТС-009). |
| ТС-003 | Выделяются **нейтральное ядро** и **сменный профиль**. Доменно-специфичная логика размещается только в профиле. Перечень неизменяемого (ядро) и сменного (профиль) — согласно «Архитектуре ISC.AI», разделы 3, 5. | Анализ зависимостей. |
| ТС-004 | Единственная точка композиции — хост `ISC.AI.Web`. Только хост знает, какой профиль загружен, и подключает его при старте. | Анализ кода `Program.cs`. |
| ТС-005 | Развёртывание — **multi-instance**: отдельный экземпляр (своя БД, своё хранилище, свой контур) под каждый **отдел/контур верхнего уровня**. Мультиарендность с дискриминатором между отделами не применяется. **Граница экземпляра — Главная инспекция в целом**; подчинённые подразделения (7 ТУ и 6 линейных) представлены не отдельными экземплярами, а атрибутом «подразделение» данных внутри одного экземпляра (см. ТО-инф-03), что и обеспечивает сводные представления ТФ-ДШ/ТФ-АРХ-03. Если для конкретного внедрения потребуется экземпляр на подразделение — вводится отдельное требование к консолидации данных в пределах контура, а формулировки «в реальном времени» уточняются. | Документация по развёртыванию; согласование с ТФ-ДШ-01/03. |
| ТС-006 | Профиль предоставляет **манифест** с программными контрактами: регистрация модулей, доменных контекстов данных, привязки моделей, источников промптов. Контракты определены в `Abstractions` (см. 5.3.4). | Наличие и реализация контрактов. |
| ТС-007 | Состав модулей профиля «Инспектор»: Дашборд, Генератор документов, База НПА, Архив, Коллегия, Совещания, Редактор, Анализ НПА, Риски, Методики, Мониторинг (детализация — 5.2). Набор модулей определяется профилем декларативно. | Реестр модулей. |
| ТС-008 | Под Blazor Server контекст данных создаётся через фабрику (`IDbContextFactory`) на операцию, а не как долгоживущий scoped-сервис. | Code review, нагрузочный тест. |
| ТС-009 | Должен существовать **автоматический архитектурный тест**, падающий при нарушении правил: (а) ядро не ссылается на проект профиля; (б) хост подключает ровно один профиль; (в) профиль не нарушает направление зависимостей. | Прогон теста в CI. |

#### 5.1.2. Требования к численности и квалификации персонала

| Код | Требование | Проверка |
|---|---|---|
| ТП-001 | Роли пользователей: **инспектор**, **руководство**, **администратор** (детализация прав — ТБ-002, ТБ-010, ТБ-011). На фазе Ф1 допускается однопользовательский режим с последующим переходом к мультипользовательскому (фаза Ф3, рабочий этап Э6). | Приёмка соответствующей фазы. |
| ТП-002 | Эксплуатация системы инспектором не требует навыков программирования. Администрирование (развёртывание в контуре, управление доступом, загрузка НПА) выполняется подготовленным администратором заказчика. | Опытная эксплуатация. |

#### 5.1.3. Показатели назначения (нефункциональные требования, НФТ)

> **Важно.** Числовые ориентиры из презентационных материалов («справка за 3 минуты», «история за 8 секунд», «проект приказа за 4 минуты») принимаются как **целевые ориентиры**, а не как контрактные значения. Контрактные значения SLA фиксируются по результатам нагрузочного тестирования на фактической инфраструктуре заказчика (ТН-002).

| Код | Требование | Проверка |
|---|---|---|
| ТН-001 | Должны быть заданы и согласованы: число одновременно работающих пользователей, целевые задержки RAG/инференса, объём корпуса (документы/чанки/ГБ), требования к GPU/VRAM, RPO/RTO, базовые величины ручных процессов (для Ц-01). Раздел НФТ заполняется по итогам обследования (Э1). | Согласованная таблица НФТ. |

Прогон выполняется на эталонном наборе. Недетерминированность LLM требует **статистической** приёмки (на выборке). Пороговые значения — **уточняются с заказчиком** на Э1; ниже — состав обязательных метрик:

|---|---|---|

| КИ-02 | Доля ошибочных ссылок на **утратившие силу** редакции, выданных как действующие. | Близка к нулю; превышение порога — блокирующий дефект (см. GATE-3). |
| КИ-03 | Полнота извлечения (recall@k) — **раздельно для русского и кыргызского**. | Каждый язык — не ниже своего порога; средняя величина не маскирует провал ky. |
| КИ-04 | Качество генерации документов (соответствие шаблону, фактологическая достоверность при выборочной экспертной проверке). | Согласованный порог. |

### 7.4. Обязательные gate-критерии (блокирующие)

| Код | Тест | Условие приёмки |
|---|---|---|
| GATE-1 | **Фильтр доступа по грифу** (интеграционный тест): пользователь не получает материалы выше своего допуска ни в каком виде. Методика: используется подготовленный документ заведомо выше допуска; проверяется **неразличимость** ответа от случая «документ отсутствует» — по контенту, метаданным, счётчикам/агрегатам, ранжированию, тексту и **времени** ответа об ошибке. Включает подпроверку изоляции грифов в индексе (ТБ-023). Фильтр — fail-closed (ТБ-021). | Тест проходит безусловно. |
| GATE-2 | **Грунтовка**: вывод со ссылкой, отсутствующей в извлечённых фрагментах, отклоняется/маркируется и не выдаётся как проверенный. | Тест проходит безусловно. |
| GATE-3 | **Версионность редакций** (детерминированный интеграционный тест): запрос по умолчанию возвращает только действующую редакцию; утратившая силу не выдаётся как действующая, а при показе помечается «УТРАТИЛА СИЛУ». Увязан с ТО-инф-04, ТФ-НПА-02, КИ-02. | Тест проходит безусловно. |

Невыполнение любого gate-критерия — основание для отказа в приёмке независимо от прочих результатов.

## Приложение Б. Схема идентификаторов требований

Идентификатор имеет вид `<ПРЕФИКС>-[<СЕГМЕНТ>-]<NN>`. Префиксы — по Приложению А. Сегмент применяется в двух группах:
- **Функциональные требования (ТФ):** код модуля — ГЕН, НПА, АНПА, АРХ, РСК, МОН, СОВ, КОЛ, МЕТ, РЕД, ДШ.
- **Виды обеспечения (ТО):** вид обеспечения — мат, инф, лнг, прог, тех, орг, мет.

Идентификаторы сквозные и неизменные: при отмене требования номер не переиспользуется. На требования ссылаются код (в комментариях к коду, реализующему безопасность/грунтовку — ТД-003/004), тесты (в названиях/описаниях, особенно GATE-1/2/3) и прочие документы. Все перекрёстные ссылки в тексте даются по этим идентификаторам.
