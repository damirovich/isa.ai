## 1. Область применения и приоритет

**1.1.** Стандарт обязателен для всего кода решения ISC.AI: ядра (`src/core/*`), профиля «Инспектор» (`src/profiles/inspector/*`) и проектов тестов (`tests/*`).

**1.2.** Стандарт является детализацией требований ТЗ к документированию (ТД-001..ТД-008) и не отменяет их. При расхождении приоритет имеет ТЗ; настоящий документ конкретизирует «как именно» выполнять требования ТЗ.

**1.3.** Соблюдение стандарта проверяется двумя путями: автоматически (анализаторы, `.editorconfig`, предупреждения сборки, повышаемые до ошибок — см. раздел 9) и при ревью pull request (человеческая проверка содержательности комментариев). Оба пути являются условием приёмки этапа (ПР-004).

**1.4.** Все идентификаторы требований в комментариях к коду и в названиях тестов берутся из ТЗ (Приложение Б ТЗ). Запрещается ссылаться на несуществующие идентификаторы.

## 2. Общие соглашения C# / .NET 10

### 2.1. Целевая платформа и общие свойства проектов

Все проекты нацелены на `net10.0`. Для всего решения обязательны единые свойства (фактически уже включены в существующих `.csproj`, см. `ISC.AI.Abstractions.csproj`):

- `Nullable` = `enable` — ссылочные типы с поддержкой `null` обязательны во всём решении. Состояние «возможно `null`» выражается типом (`T?`), а не комментарием или соглашением. Подавление через `!` (null-forgiving) допускается только с пояснительным комментарием, почему значение гарантированно не `null`.
- `ImplicitUsings` = `enable` — неявные глобальные `using` включены; проектные глобальные пространства имён выносятся в `GlobalUsings.cs`.
- `TreatWarningsAsErrors` и `GenerateDocumentationFile` — см. раздел 9.

> **Связь с безопасностью.** `Nullable enable` — не только стиль. Контракты вида ТБ-021 (fail-closed) и ТБ-024 (запрет индексации без грифа) опираются на то, что «неизвестно/не задано» выражается как `null` и обрабатывается явно. Поэтому отключение nullable в отдельных файлах запрещено.

### 2.2. Именование

| Сущность | Правило | Пример |
|---|---|---|
| Пространства имён, типы, методы, свойства, события | `PascalCase` | `RetrievalRequest`, `GroundReferencesAsync` |
| Интерфейсы | Префикс `I` + `PascalCase` | `IRetriever`, `IPromptProvider` |
| Параметры, локальные переменные | `camelCase` | `accessContext`, `topK` |
| Приватные/внутренние поля | `_camelCase` | `_dbContextFactory` |
| Константы | `PascalCase` | `MaxChunkOverlap` |
| Параметры обобщений | `T` или `TXxx` | `TEntity`, `TResult` |
| Асинхронные методы | Суффикс `Async` | `RetrieveAsync` |

Запрещены: венгерская нотация, сокращения, не являющиеся общепринятыми, транслитерация русских слов в идентификаторах (`Spravka`, `Polnota`). Доменные термины передаются устоявшимися английскими эквивалентами; русскоязычное пояснение даётся в XML-комментарии.

### 2.3. Асинхронность

- Любой ввод-вывод (БД, обращение к vLLM, файловое хранилище) — асинхронный; синхронные обёртки (`.Result`, `.Wait()`, `.GetAwaiter().GetResult()`) запрещены.
- Все публичные асинхронные методы принимают `CancellationToken` последним параметром и передают его вниз по цепочке вызовов.
- В библиотечном коде (ядро, профиль) применяется `ConfigureAwait(false)` либо это решение фиксируется единым правилом на уровне проекта; в коде компонентов Blazor `ConfigureAwait` не используется (нужен контекст синхронизации UI).
- Возврат `async void` запрещён, кроме обработчиков событий.
- `IAsyncEnumerable<T>` применяется для потоковой выдачи (например, потоковая генерация токенов модели).

### 2.4. Внедрение зависимостей (DI)

- Зависимости передаются через конструктор; service locator (`IServiceProvider.GetService` в прикладном коде) не применяется, кроме фабрик и точки композиции.
- Время жизни: для контекста данных под Blazor Server используется фабрика `IDbContextFactory<T>` и создание контекста на операцию (ТС-008), а не долгоживущий scoped-сервис.
- Модели подключаются через нейтральную абстракцию `IChatClient` / `IEmbeddingGenerator` (`Microsoft.Extensions.AI`) с keyed-регистрацией по роли (`draft`, `analysis`, эмбеддинги) — ТО-прог-02/03. Конкретные названия моделей в коде ядра не упоминаются.
- Регистрация сервисов профиля выполняется только через его манифест (`IProfile`), единственная точка композиции — хост `ISC.AI.Web` (ТС-004, ТО-прог-05/06).

### 2.5. Прочие правила

- Включён `nullable` → публичный контракт не возвращает `null` неявно; для «значение может отсутствовать» используется `T?` либо явная модель результата.
- Исключения применяются для исключительных ситуаций; ожидаемый исход «доступ запрещён / ничего не найдено» моделируется типом результата или пустой коллекцией, а не исключением (важно для GATE-1: ошибка и «пусто» должны быть неразличимы — см. раздел 6).
- Магические числа и строки выносятся в именованные константы/конфигурацию (пороги релевантности, `topK`, размеры чанков — ТО-мат-03/04).
- Публичные методы валидируют аргументы в начале тела (`ArgumentNullException.ThrowIfNull`).
- Формат — единый, задаётся `.editorconfig` (раздел 9); ручное форматирование «на свой вкус» недопустимо.

## 3. Структура файлов и проектов

**3.1.** Один публичный тип — один файл; имя файла совпадает с именем типа.

**3.2.** Порядок внутри файла: лицензионный/заголовочный комментарий файла (при наличии) → `namespace` (file-scoped) → XML-doc типа → тип. Члены упорядочиваются: константы, поля, конструкторы, свойства, методы (публичные → защищённые → приватные).

**3.3.** Слоистость и направление зависимостей (ТС-002) контролируются архитектурным тестом (ТС-009); код не должен вводить ссылки, нарушающие правило «зависимости направлены внутрь, к `Abstractions`». Ядро не ссылается на проект профиля.

**3.4.** Раскладка решения (фактическая, для справки):

```
src/
  core/
    ISC.AI.Abstractions/      // контракты платформы (только интерфейсы и базовые типы) — ТО-прог-04
    ISC.AI.AI/                // адаптеры моделей, RAG, грунтовка
    ISC.AI.Ingestion/         // конвейер загрузки (ingestion)
    ISC.AI.Documents/         // рендеринг и экспорт документов
    ISC.AI.Persistence/       // контекст(ы) данных, pgvector, аудит
    ISC.AI.Web/               // хост Blazor Server — единственная точка композиции (ТС-004)
  profiles/
    inspector/                // сменный профиль «Инспектор»: Domain, Data, Application, UI, манифест
tests/
  ISC.AI.UnitTests/           // модульные тесты (без БД и моделей) — ТО-прог-07
  ISC.AI.IntegrationTests/    // Testcontainers: PostgreSQL + pgvector
  ISC.AI.Evals/               // прогон промптов через модели на эталонном наборе
```

Каждая значимая папка снабжается `README`/заголовочным комментарием (ТД-006, см. раздел 7).

### 4.1. Что обязательно документируется (ТД-001)

XML-doc обязателен для **всех публичных и защищённых** типов и членов: классов, интерфейсов, записей, перечислений, методов, свойств, событий, делегатов. Для `internal`-типов XML-doc желателен, но не повышается до ошибки сборки; для нетривиального `internal`/`private` кода применяется ТД-005 (комментарий «почему»).

Минимальный состав XML-doc:

- `<summary>` — что делает член и **зачем** (назначение, а не пересказ сигнатуры);
- `<param>` — для каждого параметра: смысл и допустимые значения;
- `<returns>` — что возвращается, включая граничные случаи (пустая коллекция, `null`, значение по умолчанию);
- `<exception>` — какие исключения и при каких условиях;
- `<remarks>` — контракт реализации, пред-/постусловия, инварианты, потокобезопасность — обязательно для контрактов `Abstractions` (раздел 5).

### 4.2. Язык и стиль комментариев

- Язык XML-doc и поясняющих комментариев — **русский**, деловой, по существу. Допускаются англоязычные технические термины (`embedding`, `chunk`, `retrieval`), если они используются как имена в коде.
- Комментарий описывает контракт и намерение, а не очевидное. Запрещены комментарии, дублирующие имя (`/// <summary>Получает имя.</summary>` к свойству `Name`).
- Тон — утвердительный: «Возвращает действующую редакцию нормы», а не «Этот метод, возможно, вернёт…».

### 4.3. Примеры «хорошо / плохо» (ТД-001)

**Плохо** — пересказ сигнатуры, нет контракта, нет ссылки на требование, английский в summary:

```csharp
/// <summary>
/// Retrieve chunks.
/// </summary>
public Task<IReadOnlyList<Chunk>> RetrieveAsync(string query, int k);
```

**Хорошо** — назначение и «зачем», контракт, инвариант безопасности со ссылкой на ТЗ, граничные случаи, исключения:

```csharp
/// <summary>
/// Извлекает релевантные фрагменты корпуса НПА по семантическому запросу
/// с обязательной фильтрацией по допуску пользователя.
/// </summary>
/// <remarks>
/// Инвариант безопасности (ТБ-020): фильтрация по грифу/подразделению выполняется
/// на стороне БД, ДО возврата фрагментов модели. Реализация ОБЯЗАНА применять фильтр
/// для любого обращения, а не только для штатного сценария.
/// Поведение fail-closed (ТБ-021): при неопределённости допуска или грифа доступ
/// запрещается. Результат «доступ запрещён» неотличим от «ничего не найдено» (GATE-1).
/// </remarks>
/// <param name="request">
/// Запрос на извлечение: текст, контекст доступа субъекта, число результатов (topK).
/// </param>
/// <param name="cancellationToken">Токен отмены операции.</param>
/// <returns>
/// Список извлечённых фрагментов в пределах допуска субъекта; пустой список,
/// если в пределах допуска ничего не найдено или доступ запрещён (fail-closed).
/// Метод НИКОГДА не возвращает фрагменты выше допуска субъекта.
/// </returns>
/// <exception cref="ArgumentNullException">
/// <paramref name="request"/> равен <see langword="null"/>.
/// </exception>
public Task<IReadOnlyList<RetrievedChunk>> RetrieveAsync(
    RetrievalRequest request,
    CancellationToken cancellationToken);
```

### 4.4. Комментарии «почему» для нетривиальной логики (ТД-005)

Алгоритмы чанкинга (ТО-мат-03), ранжирования и порогов отсечения (ТО-мат-04), компоновки промптов (ТБ-041), кросс-контекстных транзакций (ТО-инф-06) сопровождаются комментариями, поясняющими **причину** решения, а не его механику. Комментарии поддерживаются в актуальном состоянии при изменении кода (правило синхронности — раздел 9.3 ТЗ).

**Плохо** — комментарий повторяет код:

```csharp
// прибавляем overlap к концу чанка
end += overlap;
```

**Хорошо** — объяснение «почему», с привязкой к требованию и его обоснованием:

```csharp
// Перекрытие чанков (ТО-мат-03): норма НПА часто пересекает границу фрагмента,
// поэтому соседние чанки делаются перекрывающимися — иначе цитата на стыке
// не попадёт целиком ни в один фрагмент и не пройдёт грунтовку (ТБ-040),
// что даст ложноотрицательное срабатывание валидатора ссылок.
// Конкретный размер перекрытия обоснован в ADR (ДОК-06) и проверяется на recall (КИ-03).
end += _options.ChunkOverlap;
```

## 5. Документирование контрактов `Abstractions` (ТД-003)

**5.1.** Проект `ISC.AI.Abstractions` содержит только интерфейсы и базовые типы без реализаций (ТО-прог-04). Контракты — главный носитель проектных инвариантов, поэтому документируются **особенно тщательно**: для каждого порта в XML-doc указываются назначение порта, ожидаемое поведение реализации и инварианты безопасности.

**5.2.** Для контрактов с инвариантом безопасности (ТД-003) обязательна секция `<remarks>` с прямой ссылкой на пункт ТЗ. Минимальный перечень таких контрактов (по ТО-прог-04):

| Контракт | Инвариант безопасности, который ОБЯЗАНА соблюдать любая реализация | Пункт ТЗ |
|---|---|---|
| `IRetriever` | Извлечение только с фильтром доступа по грифу/подразделению; fail-closed | ТБ-020, ТБ-021 |
| Контракт грунтовки (валидатор ссылок) | Запрет выдачи ссылок, не подтверждённых извлечёнными фрагментами | ТБ-040 |
| Порт ingestion | Заполнение полного набора обязательных метаданных; отклонение записи без грифа/подразделения | ТБ-024, ТО-инф-03 |
| Порт рендеринга документов | Маркировка грифа при экспорте `.docx` **и** наследование грифа результата как максимума грифов извлечённых фрагментов | ТБ-033, ТБ-032 |

**5.3.** Если контракт несёт инвариант безопасности, об этом говорится в первом предложении `<remarks>` словами «Инвариант безопасности (ТБ-0XX): …», чтобы реализатор не пропустил требование. Полный образец см. раздел 10.

**5.4.** Изменение сигнатуры или семантики контракта `Abstractions` сопровождается обновлением ДОК-05 (описание контрактов и порядка композиции) в том же pull request (раздел 9.3 ТЗ).

## 6. Комментирование кода безопасности и грунтовки (ТД-004)

**6.1.** Код, реализующий безопасность или грунтовку, сопровождается пояснительным комментарием, который называет: (1) защищаемый инвариант, (2) угрозу/класс нарушителя, на которую он отвечает, (3) ссылку на пункт ТЗ или модели угроз (ДОК-03). Это прямое требование ТД-004.

**6.2.** Комментарий безопасности нельзя «оптимизировать» при рефакторинге без понимания инварианта; формулировка инварианта в комментарии служит защитой от случайного ослабления контроля (например, замены fail-closed на fail-open).

### 6.3. Пример: fail-closed фильтр извлечения (ТБ-021)

```csharp
// БЕЗОПАСНОСТЬ (ТБ-021, fail-closed). Угроза (ТБ-001): внутренний нарушитель —
// пользователь, запрашивающий материалы сверх допуска. Если контекст доступа
// субъекта не установлен ИЛИ гриф/подразделение фрагмента не определены, доступ
// ЗАПРЕЩАЕТСЯ (а не разрешается). Любой ранний возврат здесь обязан возвращать
// "пусто", неотличимое от штатного "ничего не найдено" (GATE-1) — без отдельной
// ветки ошибки, отличающейся по тексту или времени ответа.
if (access is null || !access.HasClearance)
{
    return Array.Empty<RetrievedChunk>();
}
```

### 6.4. Пример: контроль грифа на загрузке (ТБ-024)

```csharp
// БЕЗОПАСНОСТЬ (ТБ-024, fail-closed ingestion). Угроза (ТБ-001): оператор загрузки
// вносит документ без явно установленного грифа/подразделения. Чанк без грифа
// или подразделения НЕ индексируется и не попадает в pgvector. Гриф по умолчанию —
// максимально ограничительный (не открытый). Поля грифа/подразделения — NOT NULL
// в схеме (ТО-инф-03), здесь дублируется проверкой в коде до записи в индекс.
if (chunk.Secrecy is null || chunk.Unit is null)
{
    throw new IngestionRejectedException(
        "Чанк отклонён: не установлен гриф или подразделение (ТБ-024).");
}
```

> Текст исключения и сообщение в журнал не должны раскрывать содержимое документа (ТД-007): указываются факт отклонения и идентификаторы, но не наименование/текст ДСП-материала.

### 6.5. Пример: неизменяемость аудита (ТБ-031)

```csharp
// БЕЗОПАСНОСТЬ (ТБ-031, append-only + хеш-цепочка). Угроза (ТБ-001): администратор/
// суперпользователь БД, пытающийся подменить или удалить записи аудита. Каждая запись
// связывается с хешем предыдущей (hash-chain), что делает выборочную правку
// обнаружимой. Запись выполняется ролью БД без прав UPDATE/DELETE на таблицу аудита;
// периодическое якорение наружу — компенсирующий контроль против TRUNCATE (см. ДОК-03).
entry.PreviousHash = previousHash;
entry.Hash = ComputeChainHash(entry, previousHash);
```

**6.6.** Системная часть промпта с правилом грунтовки размещается в ядре и не может быть отключена профилем (ТБ-041); место её сборки сопровождается комментарием о том, что это инвариант (системный промпт ядра + задачный промпт профиля + данные), запрещающий профилю ослаблять грунтовку.

## 7. Заголовочные комментарии модулей и шаблонов промптов (ТД-006)

### 7.1. Заголовок модуля/папки

Каждый модуль профиля и каждая значимая папка содержат `README.md` либо заголовочный комментарий с: назначением, точкой входа (главный тип/компонент/маршрут), ключевыми зависимостями и применимыми требованиями ТЗ. Пример `README` модуля:

```markdown
# Модуль «Генератор документов» (ТФ-ГЕН-01..05)

Назначение: генерация проектов документов (справка, акт, рапорт, проект приказа и др.)
на основе ввода инспектора и извлечённых норм НПА.
Точка входа: компонент `GeneratorPage.razor` (маршрут /generator), регистрируется
манифестом профиля через IModule.
Инварианты: каждая правовая ссылка проходит грунтовку (ТБ-040); результат — проект,
требующий проверки человеком (ТБ-042, ТЭ-002); экспорт .docx маркируется грифом (ТБ-033).
```

### 7.2. Заголовочный комментарий шаблона промпта

Промпты хранятся файлами-шаблонами в прикладном слое профиля (ТО-лнг-03), не в UI и не в коде. Каждый шаблон снабжается комментарием о задаче и ожидаемом вводе/выводе (ТД-006). Системная часть с правилом грунтовки — в ядре (ТБ-041) и в задачном шаблоне не дублируется и не ослабляется.

Пример заголовка шаблона задачного промпта (обезличенный, ТД-007):

```text
{{~ ##
   Шаблон промпта: генерация проекта справки (модуль «Генератор», ТФ-ГЕН-01).
   Роль модели: draft (ТО-прог-03).
   Вход:  document_type — тип документа; user_input — ввод инспектора
          (фрагменты НПА, прошедшие фильтр доступа ТБ-020, дописывает ЯДРО — в шаблон не входят).
   Выход: текст проекта документа со ссылками ТОЛЬКО на нормы из извлечённых фрагментов.
   Инвариант: правило грунтовки задаётся системным промптом ЯДРА (ТБ-041) и здесь
              не переопределяется. Ссылки «по памяти» запрещены (ТБ-040).
   Гриф: пример обезличен; реальные ДСП-данные в шаблоны не вставляются (ТД-007).
## ~}}
```

> Синтаксис комментария — Scriban: `{{ ## … ## }}` (с `~` для съедания переносов). Jinja-стиль `{# … #}` Scriban НЕ считает комментарием — такой «заголовок» ушёл бы в текст промпта модели.

## 8. Запрет ДСП и секретов в комментариях (ТД-007)

**8.1.** Комментарии, XML-doc, примеры в документации, тексты исключений и сообщения журналов **не содержат** сведений ограниченного доступа: реальных данных ДСП, наименований реальных ДСП-документов, персональных данных, паролей, ключей, токенов, строк подключения с учётными данными.

**8.2.** Все примеры — обезличенные и синтетические (как в настоящем документе). Для иллюстраций используются вымышленные значения.

**8.3.** Секреты и строки подключения хранятся вне исходного кода и конфигурации в открытом виде (ТБ-013); их недопустимо «временно» помещать в комментарии или закомментированный код. Закомментированный код с реальными значениями запрещён к коммиту.

**8.4.** При необходимости сослаться на чувствительный сценарий в комментарии указываются идентификатор требования и обезличенное описание угрозы, но не сами данные (см. примеры раздела 6).

**8.5.** Соблюдение проверяется при ревью и аудите (ТД-007); рекомендуется дополнительно настроить сканер секретов в CI как организационную меру (уточняется на Э1).

## 9. Технические настройки сборки и анализа (ТД-002, ТД-008)

> На момент составления документа (рабочий этап Э0) в репозитории отсутствуют `Directory.Build.props`, `Directory.Packages.props`, `.editorconfig` и `nuget.config`. Их создание — проектный результат (центральное управление версиями и офлайн-фид увязаны с ТБ-050; настройки документации/анализа — с ТД-002/ТД-008). Ниже приведены целевые фрагменты.

### 9.1. Генерация документации и повышение CS1591 до ошибки (ТД-002)

Единые свойства задаются в `Directory.Build.props` в корне решения, чтобы применяться ко всем проектам:

```xml
<!-- Directory.Build.props (корень решения) -->
<Project>
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>

    <!-- ТД-002: генерировать файл XML-документации для всех проектов -->
    <GenerateDocumentationFile>true</GenerateDocumentationFile>

    <!-- ТД-002/ТД-008: предупреждения трактуются как ошибки сборки.
         CS1591 — отсутствие XML-doc на публичном API — становится ошибкой.
         Глобальный TreatWarningsAsErrors — сознательное ужесточение относительно
         буквы ТД-002 («по согласованию, например для CS1591»); подтверждается на Э1.
         Диагностики, которые на раннем этапе уместно оставить предупреждениями,
         перечисляются в <WarningsNotAsErrors> (см. 9.2). -->
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>

    <!-- Включить анализаторы и рекомендованный уровень правил (ТД-008) -->
    <EnableNETAnalyzers>true</EnableNETAnalyzers>
    <AnalysisLevel>latest-Recommended</AnalysisLevel>
    <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
  </PropertyGroup>
</Project>
```

Для проектов тестов (`tests/*`), где публичный API не является поставляемым контрактом, допускается локально понизить требование к XML-doc, не отключая прочие проверки:

```xml
<!-- tests/*/<Project>.csproj — точечное послабление только для CS1591 -->
<PropertyGroup>
  <GenerateDocumentationFile>false</GenerateDocumentationFile>
  <NoWarn>$(NoWarn);CS1591</NoWarn>
</PropertyGroup>
```

Послабление допускается **только** для проектов тестов и фиксируется явно; для ядра и профиля CS1591 остаётся ошибкой.

### 9.2. Фрагмент `.editorconfig` (ТД-008)

`.editorconfig` в корне решения задаёт единый стиль и поведение анализаторов; нарушения выявляются автоматически (ТД-008). Ключевой фрагмент:

```ini
# .editorconfig (корень решения)
root = true

[*.cs]
charset = utf-8
end_of_line = crlf
indent_style = space
indent_size = 4
insert_final_newline = true
trim_trailing_whitespace = true

# --- Обязательность документации публичного API (ТД-001/ТД-002) ---
# CS1591: пропущен XML-комментарий для публично видимого типа или члена -> ошибка
dotnet_diagnostic.CS1591.severity = error

# --- Стиль кода (ТД-008) ---
csharp_style_namespace_declarations = file_scoped:error
dotnet_style_require_accessibility_modifiers = always:warning
csharp_prefer_braces = true:warning
dotnet_sort_system_directives_first = true
csharp_using_directive_placement = outside_namespace:warning

# --- Поддержка nullable как инварианта (см. 2.1) ---
# ВНИМАНИЕ: при TreatWarningsAsErrors=true (§9.1) перечисленные ниже warning-и
# становятся ОШИБКАМИ сборки. Если на раннем этапе разработки нужен мягкий режим,
# они исключаются в .csproj: <WarningsNotAsErrors>CS8600;CS8602;CS8625</WarningsNotAsErrors>.
# Окончательный выбор (warning или error) фиксируется на Э1.
dotnet_diagnostic.CS8600.severity = warning   # преобразование null-литерала/возможного null
dotnet_diagnostic.CS8602.severity = warning   # разыменование возможного null
dotnet_diagnostic.CS8625.severity = warning   # null-литерал для non-nullable

# --- Именование: интерфейсы начинаются с I (ТД-008/2.2) ---
dotnet_naming_rule.interfaces_start_with_i.severity = error
dotnet_naming_rule.interfaces_start_with_i.symbols = interface_symbol
dotnet_naming_rule.interfaces_start_with_i.style = prefix_i_style
dotnet_naming_symbols.interface_symbol.applicable_kinds = interface
dotnet_naming_style.prefix_i_style.required_prefix = I
dotnet_naming_style.prefix_i_style.capitalization = pascal_case

# --- Асинхронные методы оканчиваются на Async (ТД-008/2.3) ---
dotnet_naming_rule.async_methods_end_with_async.severity = warning
dotnet_naming_rule.async_methods_end_with_async.symbols = async_method_symbol
dotnet_naming_rule.async_methods_end_with_async.style = end_async_style
dotnet_naming_symbols.async_method_symbol.applicable_kinds = method
dotnet_naming_symbols.async_method_symbol.required_modifiers = async
dotnet_naming_style.end_async_style.required_suffix = Async
dotnet_naming_style.end_async_style.capitalization = pascal_case
```

> Конкретный набор правил и их severity (warning/error) согласуется на Э1 и фиксируется в `.editorconfig`. Базовый принцип: всё, что относится к обязательности документации (CS1591) и к инвариантам безопасности, — уровень `error`.

### 9.3. Синхронность документации и кода в одном PR (раздел 9.3 ТЗ)

**9.3.1.** Документация ведётся в репозитории (каталог `docs/`) под версионным контролем, синхронно с кодом (раздел 9.3 ТЗ).

**9.3.2.** **Правило одного PR.** Изменение поведения системы сопровождается обновлением соответствующей документации **в том же pull request**. В частности:

- изменение контракта `Abstractions` → обновление ДОК-05 и XML-doc контракта (разделы 5, 10);
- изменение поведения, затрагивающего безопасность/грунтовку/версионность → обновление комментариев безопасности (раздел 6) и, при необходимости, модели угроз ДОК-03;
- изменение схемы данных/метаданных → обновление ДОК-04;
- любое решение с альтернативами → ADR (ДОК-06);
- изменение публичного API без XML-doc не проходит сборку (CS1591 = error, 9.1).

**9.3.3.** PR не принимается, если: сборка падает на CS1591 или на правилах `.editorconfig`; изменён контракт `Abstractions` без обновления XML-doc/ДОК-05; в комментариях обнаружены сведения ДСП/секреты (ТД-007). Документ считается частью результата этапа и проверяется при приёмке (ПР-004).

**9.3.4.** Рекомендуемая структура шаблона PR (организационная мера, уточняется на Э1): краткое описание изменения; перечень затронутых требований ТЗ (идентификаторы); отметки «обновлены XML-doc», «обновлена документация в docs/», «комментарии безопасности добавлены/проверены», «нет ДСП/секретов в коде и комментариях».

## 10. Образец полностью прокомментированного контракта (`IRetriever`)

Ниже — эталонный образец оформления контракта из `Abstractions` (ТД-001, ТД-003) и кода реализации с комментариями безопасности (ТД-004), на который ориентируются разработчики. Образец иллюстративный; окончательные имена и сигнатуры типов фиксируются при реализации `Abstractions` (Э1, ТО-прог-04). Ссылки на требования — реальные (ТБ-020, ТБ-021, ТБ-023, ТБ-040).

```csharp
namespace ISC.AI.Abstractions.Retrieval;

/// <summary>
/// Контекст доступа субъекта, обязательный вход для фильтрации извлечения.
/// </summary>
/// <remarks>
/// Инвариант безопасности (ТБ-012): без установленного субъекта с допуском
/// операции извлечения не выполняются. Тип не допускает «пустого» допуска неявно:
/// отсутствие допуска выражается значением, при котором <see cref="HasClearance"/>
/// равно <see langword="false"/>, и обрабатывается как fail-closed (ТБ-021).
/// </remarks>
public sealed record AccessContext
{
    /// <summary>Идентификатор подразделения субъекта (для решётки доступа ТБ-002).</summary>
    public required string Unit { get; init; }

    /// <summary>Максимальный гриф, к которому субъект имеет допуск.</summary>
    public required SecrecyLevel MaxSecrecy { get; init; }

    /// <summary>
    /// Признак наличия действующего допуска. Если <see langword="false"/>,
    /// извлечение запрещается (fail-closed, ТБ-021).
    /// </summary>
    public required bool HasClearance { get; init; }
}

/// <summary>Запрос на извлечение фрагментов корпуса НПА.</summary>
public sealed record RetrievalRequest
{
    /// <summary>Текст семантического запроса.</summary>
    public required string Query { get; init; }

    /// <summary>Контекст доступа субъекта — обязателен (ТБ-012).</summary>
    public required AccessContext Access { get; init; }

    /// <summary>Число запрашиваемых фрагментов (topK); порог отсечения — конфигурация (ТО-мат-04).</summary>
    public int TopK { get; init; } = 8;
}

/// <summary>
/// Порт извлечения релевантных фрагментов корпуса НПА для RAG-конвейера.
/// </summary>
/// <remarks>
/// <para>
/// Назначение: по семантическому запросу вернуть наиболее релевантные фрагменты
/// (чанки) НПА в пределах допуска субъекта для последующей передачи модели (ТО-мат-01).
/// </para>
/// <para>
/// <b>Инвариант безопасности (ТБ-020).</b> Любая реализация ОБЯЗАНА применять фильтр
/// по грифу и подразделению НА СТОРОНЕ БД, до возврата результатов. Пользователю
/// не возвращаются векторы/чанки/документы выше его допуска — ни через штатный путь,
/// ни через какие-либо обходные обращения к хранилищу эмбеддингов.
/// </para>
/// <para>
/// <b>Fail-closed (ТБ-021).</b> При отсутствии или неопределённости допуска субъекта
/// либо грифа фрагмента доступ ЗАПРЕЩАЕТСЯ. Реализация не должна раскрывать сам факт
/// наличия материалов выше допуска: ответ «доступ запрещён» обязан быть неотличим
/// от «ничего не найдено» — по контенту, метаданным, счётчикам, ранжированию,
/// тексту и времени ответа (проверяется GATE-1).
/// </para>
/// <para>
/// <b>Изоляция грифов (ТБ-023).</b> Материалы разного грифа не смешиваются без
/// разграничения; способ изоляции обосновывается в модели угроз (ДОК-03).
/// </para>
/// <para>
/// Грунтовка (ТБ-040) выполняется отдельным валидатором над результатом генерации;
/// данный порт лишь поставляет фактически извлечённые фрагменты, против которых
/// затем проверяются ссылки модели.
/// </para>
/// </remarks>
public interface IRetriever
{
    /// <summary>
    /// Извлекает релевантные фрагменты корпуса НПА по запросу с обязательной
    /// фильтрацией по допуску субъекта (ТБ-020) в режиме fail-closed (ТБ-021).
    /// </summary>
    /// <param name="request">
    /// Запрос: текст, контекст доступа субъекта (обязателен, ТБ-012), число
    /// результатов (topK).
    /// </param>
    /// <param name="cancellationToken">Токен отмены операции.</param>
    /// <returns>
    /// Список извлечённых фрагментов в пределах допуска субъекта, упорядоченный
    /// по убыванию релевантности. Пустой список означает «ничего не найдено
    /// в пределах допуска ИЛИ доступ запрещён» (эти случаи неразличимы — GATE-1).
    /// Метод НИКОГДА не возвращает фрагменты выше допуска субъекта.
    /// </returns>
    /// <exception cref="ArgumentNullException">
    /// <paramref name="request"/> равен <see langword="null"/>.
    /// </exception>
    Task<IReadOnlyList<RetrievedChunk>> RetrieveAsync(
        RetrievalRequest request,
        CancellationToken cancellationToken);
}
```

Пример реализующего метода с комментариями безопасности (ТД-004), демонстрирующий fail-closed и неразличимость ответа:

```csharp
/// <inheritdoc />
public async Task<IReadOnlyList<RetrievedChunk>> RetrieveAsync(
    RetrievalRequest request,
    CancellationToken cancellationToken)
{
    ArgumentNullException.ThrowIfNull(request);

    // БЕЗОПАСНОСТЬ (ТБ-012/ТБ-021, fail-closed). Угроза (ТБ-001): пользователь
    // без действующего допуска или с неопределённым допуском. Возвращаем пустой
    // результат, неотличимый от «ничего не найдено» (GATE-1) — без отдельной
    // ветки ошибки, отличающейся текстом или временем ответа.
    if (!request.Access.HasClearance)
    {
        return Array.Empty<RetrievedChunk>();
    }

    await using var db = await _dbContextFactory.CreateDbContextAsync(cancellationToken);

    // БЕЗОПАСНОСТЬ (ТБ-020, фильтр на стороне БД). Предикат по грифу и подразделению
    // встраивается в SQL и применяется ДО возврата строк, а не в памяти после выборки.
    // Это исключает попадание векторов/чанков выше допуска в выдачу модели и закрывает
    // прямой доступ к таблице эмбеддингов в обход штатного пути (ТБ-020, ТБ-023).
    var queryEmbedding = await _embeddingGenerator.GenerateAsync(request.Query, cancellationToken);

    var rows = await db.Chunks
        .Where(c => c.DivisionId == request.Access.DivisionId)
        .Where(c => c.Classification <= request.Access.MaxClassification)  // решётка доступа (ТБ-002)
        .Where(c => c.IsCurrent)                                           // только актуальные источники (нейтральный флаг, ADR-0013)
        .OrderBy(c => c.Embedding.CosineDistance(queryEmbedding))
        .Take(request.TopK)
        .Select(c => new RetrievedChunk(
            c.Id.ToString(), c.DocumentId.ToString(), c.Text,
            c.Classification, c.DivisionId.ToString(), c.IsCurrent, Score: 0))
        .ToListAsync(cancellationToken);

    return rows;
}
```
