## 1. Назначение и границы ответственности администратора

**1.1.** Эксплуатация системы инспектором не требует навыков программирования; администрирование (развёртывание в контуре, управление доступом, загрузка НПА, офлайн-обновление) выполняется подготовленным администратором заказчика (ТП-002). Сопровождение корпуса НПА (OCR, чистка, разметка) ведёт выделенный персонал заказчика (ТП-003, ТО-орг-01).

**1.2.** Развёртывание — **multi-instance**: отдельный экземпляр (своя БД, своё хранилище, свой контур) на отдел/контур верхнего уровня. Граница экземпляра — Главная инспекция в целом; подчинённые подразделения (территориальные и линейные) представлены не отдельными экземплярами, а атрибутом «подразделение» данных внутри одного экземпляра (ТС-005, ТО-инф-03). Мультиарендность между отделами не применяется.

**1.3.** Разделение административных ролей (ТБ-015). Обязанности по администрированию разнесены так, чтобы ни одна роль единолично не обладала одновременно доступом к содержимому ДСП и правами на изменение/удаление аудита:

| Роль администрирования | Зона ответственности | Чего НЕ должен иметь |
|---|---|---|
| Администратор приложения | Установка/обновление хоста, конфигурация профиля, управление учётными записями и допусками пользователей, навигация модулей | Прав на изменение/удаление журнала аудита |
| Администратор БД | Развёртывание и сопровождение PostgreSQL, миграции, резервные копии | Доступа к содержимому ДСП в обход решётки; неконтролируемой возможности модифицировать аудит (компенсирующий контроль — ТБ-031) |
| Оператор загрузки | Загрузка/OCR/чистка/разметка корпуса, подтверждение грифа при ingestion (ТБ-024) | Прав на изменение допусков пользователей |
| Офицер ИБ-аудита | Контроль журнала аудита (метаданные событий), контроль режим-гейта | Доступа к чувствительному содержимому выше своего допуска (ТБ-032) |

> Конкретный персональный состав ролей, их сопоставление штатным должностям и регламент назначения — **уточняется с заказчиком (Э1)** и фиксируется регламентом управления доступом (ТО-орг-02).

**1.4.** Принципиальное ограничение. Система **не принимает решений** и **не является источником права**; любой генерируемый документ — проект, требующий проверки человеком (HITL, ТБ-042, ТЭ-002). Администратор обеспечивает технический и режимный контур, в котором это правило соблюдается, но не подменяет экспертное суждение пользователей.

## 2. Требования к инфраструктуре изолированного контура

Инфраструктуру изолированного контура (серверы, GPU-узел, хранилище, сеть) обеспечивает заказчик (ПОДГ-01, ТО-тех-01/02). Ниже — состав узлов и параметры, подлежащие согласованию.

### 2.1. Состав узлов (целевая топология)

| Узел | Назначение | Примечание |
|---|---|---|
| Хост приложения | `ISC.AI.Web` (Blazor Server), единственная точка композиции профиля (ТС-004, ТО-прог-06) | Применяет фильтр доступа; единственный клиент vLLM (ТБ-044) |
| Узел СУБД | PostgreSQL + pgvector: схемы `core` и `inspector`, эмбеддинги, аудит (ТО-инф-01/02) | Может совмещаться с хостом на старте — решение фиксируется по НФТ (ТН-001) |
| GPU-узел инференса | vLLM, роли моделей `draft` / `analysis` / эмбеддинги (ТО-прог-01/03) | Своп отключается/шифруется (ТБ-043) |
| Хранилище | Исходные документы, индексы, резервные копии (ТО-тех-02) | Доступ ОС к каталогам разграничивается (ТБ-062) |

Все узлы размещаются исключительно on-premise, в сети без доступа в Интернет и иные внешние сети; никакие данные не передаются вовне (ТБ-052).

### 2.2. Аппаратные параметры (вход для НФТ)

Требования к GPU/VRAM, ОЗУ, дисковому хранилищу определяются по выбранным моделям и объёму корпуса и являются входом для раздела НФТ (ТО-тех-01, ТН-001). На момент черновика **все нижеперечисленные значения — уточняется с заказчиком (Э1)**:

| Параметр | Значение | Источник |
|---|---|---|
| GPU / объём VRAM | уточняется с заказчиком (Э1); зависит от выбора и квантизации моделей (ТО-прог-03) | ТО-тех-01, ТН-001 |
| ОЗУ хоста и узла СУБД | уточняется с заказчиком (Э1) | ТО-тех-01 |
| Дисковое хранилище (документы/индексы/эмбеддинги/резервные копии) | уточняется с заказчиком (Э1); планируется по корпусу НПА и истории проверок | ТО-тех-02, ТН-001 |
| Число одновременных пользователей | уточняется с заказчиком (Э1) | ТН-001 |
| Целевые задержки RAG/инференса (p50/p95) | подтверждаются нагрузочным тестом на узле заказчика (ТН-002), не задаются «на бумаге» | ТН-002 |
| RPO / RTO | уточняется с заказчиком (Э1) | ТНД-003 |

### 2.3. Выбор сертифицируемых компонентов (раннее решение)

Требуемый класс защищённости информации, обязательность аттестации/сертификации и перечень обязательных сертифицированных СрЗИ/СКЗИ/ОС запрашиваются у заказчика **на Э1, до построения инфраструктурного фундамента**, чтобы исключить переделку (ТБ-061, ПОДГ-04). Решения, влияющие на сертифицируемость (ОС, СУБД, СКЗИ, режим шифрования), фиксируются ADR (ДОК-06). Настоящее руководство дополняется конкретикой по итогам этих решений — **заполняется по мере реализации**.

## 3. Состав дистрибутива и контролируемый перенос за периметр

### 3.1. Состав поставляемого дистрибутива (ТИ-001)

Состав и формат дистрибутива, пригодного для офлайн-инсталляции, определяются на Э1; целевой минимальный комплект:

1. Приложение-хост `ISC.AI.Web` и сборки профиля «Инспектор» (опубликованная сборка под целевую ОС).
2. Миграции БД для обеих схем (`core`, `inspector`) — идемпотентные SQL-скрипты и/или артефакты EF Core (ТО-прог-08, ТО-инф-01).
3. Веса моделей / образы инференса для ролей `draft`, `analysis` и модели эмбеддингов (ТО-прог-03).
4. Шаблоны документов и файлы-шаблоны промптов профиля (ТО-лнг-03).
5. Конфигурация развёртывания (примеры `appsettings`, привязки моделей по ролям, параметры подключения) — без секретов в открытом виде (ТБ-013).
6. Внутренний офлайн-фид пакетов NuGet и файлы `nuget.config` / `Directory.Packages.props` (ТБ-050; см. раздел 8).
7. Контрольные суммы/подписи на каждый артефакт и манифест комплектности (ТБ-051, ТИ-002).
8. Настоящий комплект документации (ДОК-01..ДОК-10).

> Точный перечень файлов, формат упаковки (архив/носитель/образ) и имена артефактов — **заполняется по мере реализации**.

### 3.2. Контролируемый перенос за периметр (ТБ-051, ТИ-002)

Перенос любых внешних артефактов (пакеты, веса моделей, дистрибутив, обновления) внутрь периметра выполняется только по контролируемой процедуре с проверкой целостности:

1. Подготовка артефактов во внешней доверенной зоне; фиксация контрольных сумм/подписей.
2. Перенос на контролируемом носителе согласно регламенту учёта носителей заказчика.
3. Проверка контрольных сумм/подписей внутри периметра до установки (ТИ-002).
4. Запись факта переноса в журнал переноса артефактов (кто, что, когда, контрольная сумма) — организационный журнал, ведётся заказчиком.

Организацию внутреннего доверенного фида и процедуру контролируемого переноса обеспечивает заказчик (ПОДГ-05).

## 4. Офлайн-инсталляция в air-gap

Предусматривается офлайн-инсталлятор/процедура, не требующая доступа к Интернету (ТИ-003). Учебная инсталляция и обновление отрабатываются на стенде до применения в продуктивном контуре.

### 4.1. Порядок первичной инсталляции (целевой)

1. Проверить готовность инфраструктуры (раздел 2) и факт переноса дистрибутива с контролем целостности (ТИ-002).
2. Развернуть PostgreSQL + pgvector (раздел 5).
3. Применить миграции в порядке `core → inspector` (раздел 6, ТО-прог-08).
4. Установить и сконфигурировать узел инференса vLLM, загрузить веса моделей, настроить роли (раздел 7).
5. Развернуть хост `ISC.AI.Web`, подключить профиль «Инспектор» (точка композиции — ТО-прог-05/06), задать строки подключения и привязки моделей.
6. Настроить аутентификацию/авторизацию, завести учётные записи и допуски (раздел 9, ТБ-010..016).
7. Включить и проверить защитные контуры: фильтр доступа (ТБ-020/021), грунтовку (ТБ-040), защиту канала vLLM (ТБ-044), append-only аудит и его якорение (ТБ-031), защиту at-rest (ТБ-062), маркировку экспорта (ТБ-033), fail-closed загрузку (ТБ-024).
8. Выполнить проверку комплектности и целостности после установки (ТИ-002).
9. Прогнать gate-тесты GATE-1/2/3 на фактической конфигурации контура (раздел 12, ПР-002).

> Точные команды установки, имена служб ОС (автозапуск — ТНД-005), пути и шаги конфигурации — **заполняется по мере реализации** (рабочие этапы Э2–Э3).

### 4.2. Офлайн-обновление

Процедура обновления также офлайн (ТИ-003) и включает: перенос обновлённого дистрибутива с контролем целостности (ТБ-051), резервное копирование БД и хранилища перед обновлением (раздел 10), применение новых миграций в порядке `core → inspector` (раздел 6), при необходимости — план отката (ТО-прог-08, ТНД-004). Регламент офлайн-обновления зависимостей и миграций — часть ТО-орг-02.

## 5. Развёртывание PostgreSQL + pgvector

**5.1.** Данные размещаются в одной СУБД PostgreSQL в двух схемах (ТО-инф-01):

- `core` — универсальные таблицы: документы, чанки НПА, эмбеддинги, аудит, пользователи, задания индексации;
- `inspector` — доменные сущности профиля (Проверка, Нарушение, Риск, Поручение и др., ТО-инф-05).

Каждая схема ведёт собственную историю миграций.

**5.2.** Векторное хранилище — расширение **pgvector**. Создание расширения и индексов входит в процедуру первичного развёртывания и в bootstrap миграций (ТО-инф-02, ТО-прог-08).

**5.3.** Обязательные метаданные документа/чанка/эмбеддинга закладываются с самого начала (ТО-инф-03): тип документа; дата; редакция и её статус (действующая / утратила силу); подразделение; гриф; источник; идентификатор нормы. Поля **грифа и подразделения — `NOT NULL`** (поддержка fail-closed загрузки ТБ-024). Добавление этих полей задним числом считается недопустимым по умолчанию.

**5.4.** Разграничение доступа ОС. Доступ операционной системы к файлам данных PostgreSQL и к каталогам индексов/эмбеддингов разграничивается (ТБ-062, ТО-тех-02). Учётная запись службы СУБД и каталоги данных изолируются от учётных записей пользователей и оператора загрузки.

**5.5.** Управление ролями БД. Для аудита выделяется роль без прав `UPDATE`/`DELETE` на таблицу аудита (append-only, ТБ-031). Доступ суперпользователя PostgreSQL отнесён к модели угроз как отдельный класс нарушителя с компенсирующим контролем (внешнее якорение аудита, раздел 11).

> Конкретные версии PostgreSQL и pgvector, параметры кластера, расположение табличных пространств, индексные стратегии pgvector (тип индекса, параметры) — **заполняется по мере реализации**; выбор СУБД, влияющий на сертифицируемость, фиксируется ADR на Э1 (ТБ-061).

## 6. Применение и откат миграций офлайн

Миграции выполняются предсказуемо и обратимо в изолированном контуре; регламент — офлайн (ТНД-004, ТО-прог-08). Учебное применение и откат отрабатываются на стенде до продуктива.

### 6.1. Порядок применения

1. **Резервная копия** БД и хранилища перед любым изменением схемы (раздел 10).
2. **Bootstrap**: создание расширения pgvector (ТО-инф-02), при необходимости — схем и служебных ролей.
3. **Схема `core`** — применение миграций ядра (универсальные таблицы, аудит, эмбеддинги).
4. **Схема `inspector`** — применение миграций профиля (доменные сущности), **строго после** `core` (порядок `core → inspector`, ТО-прог-08).
5. **Проверка**: контроль успешности, целостности расширения и индексов, наличия обязательных `NOT NULL` полей (ТО-инф-03).

Скрипты миграций — **идемпотентные SQL** (повторный запуск не нарушает состояние), что согласуется с идемпотентностью индексации и дедупликацией (ТНД-002).

### 6.2. Откат

Для каждой миграции предусматривается процедура отката (ТО-прог-08). Откат выполняется в обратном порядке (`inspector → core`) и сопровождается восстановлением из резервной копии при невозможности обратимого отката отдельной миграции. EF Core не создаёт внешних ключей между контекстами `core`/`inspector` (ТО-инф-06), что упрощает раздельное версионирование схем, но требует контроля ссылок на уровне приложения.

> Конкретные команды применения/отката (инструмент миграций, точки входа, имена скриптов), карта обратимости каждой миграции и контрольные SQL-проверки — **заполняется по мере реализации**.

## 7. Настройка vLLM и моделей; защита канала инференса

### 7.1. Роли моделей (ТО-прог-01/03)

Инференс — локальный сервер vLLM с OpenAI-совместимым API. Доступ к моделям из приложения — через нейтральную абстракцию (`IChatClient`, `Microsoft.Extensions.AI`); связка «модель ↔ задача» задаётся конфигурацией через keyed-регистрацию по роли (ТО-прог-02). Роли:

| Роль (keyed) | Назначение |
|---|---|
| `draft` | Быстрая генерация/форматирование документов |
| `analysis` | Анализ и сверка НПА, длинный контекст |
| эмбеддинги | Отдельная модель векторизации (ru/ky) |

> **Важно по версиям моделей.** Названия моделей из презентационных материалов («Gemma 4», «Qwen 3.5») **не соответствуют реальным релизам** и подлежат замене на существующие версии (ТО-прог-03). Конкретные семейства, веса, размер и квантизация фиксируются конфигурацией под бюджет VRAM, согласуются и бенчмаркаются на Э1/Э5. Выбор модели эмбеддингов — предмет отдельного бенчмарка на реальном юридическом корпусе с **раздельным измерением качества ru и ky** (ТО-лнг-02, КИ-03). До этого момента — **уточняется с заказчиком (Э1)**.

### 7.2. Защита канала «хост ↔ vLLM» (ТБ-044) — обязательно

Для конфигураций с ДСП канал инференса защищается **обязательно** (не «при необходимости»):

1. vLLM привязывается к внутреннему/loopback-интерфейсу и **недоступен с произвольных АРМ**.
2. Доступ к API vLLM — **только от хоста `ISC.AI.Web`**, с аутентификацией.
3. Сетевые ограничения (firewall/namespace) задокументированы в модели угроз (ДОК-03) как граница доверия.
4. Прямой доступ к vLLM в обход хоста исключён, поскольку фильтр доступа применяется в хосте (ТБ-044, ТБ-020).

### 7.3. Защита промежуточных артефактов инференса (ТБ-043)

Промежуточные артефакты инференса — носители сведений. Администратор обеспечивает:

- запрет записи полнотекстовых промптов/ответов с ДСП в технологические логи (приложения, веб-сервера, vLLM, ОС) в открытом виде, либо подчинение таких логов решётке доступа;
- ограниченный срок жизни и очистку кэша (в т.ч. KV-cache) и временных файлов;
- **отключение или шифрование свопа** на GPU-узле;
- отключение телеметрии моделей/инструментов в режимном контуре;
- срок хранения и защиту журнала промптов (увязка с ТБ-032).

> Конкретные параметры запуска vLLM, файлы конфигурации логирования, политики кэша и свопа — **заполняется по мере реализации**; проверяются аудитом конфигурации логирования, vLLM и ОС.

## 8. Внутренний фид пакетов NuGet (офлайн-сборка)

Сборка и восстановление зависимостей должны быть возможны **офлайн** (ТБ-050). На момент ТЗ файлы `nuget.config` и `Directory.Packages.props` отсутствуют, текущая сборка идёт из внешних/кэшированных источников; переход на офлайн-фид — отдельный проверяемый результат Э1 (ТЗ, 6.1; ТБ-050).

Целевая настройка:

1. Развернуть **внутренний доверенный фид** пакетов в периметре (наполняется через контролируемый перенос, ТБ-051, ПОДГ-05).
2. `nuget.config` ограничивает источники **единственным офлайн-фидом** (внешние источники отключены).
3. Версии пакетов фиксируются централизованно в `Directory.Packages.props` (Central Package Management).
4. Проверка: сборка в изолированной среде без доступа в Интернет (критерий Э1).

> Адрес/путь внутреннего фида, конкретное содержимое `nuget.config` и `Directory.Packages.props`, процедура пополнения фида — **заполняется по мере реализации**.

## 9. Управление доступом: роли, допуски, отзыв

Управление доступом регламентируется ТО-орг-02; назначение/отзыв ролей и допусков — ПОДГ-03. Доступ к системе — только после аутентификации; анонимный доступ запрещён (ТБ-010).

### 9.1. Роли пользователей и решётка доступа

Роли пользователей: инспектор, руководство, администратор (ТП-001). Авторизация — ролевая и атрибутная: доступ к данным определяется **ролью, допуском и подразделением** по решётке «гриф × роль × подразделение → разрешение» (ТБ-002, ТБ-011). Каждый документ/чанк/эмбеддинг несёт атрибут грифа и принадлежности к подразделению.

**Допуск пользователя — обязательный вход фильтра доступа** (ТБ-012): без установленного субъекта с допуском операции извлечения данных не выполняются. Фильтр работает по принципу **fail-closed** (ТБ-021): при отсутствии/неопределённости атрибутов доступ запрещается.

### 9.2. Управление учётными данными и сессиями

- Парольная политика и второй фактор — по политике заказчика и классу защищённости (ТБ-013, ТБ-061). Секреты хранятся **вне исходного кода и конфигурационных файлов в открытом виде** (ТБ-013).
- Управление сессиями (ТБ-014): таймаут неактивной сессии и принудительное завершение; повторная аутентификация для привилегированных действий.
- Принцип наименьших привилегий и организационное разделение ролей (ТБ-015) — см. также п. 1.3.

### 9.3. Жизненный цикл допусков: выдача, изменение, отзыв (ТБ-016)

| Действие | Порядок | Эффект |
|---|---|---|
| Выдача допуска | По заявке, с фиксацией в аудите | Доступ в пределах решётки (ТБ-002) |
| Изменение допуска | С фиксацией в аудите | Пересчёт прав по решётке |
| **Немедленный отзыв** (увольнение/ротация) | С фиксацией в аудите | **Вступает в силу для retrieval немедленно** |

Отзыв допуска вступает в силу для извлечения данных немедленно (ТБ-016). Корректность немедленного отзыва проверяется тестом отзыва.

> Конкретный механизм аутентификации (поставщик удостоверений, схема хранения секретов, способ настройки второго фактора), экранные формы управления пользователями и точные шаги назначения допусков — **заполняется по мере реализации** (рабочий этап Э2, ТБ-010..016).

## 10. Резервное копирование, восстановление и защита at-rest

### 10.1. Резервное копирование и восстановление (ТБ-060, ТНД-003)

- Резервируются БД и файловое хранилище.
- Резервные копии режимных данных **шифруются** (ТБ-060).
- Процедура восстановления — **проверяемая**, отрабатывается учебным восстановлением на соответствие RPO/RTO (ТНД-003, ТБ-060).
- Регламент резервного копирования и восстановления — часть ТО-орг-02.

Числовые значения RPO/RTO — **уточняется с заказчиком (Э1)** (ТН-001, ТНД-003).

### 10.2. Защита данных at-rest (ТБ-062)

Защита ДСП-данных at-rest распространяется **не только на резервные копии**, но и на основную БД и файловое хранилище:

- шифрование носителей/тома или прозрачное шифрование БД — по политике заказчика и классу защищённости;
- **управление ключами вне БД**;
- разграничение доступа ОС к файлам данных PostgreSQL и к каталогам индексов/эмбеддингов (см. также п. 5.4).

Механизм увязывается с сертифицированными СКЗИ (ТБ-061). Конкретный режим шифрования и схема управления ключами фиксируются ADR на Э1 и **заполняется по мере реализации**.

### 10.3. Устойчивость к перезапуску (ТНД-005)

После восстановления питания службы (хост, GPU-узел, СУБД) автозапускаются, состояние восстанавливается, незавершённые задания индексации не теряются сверх RPO. Администратор настраивает автозапуск служб ОС и проверяет это тестом перезапуска/восстановления. Сбой одного фонового процесса (например, индексации) не должен приводить к отказу интерактивной части (ТНД-001).

## 11. Аудит и его якорение

### 11.1. Состав и неизменяемость (ТБ-030, ТБ-031)

Ведётся **полный неизменяемый журнал аудита**: вход, просмотр, поиск, генерация, экспорт, печать, выгрузка — кто, что, когда (ТБ-030).

Неизменяемость обеспечивается технически (ТБ-031):

- журнал — **append-only**: роль БД без прав `UPDATE`/`DELETE` на таблицу аудита;
- **хеш-цепочка записей обязательна** (не рекомендация).

### 11.2. Якорение вовне (защита от суперпользователя БД, ТБ-031)

Суперпользователь PostgreSQL способен на `TRUNCATE`/пересоздание таблицы или отключение триггеров, поэтому аудит **периодически якорится вовне** административного контроля администратора БД:

- append-only выгрузка на отдельный носитель/узел, **либо**
- периодическая публикация хеша-якоря.

Роль суперпользователя БД явно отнесена к модели угроз (ДОК-03) с описанием компенсирующего контроля. Администратор настраивает периодичность якорения и его носитель/узел.

### 11.3. Разделение метаданных и содержимого (ТБ-032)

Журнал аудита и сохранённые промпты/выводы ИИ — **производные носители грифа**. В журнале разделяются:

- **метаданные события** (субъект, действие, время, идентификаторы, гриф) — доступны роли ИБ-аудита;
- **чувствительное содержимое** (тексты промптов/выводов, наименования ДСП-документов) — под решёткой доступа к самим данным.

Роль аудита видит факт и метаданные, но не содержимое выше своего допуска.

> Периодичность якорения, формат и носитель выгрузки/публикации хеша, конкретная схема хеш-цепочки — **заполняется по мере реализации**.

### 11.4. Контроль канала экспорта (ТБ-033)

Канал вывода/экспорта контролируется как режимный — это основной путь экфильтрации ДСП за пределы приложения. Администратор обеспечивает:

- **автоматическую маркировку** каждого экспортируемого материала со сведениями ограниченного доступа: гриф и учётные реквизиты (гриф, учётный номер, исполнитель) проставляются в теле документа и в метаданных файла `.docx`;
- **наследование грифа результата как максимума грифов извлечённых фрагментов** (производный носитель, увязка с ТБ-032): итоговый документ не может иметь гриф ниже самого защищённого из фрагментов, использованных при его подготовке;
- **фиксацию экспорта и печати в аудите** с привязкой к субъекту и грифу (ТБ-030);
- **вынос за контролируемое хранилище** — только по регламенту учёта носителей ДСП.

Маркировку выполняет движок документов (порт рендеринга, ДОК-05); отключить её параметрами вызова нельзя.

## 12. Чек-лист организационного режим-гейта перед первой загрузкой ДСП

**Обработка реальных сведений ДСП запрещена** до одновременного выполнения всех условий ниже (ТБ-063). До этого момента система эксплуатируется **только на обезличенных/тестовых данных** (ПОДГ-06). По итогам оформляется **акт готовности режима** (ПОДГ-06); для приёмки конфигурации с обработкой реальных ДСП этот акт обязателен (ПР-005).

| № | Условие режим-гейта | Требование | Отметка |
|---|---|---|---|
| 1 | Утверждена модель угроз (с матрицей трассировки) | ДОК-03, ТБ-001 | ☐ |
| 2 | Пройден GATE-1 (фильтр доступа по грифу; неразличимость ответа по контенту, метаданным, счётчикам, ранжированию, времени и тексту ошибки) на фактической конфигурации контура | GATE-1, ТБ-020/021/022/023 | ☐ |
| 3 | Пройден GATE-2 (грунтовка) на фактической конфигурации | GATE-2, ТБ-040 | ☐ |
| 4 | Пройден GATE-3 (версионность редакций) на фактической конфигурации | GATE-3, ТО-инф-04, ТФ-НПА-02 | ☐ |
| 5 | Настроены и проверены допуски/решётка (тест доступа) | ТБ-002, ТБ-011/012 | ☐ |
| 6 | Включена защита at-rest | ТБ-062 | ☐ |
| 7 | Включена маркировка экспорта | ТБ-033 | ☐ |
| 8 | Включена защита канала vLLM | ТБ-044 | ☐ |
| 9 | Включён append-only аудит (с якорением) | ТБ-031 | ☐ |
| 10 | Включена fail-closed загрузка (ingestion) | ТБ-024 | ☐ |
| 11 | Получено письменное разрешение уполномоченного лица/офицера ИБ заказчика | ТБ-063 | ☐ |

Невыполнение хотя бы одного пункта — основание не допускать загрузку реальных ДСП-сведений. Невыполнение любого gate-критерия (пп. 2–4) — основание для отказа в приёмке независимо от прочих результатов (ТЗ, 7.4).

## 13. Гарантированное удаление данных

Процедура **гарантированного удаления** документа и всех его производных (ТБ-064) применяется при отзыве, ошибочной загрузке или изменении грифа документа. Удаляются:

- исходный документ;
- чанки;
- эмбеддинги в pgvector;
- индексы;
- журнал промптов (с учётом срока хранения, ТБ-043);
- при необходимости — обработка в резервных копиях.

Удаление **фиксируется в аудите** (ТБ-064). Процедура увязывается с дедупликацией и версионностью редакций (ТО-инф-07): удаление учитывает, что один источник мог породить несколько производных. Регламент санитизации и вывода из эксплуатации носителей с ДСП — по политике заказчика.

Корректность удаления из всех производных проверяется тестом удаления (ТБ-064).

> Точные шаги операции удаления (точка входа, охват каскада по схемам `core`/`inspector`, обработка резервных копий) и регламент санитизации носителей — **заполняется по мере реализации**.

## 14. Эксплуатация, обслуживание, типовые неисправности

**14.1. Регламент эксплуатации и окна обслуживания** определяются заказчиком (ТОБ-001, увязка с ТН-004, ТНД-006). Целевая доступность в рабочее время и окна обслуживания — **уточняется с заказчиком (Э1)**.

**14.2. Плановое ТО** GPU-узла инференса и СУБД (профилактика, обновление в офлайн-режиме) выполняется по регламенту (ТОБ-002, ТО-прог-08).

**14.3. Управляемая деградация** (ТН-003). При недоступности модели/индекса система сообщает об ошибке и **не выдаёт непроверенный результат как готовый** (увязка с грунтовкой ТБ-040). Администратор контролирует доступность vLLM и индексов; восстановление — по регламенту.

**14.4. Сопровождение корпуса НПА.** Обновление знаний — это замена/добавление документа с переиндексацией; переобучение моделей не требуется (ТО-инф-07). Загрузка/OCR/чистка/разметка выполняются выделенным персоналом по регламенту сопровождения корпуса (ТО-орг-01). При загрузке действует **fail-closed**: документ/чанк без явно установленных грифа и подразделения не индексируется; обязателен шаг подтверждения грифа оператором; гриф по умолчанию — максимально ограничительный (ТБ-024).

> Перечень типовых неисправностей с диагностикой и действиями по устранению (служба не стартует, vLLM недоступен, миграция не применилась, индексация зависла, нарушение целостности аудита) — **заполняется по мере реализации** по результатам опытной эксплуатации (Э5).

## 15. Открытые вопросы (уточняется на Э1)

Перечень значений и решений, которые фиксируются совместно с заказчиком на рабочем этапе Э1 и до того отражены в документе как «уточняется с заказчиком (Э1)» либо «заполняется по мере реализации»:

1. **Аппаратные требования**: GPU/VRAM, ОЗУ, дисковое хранилище, число одновременных пользователей (ТО-тех-01/02, ТН-001).
2. **НФТ и SLA**: целевые задержки p50/p95 (подтверждаются нагрузочным тестом ТН-002), целевая доступность и окна обслуживания (ТН-004, ТОБ-001), RPO/RTO (ТНД-003).
3. **Сертификация/режим**: требуемый класс защищённости, обязательность аттестации/сертификации, перечень сертифицированных СрЗИ/СКЗИ/ОС; решения, влияющие на сертифицируемость, — ADR (ТБ-061, ПОДГ-04, ДОК-06).
4. **Защита at-rest**: режим шифрования (тома/прозрачное шифрование БД) и схема управления ключами вне БД (ТБ-062).
