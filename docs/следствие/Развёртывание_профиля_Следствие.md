# Сборка и развёртывание профиля «Следствие» («СледствиеAI»)

| | |
|---|---|
| **Документ** | Инструкция к ДОК-13 (архитектура профиля «Следствие»), раздел «Сборка и развёртывание» |
| **Система** | ISC.AI — профиль «Следствие» |
| **Версия** | 0.1 (ЭС3-01, 17.09.2026) |
| **Связь** | ADR-0021 (выбор профиля при сборке), ADR-0019/0020 (векторный поиск, стек распознавания), ADR-0006 (экземпляр на профиль), ADR-0026 (расшифровка речи), ADR-0028 (покадровый просмотр и снимок кадра); ТС-004, ТИ-004, ТБ-062 |

## 1. Принцип

Профиль в поставке ровно один (ТС-004). Репозиторий содержит два профиля — «ИнспекторAI» и
«Следствие», — и выбор делается **при сборке** свойством MSBuild `IscProfile`. По умолчанию (свойство
не задано) собирается «ИнспекторAI»: ни одна существующая поставка не меняется.

## 2. Сборка

```bash
dotnet clean src/core/ISC.AI.Web
dotnet build src/core/ISC.AI.Web/ISC.AI.Web.csproj -p:IscProfile=investigation
dotnet publish src/core/ISC.AI.Web/ISC.AI.Web.csproj -c Release -p:IscProfile=investigation -o publish/investigation
```

`dotnet clean` обязателен при **смене** профиля: каталог `obj/` хоста общий, и в нём остаются
артефакты прежнего варианта (список ссылок, сгенерированный диспетчер Mediator). Возврат к
«ИнспекторAI» — снова `dotnet clean`, затем обычная сборка без свойства.

В Visual Studio то же свойство задаётся переменной окружения `IscProfile=investigation` перед
запуском среды (MSBuild читает переменные окружения как свойства); после смены — «Очистить решение».

Проверка, что собрался нужный профиль: строка запуска в логе
`Хост ISC.AI запущен с профилем investigation (СледствиеAI)`.

**В изолированном контуре** пакеты восстанавливаются только из офлайн-фида и только по фильтру решения
`ISC.AI.Offline.slnf`, а не по `ISC.AI.slnx` ([офлайн-поставка](../reference/офлайн-поставка.md), ТБ-050):
`dotnet restore ISC.AI.Offline.slnf --configfile deploy\offline\nuget.config`, затем команды выше с
`--no-restore`. В фильтре нет процесса-распознавателя речи и его тестов: их пакетов в фиде нет намеренно
(§7.2, ADR-0026 п. 7), распознаватель приходит в контур готовой папкой.

## 2.1. Офлайн-поставка моделей и ffmpeg

Профиль работает в изолированном контуре, поэтому исполняемые артефакты переносятся заранее, каждый
с пином SHA-256 (ТИ-004). Запускать на машине **с** интернетом, затем переносить `deploy/offline`
целиком:

```powershell
deploy\offline\export-vision-models.ps1   # YuNet (детектор) и SFace (векторизатор), ~37 МБ
deploy\offline\export-ffmpeg.ps1          # ffmpeg LGPL-сборки для раскадровки видео, ~148 МБ
```

Скрипт ffmpeg проверяет лицензию дважды: пин архива тегированного релиза и флаги конфигурации самого
бинарника (в LGPL-сборке нет `--enable-gpl` и `--enable-nonfree`); при несовпадении файлы удаляются и
перенос запрещается. В поставке остаются `ffmpeg.exe`, `ffprobe.exe`, библиотеки, `LICENSE.txt` и
манифест `ffmpeg.sha256`. Без ffmpeg (ни в `Vision:Ffmpeg:Folder`, ни в `PATH`) фотографии обрабатываются
полностью, а индексация видео завершается ошибкой при первом обращении (§4).

Проверка раскадровки на месте: `dotnet test tests/ISC.AI.IntegrationTests --filter "Category=Video"`
(тест сам генерирует клип тем же ffmpeg, медиафайлов в репозитории нет). Прогон без поставки —
`--filter "Category!=Video"`.

## 3. База данных

У поставки «Следствие» **своя** БД PostgreSQL с расширением `pgvector` (ADR-0006): на одной БД с
«ИнспекторAI» профиль не разворачивается — словари подразделений (`inspector.division` и
`investigation.division`) разные, а `core.clearance.division_scope` один на всех.

Схемы и порядок наката миграций (у каждой своя история `<схема>.__ef_migrations_history`):

| № | Схема | Контекст | Проект | Переменная окружения со строкой подключения |
|---|---|---|---|---|
| 1 | `core` | `CoreDbContext` | `src/core/ISC.AI.Persistence` | `ISCAI_CORE_CONNECTION` |
| 2 | `docflow` | `DocFlowDbContext` | `src/modules/docflow/ISC.AI.Modules.DocFlow.Data` | `ISCAI_DOCFLOW_CONNECTION` |
| 3 | `media` | `MediaDbContext` | `src/modules/media/ISC.AI.Modules.Media.Data` | `ISCAI_MEDIA_CONNECTION` |
| 4 | `investigation` | `InvestigationDbContext` | `src/profiles/investigation/ISC.AI.Profile.Investigation.Data` | `ISCAI_INVESTIGATION_CONNECTION` |

Пример для схемы `media` (строка с паролем — только в переменной окружения, не в файлах):

```bash
ISCAI_MEDIA_CONNECTION="Server=...;Database=ISC_AI_INV;Username=...;Password=...;SSL Mode=Require" \
dotnet ef database update --project src/modules/media/ISC.AI.Modules.Media.Data --startup-project src/modules/media/ISC.AI.Modules.Media.Data --context MediaDbContext
```

То же из **консоли диспетчера пакетов** Visual Studio (Package Manager Console) — строка подключения
задаётся переменной окружения текущей сессии консоли, затем накат по одному контексту:

```powershell
$env:ISCAI_CORE_CONNECTION="Host=localhost;Port=55432;Database=ISC_AI_INV;Username=postgres"
$env:ISCAI_DOCFLOW_CONNECTION=$env:ISCAI_CORE_CONNECTION
$env:ISCAI_MEDIA_CONNECTION=$env:ISCAI_CORE_CONNECTION
$env:ISCAI_INVESTIGATION_CONNECTION=$env:ISCAI_CORE_CONNECTION

Update-Database -Context CoreDbContext          -Project ISC.AI.Persistence                 -StartupProject ISC.AI.Persistence
Update-Database -Context DocFlowDbContext       -Project ISC.AI.Modules.DocFlow.Data        -StartupProject ISC.AI.Modules.DocFlow.Data
Update-Database -Context MediaDbContext         -Project ISC.AI.Modules.Media.Data          -StartupProject ISC.AI.Modules.Media.Data
Update-Database -Context InvestigationDbContext -Project ISC.AI.Profile.Investigation.Data  -StartupProject ISC.AI.Profile.Investigation.Data
```

`-Project` и `-StartupProject` указывают на ОДИН и тот же проект слоя данных: у каждого есть своя
design-фабрика, которая берёт строку подключения из переменной окружения выше и не требует запуска хоста.
Без переменной фабрика подставляет заглушку без пароля и накат не пройдёт.

Ошибка вида `42P01: relation "investigation.user_role_assignment" does not exist` означает ровно одно:
хост запущен на базе, где схема профиля ещё не создана. Либо накатите четыре миграции выше на эту базу,
либо укажите строки подключения к базе, где они уже применены, в `appsettings.Development.investigation.json`.

**Настройки разработчика — по профилям.** Строки подключения «Следствия» и пути к моделям распознавания
лежат в `src/core/ISC.AI.Web/appsettings.Development.investigation.json`; хост читает его ТОЛЬКО когда
собран с `IscProfile=investigation`. Общий `appsettings.Development.json` строк подключения не содержит
намеренно: у профилей разные базы (ADR-0006), и прописанные в общем файле строки одного профиля уводили
второй в чужую базу — «ИнспекторAI» падал на отсутствующей схеме `inspector`. Своя поставка Инспектора
настраивается симметрично — файлом `appsettings.Development.inspector.json` (в репозитории его нет: по
умолчанию Инспектор работает с топологией из `appsettings.json`).

Миграция `InitialMedia` создаёт HNSW-индекс (`m=16, ef_construction=512`) на `media.face_template`:
сервер должен иметь исправный `pgvector` (`SELECT extversion FROM pg_extension WHERE extname='vector'`)
и достаточный `maintenance_work_mem`. Отдельная БД нужна не из-за pgvector (он исправен), а по ADR-0006:
справочники подразделений у профилей разные, а `core.clearance.division_scope` — один на базу, поэтому
номера подразделений двух профилей в одной БД перемешались бы в допусках.

Миграция `VideoFrameInfo` (ADR-0028) добавляет `media.asset` пять nullable-столбцов: частота кадров, ширина и
высота кадра после автоповорота, носитель-источник и момент записи для снимка кадра. Накатывается теми же
командами, что и остальные миграции `media`, отдельных шагов не требует. Видео, загруженные до неё, получают
частоту и размер кадра при «Переиндексировать» в карточке носителя; до этого шаг «на кадр» в интерфейсе —
40 мс (25 к/с) с явной пометкой, а длительность у них — оценка по раскадровке (округлена вниз до шага выборки),
поэтому кадр за её пределами не отклоняется заранее: решает ffmpeg. У незавершённых записей Matroska/WebM без
длительности в заголовке она после пробы остаётся неизвестной (ноль не записывается, оценка по раскадровке не
подставляется) — за концом снова решает ffmpeg; точную длительность им даёт расшифровка речи, если есть звук.

Миграция `SearchMultiProbe` (ADR-0046, поиск по всем эталонам фигуранта) добавляет три необязательных столбца:
`media.search_session.probe_face_ids` (эталоны поиска) и `media.search_candidate.probe_face_id`,
`probe_match_count` (эталон лучшего совпадения и число совпавших эталонов). Накатывается теми же командами, что и
остальные миграции `media`; прежние сессии не меняются (у них столбцы пусты). Без этой миграции хост с новой
версией не прочитает сессии поиска — накатить до запуска.

Миграция `AudioWaveform` (ADR-0047, проигрыватель аудиозаписи) добавляет `media.asset` три необязательных столбца:
`waveform_peaks`, `waveform_step_ms`, `waveform_version` — волна записи (огибающая громкости, единицы килобайт). Волна
строится ffmpeg при первом открытии карточки аудио и запоминается; у прежних аудиозаписей столбцы пусты до первого
открытия. Накатывается теми же командами, что и остальные миграции `media`; без неё хост с новой версией не прочитает
носители — накатить до запуска.

## 4. Конфигурация хоста (`appsettings.json`, секреты — user-secrets / переменные окружения)

| Ключ | Назначение |
|---|---|
| `ConnectionStrings:Core/DocFlow/Media/Investigation` | одна БД профиля, четыре схемы; пароль — общий секрет `Database:Password` (`Database__Password` в окружении) |
| `Storage:BasePath` | корень файлового хранилища ядра (носители `media-originals`, вырезки `media-faces`, вырезки проб `media-probes`, ленты кадров видео `media-filmstrips` — ADR-0038); в проде — защищённый том (ТБ-062) |
| `Vision:Detector:Path/Sha256`, `Vision:Embedder:Path/Sha256` | модели YuNet и SFace из `deploy/offline/models` с пинами SHA-256; при несовпадении модель не загружается (ТИ-004) |
| `Vision:Ffmpeg:Folder` | папка с бинарниками ffmpeg/ffprobe LGPL-сборки (`deploy/offline/export-ffmpeg.ps1`, пин SHA-256, ADR-0020) — раскадровка, проба и вырезка кадра, волна аудиозаписи (ADR-0047). **Пусто — ffmpeg/ffprobe ищутся в `PATH` без проверки пина**: посторонний бинарник (GPL-сборка) нарушит ТСТ-004, а при пустом `PATH` каждое видео получит статус «ошибка» при первом обращении. В поставке задавать явно (`deploy/offline/ffmpeg/win-x64`) |
| `Vision:Ffmpeg:MaxConcurrentFrameExtractions` | предел одновременных процессов ffmpeg на вырезку и пробу кадра (покадровый просмотр, снимок кадра — ADR-0028); по умолчанию (не задано или ≤ 0) половина ядер процессора, не меньше 1; на раскадровку при индексации (фоновая, по одной задаче) не распространяется. Тем же числом ограничено построение волны аудиозаписи (ADR-0047) — отдельный счётчик: волна не занимает процессы кадров; ожидание — в пределах 10 минут, дальше — «Сервер занят построением волн записей…». Сверх предела запросы ждут свободного процесса в пределах общего срока 60 с, дальше — ошибка «Сервер занят вырезкой кадров…» с указанием предела и ключа. Второй рубеж — лимитер эндпоинта кадра, политика `media-frames` (2 одновременных запроса, очередь 4, сверх — 429 без тела); ключа не имеет; партиция — адрес клиента (лимитер в хосте стоит до аутентификации; за обратным прокси нужен `UseForwardedHeaders`, он включён); в режиме `Auth:Mode=Dev` лимитера нет |
| `Vision:Detection:*`, `Vision:Quality:*` | пороги детекции и пригодности лиц (стартовые, калибруются на пилоте — ТО-мат-08) |
| `Media:Upload:MaxFileBytes` | предел размера видео и аудио, байт (ADR-0040): по умолчанию 16 ГБ, допустимо от 200 МБ до 64 ГБ, значение вне диапазона — к границе. Фото — всегда до 200 МБ (раскодируются в памяти). Задавать по свободному месту на защищённом томе: файл занимает место во временном каталоге при приёме и при обработке и ещё раз в хранилище |
| `Media:Import:Roots` | каталоги диска сервера, откуда разрешён импорт архива (ADR-0041): массив путей или строка через `;`, только абсолютные. Каталог внутри хранилища материалов (`Storage:BasePath`) или временного каталога исключается с причиной на экране импорта. Пусто — импорт выключен. Учётная запись службы должна иметь право чтения |
| `Media:Import:ProcessingSlots` | сколько носителей архива одновременно стоит в общей очереди обработки, по умолчанию 1, допустимо 1–8: новые материалы следователей ждут не дольше обработки стольких носителей архива |
| `Media:Search:CandidateListSize/Min/Max` | длина кандидат-листа по умолчанию 20, допустимо 5..50 (ТН-008) |
| `Media:Search:MaxCosineDistance` / `MaxAllowedCosineDistance` | порог отсечения и потолок, выше которого пользователь ослабить порог не может (ТФ-ПЛ-06) |
| `Media:Search:HnswEfSearch` | ширина обхода HNSW (200 — проверенная пара к `ef_construction=512`, ADR-0019) |
| `Media:Search:ProbeCopyMaxBytes` | до какого размера копия пробного изображения кладётся в аудит (ТБ-072) |
| `Media:Search:AutoSuggest:Enabled` / `MaxCosineDistance` / `CandidatesPerReference` | автопредложение связи с фигурантами после индексации носителя (ТФ-ПЕР-09, ADR-0035): выключатель (выключает только `false`), порог (0,5 — до калибровки на пилоте; не мягче `MaxCosineDistance` и `MaxAllowedCosineDistance`), не больше стольких кандидатов на один эталон (по умолчанию 5). Предложения идут в общую очередь верификации с пометкой «предложено системой»; подтверждают два человека |
| `Media:Video:SampleFps` | частота выборки кадров при раскадровке (ТО-мат-06) |
| `Media:Video:TrackMinSimilarity` / `TrackMaxGapSeconds` | треки лиц в видео (ТФ-ПЕР-02, ADR-0037): схожесть шаблонов, с которой лицо соседнего кадра продолжает трек (0,5 — до калибровки на пилоте), и наибольший разрыв трека в секундах (3 — при выборке 1 кадр/с лицо может пропасть на два кадра). По трекам появление фигуранта показывается отрезком «с … по …»; видео, проиндексированные раньше, получают треки после «Переиндексировать» |
| `Investigation:Retention:PurgeTemplatesOnCaseClosure` | удалять ли шаблоны лиц и вырезки при закрытии дела (регламент ТБ-074 с актом). По умолчанию `false` — хранятся, пока хранится дело (ADR-0024, решение заказчика): иначе человек из оконченного дела не найдётся по новому |
| `Auth:Mode` | только `Local`: в режиме `Dev` у субъекта нет идентификатора, все гварды по ролям отказывают, администрирование недоступно |

## 5. Первый вход и первичная настройка

1. Учётка по умолчанию создаётся на пустом реестре (`Auth:DefaultAccount`) с временным паролем; первый вход уводит на `/account/password`.
2. Пока нет ни одного Администратора, роли, допуски и справочник подразделений открыты любому вошедшему (режим первичной настройки, `AdministrationRule`); назначьте себе роль **Администратор**: меню «Пользователи» (`/admin/users`) → карточка сотрудника → раздел «Роль» — режим закрывается. Прежние адреса `/admin/roles` и `/admin/clearances` ведут на тот же экран.
3. Заведите подразделения (`/admin/divisions`) — их идентификаторы попадают в допуски.
4. Выдайте допуски: «Пользователи» → карточка сотрудника → раздел «Допуск» — максимальный гриф и галочки подразделений деревом (рядом — отдел ОН/ОУ; галочка у управления не открывает его отделы, для ветки целиком — «+ вложенные»), затем «Сохранить допуск»; без допуска ни одно дело не видно (fail-closed, ТБ-020/021).
5. Назначьте роли следователей, экспертов по лицам и верификаторов (ТП-004): одно лицо не может быть экспертом и верификатором одного результата (ТБ-073).
6. Поиск по лицу возможен только в деле, у которого есть **основание** (поручение, постановление, ОРМ) — добавляется в карточке дела (ТБ-071).

## 6. Что не входит в первый срез (ЭС3-01)

- ~~Учётные записи и журнал аудита из интерфейса~~ — **сделано** (ADR-0023, пакет `src/modules/admin`):
  «Пользователи» `/admin/users` (учётная запись, роль и допуск — в карточке сотрудника), `/admin/audit` и смена своего пароля на `/account/password`.
  Команда хоста `create-account` осталась резервным путём для самой первой учётки.
- ~~Регламент удаления шаблонов по закрытию дела с актом (ТФ-ДЕЛ-04, ТБ-074)~~ — **сделано** (ADR-0024),
  но по умолчанию **ВЫКЛЮЧЕН** решением заказчика: шаблоны хранятся, пока хранится дело, чтобы человек
  из оконченного дела находился по новому. Включается ключом
  `Investigation:Retention:PurgeTemplatesOnCaseClosure = true` — тогда закрытие снимает шаблоны и вырезки
  и пишет акт в карточку дела (носители, кадры, лица и документы сохраняются всегда).
  Закрытые дела в поиск по лицу сами не попадают: оператор включает их галочкой «искать и по закрытым
  делам», и это фиксируется в журнале (ТФ-ПЛ-05, ТБ-072).
- **Уничтожение дела целиком** — кнопка «Уничтожить дело…» в карточке, только Администратору (ADR-0025).
  Оператор вводит номер дела и основание; полный состав уничтожаемого записывается в журнал до
  удаления. Уничтожаются носители дела со всеми производными, история поисков, фигуранты, эталоны,
  появления, основания и само дело; сохраняются документы документооборота (снимается привязка) и
  носители, привязанные ещё и к другим делам.
- Изображения TIFF/HEIC не принимаются (ADR-0020). ~~Видео MKV/AVI/MOV смотрится через скачивание оригинала~~ —
  **сделано** (ADR-0028): контейнеры, которые браузер не воспроизводит (mkv, avi, mov, 3gp), смотрятся покадрово
  через серверный просмотрщик кадров — кадр вырезается ffmpeg из оригинала по запросу, под той же решёткой, что
  и файл носителя; скачивание оригинала остаётся. Для mp4/webm шаг «на кадр» делает браузер. В карточке
  носителя: кнопки «◀ кадр»/«кадр ▶» (клавиши `,` и `.`), таймкод до миллисекунды и номер кадра по нативной
  частоте, кнопка «Снимок кадра» — PNG кадра из оригинала становится новым фото-носителем того же дела с
  грифом источника, проходит индексацию лиц и дедупликацию как загруженное фото.
- ~~Потоковый приём больших видео~~ — **сделано** (ADR-0040): файл принимается потоком, без загрузки в память. Фото —
  до 200 МБ, видео и аудио — до `Media:Upload:MaxFileBytes` (по умолчанию 16 ГБ). Временный каталог службы (`TEMP`)
  должен вмещать принимаемые файлы целиком.
- ~~Пакетный импорт архива с носителя~~ — **сделано** (ТФ-МЕД-06, ADR-0041), порядок работы — §6.1.

## 6.1. Импорт архива (ADR-0041)

Накопленный архив переносится с диска сервера по описи — таблице CSV из Excel. Право «Импорт архива материалов»
(матрица доступа) по умолчанию у Администратора; файлы ложатся только в дела, доступные ему по допуску.

1. Эксплуатант подключает диск с архивом к серверу и прописывает его каталог в `Media:Import:Roots` (§4), затем
   перезапускает службу. Архив должен быть распакован: `.zip`/`.7z` не читаются.
2. Дела архива заводятся в системе заранее (номер, подразделение, гриф). Материалы ОТМ — только в дела подразделений
   ОТМ, иначе их увидят ОН и ОУ (ТС-014).
3. Меню «Медиа» → «Импорт архива» (`/media/import`): выбрать каталог и папку, «Скачать черновик описи по этой папке»
   (по желанию — номер дела из имени папки первого уровня), дописать в Excel номера дел, даты съёмки, источник, место
   и, если есть, контрольные суммы SHA-256; сохранить как CSV.
4. «Загрузить опись…» → «Проверить». Итог показывает, сколько файлов и в какие дела ляжет — с подразделением, отделом
   и грифом каждого дела, — и строки с ошибками (их можно скачать в формате описи, исправить и проверить снова).
5. Отметить «Гриф и подразделение каждого дела проверены» → «Запустить импорт». Страницу можно закрыть: задание идёт
   на сервере, после перезапуска продолжается с того же места. На странице задания — ход, «Остановить»/«Продолжить»,
   отчёт CSV для акта переноса и отказы в формате описи.

Документы `.docx`, `.doc`, `.pdf` из той же папки (ADR-0042) становятся документами документооборота группы «Хранение»,
прикреплёнными к делу из описи, с грифом и подразделением дела; их текст индексируется в фоне и ищется (текст `.doc`
система читает сама, без Word на сервере). Нужен хотя бы один действующий тип группы «Хранение» («Документооборот» →
«Типы документов»): тип указывается в описи столбцом «тип документа» или выбирается общим для задания. В описи для
документов есть столбцы «рег. номер», «дата документа» (нет — дата изменения файла), «название» (нет — имя файла).
Тот же файл, уже введённый импортом в это дело, второй раз не регистрируется. Документы больше 100 МБ, `.doc` с паролем и
формата Word 6/95 — отказ по строке.

Правила приёма — те же, что у загрузки из браузера: формат по содержимому, предел размера по виду, гриф и
подразделение от дела, дубликат по хешу не создаёт второго носителя. Дата съёмки фото и видео обязательна: не указана в
описи — берётся из метаданных файла, нет и там — файл не принимается. Каждый файл (принят, дубликат, отказ) — запись
журнала аудита. Перед каждым файлом заново проверяются допуск и право запустившего; снятое право или отозванный
допуск останавливают задание с причиной на его странице.
- Протокол сравнения .docx (ТФ-ВЕР-04), метрики верификации (ТФ-ВЕР-05), справки (ТФ-ОТЧ), документы дела через документооборот (ТФ-ДДЛ) — P1 по ТЗ.

## 6.1а. Взаимный поиск по лицу ОН и ОУ (ADR-0044)

Область поиска «все дела в пределах допуска» охватывает дела **всех** сотрудников в пределах грифа и подразделений
учётной записи — в том числе следователю, который в остальном видит только свои дела. Кандидат из чужого дела
открывается ему на просмотр целиком (фото или видео, кадр, место, дата), но только если найден его поиском в доступном
ему деле; карточка чужого дела, изменения и поиск по лицу такого кандидата закрыты. Это шире, чем у пересечений
(ADR-0029, там по чужому делу видны только номер, вид и ведущий) — так решил заказчик 14.10.2026.

Чем управляет администратор: **разрешёнными подразделениями и грифом** учётной записи. Выдал следователю ОН
подразделения ОУ — он ищет и по делам ОУ; не выдал подразделения ОТМ — дела ОТМ в поиск не попадают ни делом, ни
кандидатом (ТС-014). Отдельной настройки «взаимный поиск» нет. Каждый поиск (область и полный список дел) и каждое
открытие материала пишутся в журнал аудита.

## 6.1б. Граф связей (ADR-0045)

Кнопка «Граф связей» в карточке фигуранта и в карточке дела. Настраивать нечего: граф строится из тех же данных и под
теми же правами, что и карточки, — чужое дело видно только как в пересечениях (номер, вид, статус, ведущий). Библиотека
рисования Z.Blazor.Diagrams (MIT) со своими зависимостями (MIT) попадает в офлайн-фид сам при `export-packages.ps1`;
её скрипт и стили лежат в самой сборке (`_content/Z.Blazor.Diagrams/...`), интернет не нужен, `App.razor` не меняется.
Каждое построение графа и каждое раскрытие узла — запись в журнале аудита (`investigation:graph:...`).

С версии 0.2 (анализ связей) граф расставляется сам (силовая раскладка, кнопки «Расставить заново» и «Вписать»), машина и
адрес раскрываются до доступных фигурантов с тем же номером или адресом, есть связь «вместе на материалах», поиск
цепочки «Как связан с…» и выгрузка картинки (PNG, SVG). Настраивать по-прежнему нечего: картинка собирается из того,
что на экране, без внешних библиотек; на ней гриф (наибольший из грифов фигурантов и дел) и подпись «кто и когда
сформировал»; выгрузка — запись `Export` в журнале с тем же грифом. Миграций БД нет.

## 6.1в. Проигрыватель аудиозаписи (ADR-0047)

Карточка аудиозаписи показывает волну записи с участками речи, своё управление (скорость, ±5 с, клавиши) и работу с
расшифровкой (следование за записью, поиск, режим «Текстом», выгрузка в Word и копирование). Настраивать нечего:
волну строит тот же ffmpeg, что и кадры видео (`Vision:Ffmpeg:Folder`), одновременно — не больше
`Vision:Ffmpeg:MaxConcurrentFrameExtractions` процессов (свой предел, не общий с кадрами), прогон — не дольше 10 минут.
Эндпоинт `GET /media/waveforms/{id}` — под той же решёткой и тем же лимитером `media-frames`, что кадр видео; просмотр
волны — запись `View` `media:waveform:{id}` в журнале, выгрузка расшифровки — `Export`
`media:asset:{id}:transcript:export`. Выгрузка в Word идёт через экспорт документов ядра (`IDocumentExporter`). Нужна
миграция `AudioWaveform` (раздел 3).

## 6.2. Перенос баз Access (ADR-0043)

Учёт заданий из баз Access отделов («Задания», «Связи») переносится в дела «Задание по объекту» с анкетой объекта, фото,
связями, автомобилями и адресами. Право «Перенос баз Access» (матрица доступа) по умолчанию у Администратора.

**Что поставить на сервер приложений (один раз).** Базу читает драйвер **Microsoft Access Database Engine 2016
Redistributable, x64** (`AccessDatabaseEngine_X64.exe`, бесплатный компонент Microsoft). Разрядность — только x64, как у
службы. Перенос в контур — как остальные поставки: скачать на машине с интернетом с сайта Microsoft, сверить подпись
файла (свойства → «Цифровые подписи»: Microsoft Corporation) и SHA-256, перенести и установить:

```powershell
AccessDatabaseEngine_X64.exe /quiet
```

Если на сервере стоит 32-битный Office, установщик x64 откажет: Microsoft не поддерживает две разрядности рядом. Office на
сервере приложений не нужен вовсе — уберите его. На сервере с Office x64 драйвер уже есть. Проверка, что драйвер виден:

```powershell
(New-Object System.Data.OleDb.OleDbEnumerator).GetElements() | Where-Object SOURCES_NAME -like 'Microsoft.ACE*' | Select-Object SOURCES_NAME
```

Нужна строка `Microsoft.ACE.OLEDB.16.0` (или `12.0`). Без драйвера экран «Перенос из Access» говорит, что поставить, и не
открывает загрузку; остальная система работает. Пакет `System.Data.OleDb` (MIT) попадает в офлайн-фид сам при
`export-packages.ps1`. Проверка на месте: `dotnet test tests/ISC.AI.IntegrationTests --filter "Category=Access"` (тест сам
создаёт базу через драйвер); прогон без драйвера — `--filter "Category!=Access"`.

**Порядок работы.**

1. Сделать копию базы отдела. Если база защищена паролем — открыть копию в Access и снять пароль («Файл» → «Сведения» →
   «Расшифровать базу данных»).
2. «Администрирование» → «Перенос из Access» (`/admin/access-import`) → «Загрузить базу…». Файл сохраняется в хранилище с
   контрольной суммой SHA-256 (запись в журнале) — как исходник переноса.
3. Проверить сопоставление: таблица заданий и таблица связей, столбец для каждого поля (система предлагает его по названию;
   пустое — не переносится). Связи привязываются к заданию по № задания.
4. Выбрать подразделение (под ним виден отдел ОН/ОУ/ОТМ — учёт ОТМ только в подразделение ОТМ, ТС-014), гриф и статус всех
   заданий базы; при необходимости — «Завести недостающие записи справочников» (нужно ещё право «Подразделения и
   справочники»). «Проверить»: сколько заданий, связей и фото перенесётся, какие записи справочников заведутся, ошибки по
   записям (скачиваются списком CSV) и первые задания для сверки.
5. Подтвердить гриф и подразделение → «Перенести». Страницу не закрывать до итога. Прерванный перенос (закрыли страницу,
   перезапуск) повторяется той же базой — перенесённое пропускается, дублей нет.

Фото объектов ложатся в материалы дел и обрабатываются (поиск лиц); эталоном снимок делает сотрудник в карточке объекта.
Временная копия базы на время чтения лежит в `%TEMP%\iscai-access` и удаляется сразу после чтения; оставшееся после
аварии удаляется при старте службы.

## 7. Расшифровка речи (ADR-0026)

Аудиозаписи (голосовые сообщения, записи разговоров, диктофон) и звуковые дорожки видео расшифровываются
в текст: русский, киргизский и смешанная речь. Конвейер: ffmpeg → детектор речи Silero VAD → модель
GigaAM Multilingual (CTC) в **отдельном процессе** `ISC.AI.Speech.Worker` → фрагменты с таймкодами.
Дословный текст модели (строчные буквы без знаков препинания) — первичный слой. В интерфейсе у него
постоянная пометка «автоматическая расшифровка, требует проверки, не является протоколом» (ТЭ-002).
Решение и выбор модели описаны в [ADR-0026](../06_ADR/ADR-0026-raspoznavanie-rechi.md).

## 7.2. Офлайн-поставка

Запускать на машине **с** интернетом, как и для остальных артефактов (§2.1):

```powershell
deploy\offline\export-speech-models.ps1    # модель речи, словарь, детектор речи, тексты лицензий, пины SHA-256
deploy\offline\export-sherpa-no-tts.ps1    # нативная sherpa-onnx БЕЗ синтеза речи (win-x64 и linux-x64), пины SHA-256
deploy\offline\publish-speech-worker.ps1   # публикация процесса-распознавателя (по умолчанию win-x64; -Runtime linux-x64)
```

Порядок важен: `export-sherpa-no-tts.ps1` выполняется **до** публикации. Без его результата
`publish-speech-worker.ps1` откажет с подсказкой «выполните export-sherpa-no-tts.ps1».

**Почему нужна отдельная нативная библиотека.** Нативная библиотека sherpa-onnx из пакета NuGet собрана вместе
с синтезом речи и **статически содержит движок eSpeak NG под лицензией GPL-3.0**: 25 функций `espeak_ng_*` в
`sherpa-onnx-c-api.dll`. Нам нужно только распознавание, но поставлять GPL-код нельзя. Это то же правило,
по которому запрещены GPL-сборки ffmpeg (ADR-0026, п. 7). Проект k2-fsa выпускает официальные сборки того же
релиза **без синтеза речи**: в них нет eSpeak NG, а распознавание и детектор речи те же. Скрипт скачивает их с
закреплёнными SHA-256 в `deploy/offline/sherpa-no-tts/<платформа>` и пишет манифест `sherpa-no-tts.sha256`.
Публикация подставляет эти библиотеки вместо библиотек пакета и ещё раз проверяет на признаки eSpeak NG
**все** нативные файлы папки, а не только две подменённые библиотеки. Признаками считаются функции
`espeak_ng_*` и строки движка. Совпадение по слову «espeak» без учёта регистра признаком не считается: такая
подстрока есть и в сборке без синтеза, внутри имени `OfflineSpeakerDiarization`. Нативный файл сверх пары
`sherpa-onnx-c-api` + `onnxruntime` — отказ «лишняя нативная библиотека». Опубликованная папка получает
манифест `worker.sha256`, `THIRD-PARTY-NOTICES.txt` и тексты лицензий `LICENSE-sherpa-onnx.txt` (Apache-2.0) и
`LICENSE-onnxruntime.txt` (MIT); при `-SelfContained` — ещё `LICENSE-dotnet.txt` и
`THIRD-PARTY-NOTICES-dotnet.txt`. Тексты лежат в git в `deploy/offline/licenses`; без них публикация отказывает,
а `-Verify` не принимает папку. Проверено 25.09.2026: распознаватель на сборке без синтеза речи выдаёт на тех
же записях тот же текст, что и на библиотеке NuGet.

- `export-sherpa-no-tts.ps1 -VerifyOnly` проверяет уже распакованную папку по пинам без сети. Так проверяют
  папку после переноса или если архивы распакованы вручную. Архивы, скачанные на другой машине, можно передать
  ключом `-ArchiveDir`: пины проверяются так же.
- Публикуется распознаватель **только вне контура**, в контур переносится готовая папка с `worker.sha256`.
  Пакетов sherpa-onnx в общем офлайн-фиде нет и быть не должно: их нативные библиотеки из NuGet содержат eSpeak NG
  (GPL-3.0). Фид собирается по фильтру `ISC.AI.Offline.slnf` без утилиты и её тестов, а `export-packages.ps1` и
  `verify-packages.ps1` отказывают, если в фиде есть пакет `org.k2fsa.sherpa.onnx*` или нативный файл с признаками
  eSpeak NG (ADR-0026, п. 7). Ключа `-Offline` у скрипта публикации больше нет.
- Ключ `-AllowGplEspeakNg` — **крайний случай** и допустим только по решению заказчика после юридической оценки.
  Если сборки без синтеза речи нет, публикуются библиотеки NuGet с eSpeak NG, а в `THIRD-PARTY-NOTICES.txt`
  появляется запись о GPL. Для поставки в контур этот ключ не использовать.
- Быстрая проверка опубликованного распознавателя на WAV 16 кГц моно:
  `ISC.AI.Speech.Worker.exe --model <модель> --tokens <tokens.txt> --vad <silero_vad.onnx> --input <файл.wav>`.
  Ожидается код выхода 0 и последняя строка stdout `{"type":"done",...}`. Для тишины это
  `"segments":0`, для речи — фрагменты с текстом строчными буквами.

Параметры скриптов (вариант модели, платформа, папки) описаны в их шапках. Скрипт моделей создаёт манифест
целостности `speech-models.sha256` и в конце печатает значения `Speech:*:Sha256` для конфигурации. Файлы
моделей, библиотеки `sherpa-no-tts` и опубликованный распознаватель в git не хранятся. Если ffmpeg уже поставлен
для видео, отдельно его ставить не нужно.

## 7.3. Размещение на сервере

- Папку публикации распознавателя (`deploy/offline/speech-worker/<платформа>`) переносить **целиком**: рядом с
  `ISC.AI.Speech.Worker.exe` лежат нативные `sherpa-onnx-c-api.dll` и `onnxruntime.dll` и тексты их лицензий.
  Класть её нужно
  **отдельно от папки хоста**: там свой `onnxruntime.dll` распознавания лиц, другая сборка с тем же именем
  (ADR-0026, п. 1).
- После переноса на сервере выполнить `publish-speech-worker.ps1 -Verify -WorkerDir <папка>` (рядом со скриптом
  должен лежать `offline-common.ps1` — папка `deploy/offline` переносится целиком). Скрипт сверяет папку с
  `worker.sha256`, проверяет наличие текстов лицензий и пишет результат в журнал переноса. Папку, опубликованную до
  появления текстов лицензий, он не примет — её нужно опубликовать заново. Без SDK это работает, на Linux есть замена:
  `sha256sum -c worker.sha256`. Неполная папка опасна: если рядом с утилитой нет `onnxruntime.dll`, Windows
  подхватывает системную `C:\Windows\System32\onnxruntime.dll` (Windows ML, старая версия). Процесс тогда
  падает аварийно, без понятного сообщения.
- **Microsoft Visual C++ Redistributable на Windows-сервере НЕ нужен.** Для win-x64 ставится вариант MT
  сборки sherpa-onnx без синтеза речи: среда C++ вшита в библиотеки статически, импортов `VCRUNTIME140` и
  `MSVCP140` у `sherpa-onnx-c-api.dll` и `onnxruntime.dll` нет (проверено по таблице импорта). Если когда-нибудь
  подставят MD-сборку, `publish-speech-worker.ps1` увидит импорты сам и напечатает требование, а `-Verify`
  проверит наличие среды на сервере.
- Модели — на защищённом томе (ТБ-062), пути в конфигурации — **абсолютные**. Относительный путь
  считается от рабочего каталога процесса хоста, а он у службы, `dotnet run` и Visual Studio разный.
- **Временные копии материала дела.** Внешние процессы (ffmpeg, распознаватель) работают с файлом, поэтому хост
  пишет на диск временные копии:
  - копию исходника для расшифровки — `%TEMP%\iscai-media\speech-<guid><расширение>`;
  - WAV-звук для распознавателя — в каталог прогона `%TEMP%\iscai-speech\<guid>\`;
  - копию видео для раскадровки индексатором лиц — `%TEMP%\iscai-media\frames-<guid><расширение>`;
  - копию оригинала для пробы, вырезки кадра при покадровом просмотре и снимка кадра (ADR-0028) — **только если
    у хранилища нет локального пути**: локальное хранилище (`Storage:BasePath`) отдаёт ffmpeg путь к оригиналу
    на месте через `ILocalFileLocator`, и копия не создаётся; иначе — файл в `%TEMP%\iscai-media` по тем же
    правилам именования и уборки;
  - буфер приёма загружаемого файла (хеш считается до записи в хранилище) — `%TEMP%\iscai-media-<guid>`, тоже
    полная копия материала.

  Расширение в именах копий нормализуется (латинские буквы и цифры, 2–5 символов, иначе `.bin`): путь уходит
  ffmpeg текстом командной строки. При штатной работе копии удаляются в конце операции при любом исходе (успех,
  ошибка, отмена, таймаут). Гарантия «при любом исходе» действует, пока хост жив: при аварийном останове (снят
  процесс, пропало питание) удаление не выполняется. Такие остатки удаляются при **следующем старте хоста**, до
  приёма запросов и запуска фоновой очереди: всё, что записано раньше старта процесса, — в `%TEMP%\iscai-media`,
  `%TEMP%\iscai-speech` и в корне `%TEMP%` (буфер приёма `iscai-media-*` и файлы прежних версий `isc-speech-*`,
  `isc-media-*`). Каталог живого прогона (файл-замок `run.lock`) не трогается, даже если его держит другой
  экземпляр хоста под той же учётной записью. Каждый файл удаляется отдельно: один занятый не останавливает
  уборку остальных, а неудавшееся удаление пишется в журнал с путём. Если дело уничтожено (ADR-0025, ТБ-064) после аварийного останова, а хост ещё не
  перезапускался, эти каталоги нужно проверить и очистить вручную по путям из журнала.
- Это копии материала дела, поэтому `TEMP` учётной записи службы должен указывать на защищённый том (ТБ-062).
- Одновременно работает **один** процесс-распознаватель, остальные расшифровки ждут в фоновой очереди.
  Модель занимает сотни мегабайт памяти и `Speech:Threads` потоков процессора. Это надо учитывать при
  планировании сервера вместе с языковой моделью.

## 7.4. Конфигурация (секция `Speech`)

| Ключ | Назначение |
|---|---|
| `Speech:Worker:Path` | путь к `ISC.AI.Speech.Worker.exe` (или к `.dll` — тогда запуск через `dotnet`) |
| `Speech:Model:Path` / `Speech:Model:Sha256` | файл модели GigaAM Multilingual (ONNX, int8) и его пин |
| `Speech:Tokens:Path` / `Speech:Tokens:Sha256` | словарь модели `tokens.txt` и его пин |
| `Speech:Vad:Path` / `Speech:Vad:Sha256` | детектор речи `silero_vad.onnx` и его пин |
| `Speech:Threads` | потоки модели; по умолчанию 4, допустимо 1–64. Больше потоков — быстрее расшифровка, но меньше процессора остаётся хосту и языковой модели. Значение уточняется на пилоте |
| `Speech:MaxSegmentSeconds` | наибольший кусок звука, который получает модель, в секундах; по умолчанию 20, допустимо 2–25 (модель принимает до ~25 с). Соседние участки речи склеиваются в кусок до этого предела вместе с паузами — так модели хватает контекста языка; фрагменты и таймкоды остаются по паузам (ADR-0026, п. 13). Длинная речь без пауз режется по самому тихому месту |
| `Speech:MaxDurationHours` | наибольшая длительность записи, часы; по умолчанию 24, допустимо 1–36. Запись длиннее отклоняется до запуска ffmpeg («разбейте на части»). 36 ч — жёсткий потолок: номер отсчёта в нативном детекторе речи — int32 (≈37,3 ч при 16 кГц), тот же предел у WAV (4 ГБ) |
| `Speech:TimeoutFactor` | множитель таймаута прогона: прогон длится не дольше `15 мин + множитель × длительность записи`; по умолчанию 3, допустимо 0,5–20. Увеличивать на медленном или занятом сервере |
| `Speech:Ffmpeg:Folder` | каталог ffmpeg/ffprobe. **Пусто — берётся `Vision:Ffmpeg:Folder`** (одна поставка ffmpeg на оба конвейера); пусто и там — ffmpeg ищется в `PATH` |
| `Speech:Model:Name` | необязательно: имя модели в её версии (по умолчанию `gigaam-multilingual-ctc`) |

Числовые ключи вне допустимого диапазона зажимаются в его границы. Путь к распознавателю и три пары «путь +
пин» обязательны. Пины проверяются **при каждом запуске**
расшифровки, а не только при старте хоста, поэтому подмена файла между запусками не пройдёт незамеченной.
Каждая расшифровка помечается версией модели вида `gigaam-multilingual-ctc@<первые 12 символов SHA-256>`:
по ней видно, каким файлом (220M или 600M) сделан текст. Результаты разных моделей не сравнимы.

Пример (пути — свои; пины — из вывода `export-speech-models.ps1`, ниже — для закреплённой ревизии конвертации;
при собственном экспорте из официальных весов пин модели — хеш своего файла):

```json
"Speech": {
  "Worker":  { "Path": "D:\\ISC.AI\\speech-worker\\ISC.AI.Speech.Worker.exe" },
  "Model":   { "Path": "D:\\ISC.AI\\models\\speech\\gigaam-multilingual-ctc-600m.int8.onnx",
               "Sha256": "6B6F195026B0F90721CD4593C664BECF009A71131550B664EEC71446EC351C81" },
  "Tokens":  { "Path": "D:\\ISC.AI\\models\\speech\\tokens.txt",
               "Sha256": "9B5DF7987CB4CA52C1A468649CE897FAB1CD182067416E29FEF49DFAA7A856C2" },
  "Vad":     { "Path": "D:\\ISC.AI\\models\\speech\\silero_vad.onnx",
               "Sha256": "9E2449E1087496D8D4CABA907F23E0BD3F78D91FA552479BB9C23AC09CBB1FD6" },
  "Threads": 4,
  "MaxSegmentSeconds": 20,
  "MaxDurationHours": 24,
  "TimeoutFactor": 3,
  "Ffmpeg":  { "Folder": "" }
}
```

Те же ключи можно задать переменными окружения (`Speech__Model__Path` и т. д.).

**Модель 600M — основная** (ADR-0026, п. 13): 592 МБ на диске; на замере 30 с записи распознаются за ~3,6 с на
4 потоках (RTF ~0,12, час записи — ориентировочно ~7 мин). **220M остаётся запасным вариантом** для слабых
машин: вдвое быстрее и 225 МБ, но на киргизском заметно хуже. Для неё — поставка
`export-speech-models.ps1 -Variant 220m`, а в конфигурации сменить путь на `gigaam-multilingual-ctc-220m.int8.onnx` и
пин `Speech:Model:Sha256` на `2D94F93FFD4EF58E7899C9DE885C25BBBC8C9F1073618868D118A674450BA5F7`; словарь и детектор
речи те же. Смена варианта — это смена модели (7.6).

## 7.5. Поведение без настройки и при ошибках

- **Если не задан хотя бы один обязательный ключ**, хост стартует как обычно, а расшифровка **явно
  отказывает**: в карточке носителя — ошибка «Расшифровка не настроена: не заданы ключи конфигурации …» с
  перечнем недостающих ключей. Пустая расшифровка выглядела бы как «в записи нет речи», поэтому система
  отказывает, а не пропускает молча.
- **Загрузка аудио при этом работает.** Записи принимаются в дело с реквизитами и грифом, хранятся и
  воспроизводятся. Индексация лиц к аудио неприменима (статус «неприменимо», а не «ноль лиц»). После
  настройки расшифровку запускает кнопка «Расшифровать заново» (7.6).
- **Файл модели не найден** — ошибка с полным путём, по которому искали. **Пин не совпал** — ошибка,
  расшифровка не запускается (ТИ-004).
- **Без ffmpeg** расшифровка не выполняется ни для аудио, ни для видео: звук к формату модели приводит
  ffmpeg.
- **Видео без звуковой дорожки** (камеры наблюдения) — расшифровка завершается успешно с нулём
  фрагментов: говорить в записи некому.
- Предел загрузки аудио — как у видео, `Media:Upload:MaxFileBytes` (по умолчанию 16 ГБ, ADR-0040): помещается и
  многочасовой WAV.
- **Запись длиннее `Speech:MaxDurationHours`** (по умолчанию 24 ч) — ошибка «разбейте на части» до запуска ffmpeg
  и распознавателя. Длительность берётся из ffprobe; если он её не сообщил или занизил, запись всё равно не
  обрезается молча: длина извлечённого WAV сверяется с тем же пределом.
- **Прогон дольше таймаута** (`15 мин + Speech:TimeoutFactor × длительность`) — процессы останавливаются,
  временные файлы удаляются, в карточке ошибка с упоминанием `Speech:TimeoutFactor`.
- **«Видео» без видеопотока** — голосовое `.3gp` (браузер объявляет его видео), звук в mp4/webm. Индексатор
  проверяет потоки через ffprobe (обложка звуковой записи видеопотоком не считается) и переводит носитель в
  «Аудио» с индексацией лиц «неприменимо», без записи в журнал об обработке биометрии; запись расшифровывается
  как аудио.
- **Перезапуск хоста посреди работы.** При старте расшифровки в состоянии «в очереди» или «выполняется»
  переводятся в «ошибку» с текстом «прервано перезапуском системы — нажмите «Расшифровать заново»», а
  индексация лиц «выполняется» — в «ошибку» с подсказкой «Переиндексировать». Носители в состоянии «загружен» не
  трогаются.

## 7.6. Уже загруженные материалы и смена модели

- Видео, загруженные **до** этой версии, не расшифрованы. Их отправляют на расшифровку кнопкой
  **«Расшифровать»** в карточке носителя (роли Следователь и Администратор; запуск пишется в журнал).
- После сбоя (в том числе «не настроена») и после **смены модели** (вариант 600M ↔ 220M или новая ревизия)
  та же кнопка называется **«Расшифровать заново»**. Прежняя расшифровка остаётся видна, пока новая не
  записана целиком.
- Пока расшифровка идёт, кнопка неактивна, а повторный запуск отклоняется («Расшифровка уже выполняется —
  нажмите «Обновить»»).
- Расшифровка — событие журнала (модель, число фрагментов). Поиск по словам в расшифровках аудируется
  вместе с искомым текстом. Уничтожение носителя или дела удаляет и расшифровку (ADR-0025).

## 7.7. Проверка на месте и качество

Интеграционные тесты речи запускаются на машине сборки с поставкой: ffmpeg в `deploy/offline/ffmpeg`, модели
в `deploy/offline/models/speech`. Тестовый проект на распознаватель не ссылается (его пакетов нет в офлайн-фиде,
ADR-0026 п. 7), поэтому утилиту сначала собирают отдельно:

```powershell
dotnet build src/integrations/ISC.AI.Speech.Worker
dotnet test tests/ISC.AI.IntegrationTests --filter "Category=Speech"
```

- **Какая сборка проверяется.** По умолчанию — утилита из её `bin` с нативными библиотеками NuGet (с синтезом
  речи; это использование, а не поставка). Чтобы проверить именно опубликованную no-tts сборку, задайте
  переменную окружения `ISCAI_SPEECH_WORKER=<путь к ISC.AI.Speech.Worker.exe>` (или к `.dll` — тогда запуск через
  `dotnet`). Утилиты нет ни там, ни там — тесты **падают** с подсказкой, как её собрать, а не пропускаются.
- **Что проверяется.** Процесс-распознаватель и его протокол, пины моделей, извлечение звука (mp4 с AAC, m4a,
  немое mp4, предел длительности) и уборка временных файлов. Путь декодирования моделью, который детектор речи
  на синтетическом звуке не открывает, покрыт тестом с диагностическим ключом утилиты `--decode-whole` (вся
  запись без детектора подаётся модели; адаптер хоста этот ключ не передаёт).
- Звук тесты генерируют сами через ffmpeg (тишина, тон), записей людей в репозитории нет, и **качество
  распознавания эти тесты не проверяют**. Прогон без поставки — `--filter "Category!=Speech"`.
- Чистая логика утилиты (разбор аргументов, чтение WAV, нарезка, протокол) проверяется без моделей отдельным
  проектом `dotnet test tests/ISC.AI.Speech.Worker.Tests`. Он, как и утилита, не входит в `ISC.AI.Offline.slnf`
  и в контуре не собирается.

Качество проверяется только пилотом на записях Заказчика, по методике
[Пилот_расшифровки_речи.md](Пилот_расшифровки_речи.md). До пилота выбор модели считается
предварительным, а пороги КИ-10 не согласованы.
