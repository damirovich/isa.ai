# Сборка и развёртывание профиля «Следствие» («СледствиеAI»)

| | |
|---|---|
| **Документ** | Инструкция к ДОК-13 (архитектура профиля «Следствие»), раздел «Сборка и развёртывание» |
| **Система** | ISC.AI — профиль «Следствие» |
| **Версия** | 0.1 (ЭС3-01, 17.09.2026) |
| **Связь** | ADR-0021 (выбор профиля при сборке), ADR-0019/0020 (векторный поиск, стек распознавания), ADR-0006 (экземпляр на профиль); ТС-004, ТИ-004, ТБ-062 |

## 1. Принцип

Профиль в поставке ровно один (ТС-004). Репозиторий содержит два профиля — «ИнспекторAI» и
«Следствие», — и выбор делается **при сборке** свойством MSBuild `IscProfile`. По умолчанию (свойство
не задано) собирается «ИнспекторAI»: ни одна существующая поставка не меняется.

## 2. Сборка

```bash
dotnet clean src/core/ISC.AI.Web
dotnet build src/core/ISC.AI.Web/ISC.AI.Web.csproj -p:IscProfile=investigation
dotnet publish src/core/ISC.AI.Web/ISC.AI.Web.csproj -c Release -p:IscProfile=investigation -o publish/investigation
```

`dotnet clean` обязателен при **смене** профиля: каталог `obj/` хоста общий, и в нём остаются
артефакты прежнего варианта (список ссылок, сгенерированный диспетчер Mediator). Возврат к
«ИнспекторAI» — снова `dotnet clean`, затем обычная сборка без свойства.

В Visual Studio то же свойство задаётся переменной окружения `IscProfile=investigation` перед
запуском среды (MSBuild читает переменные окружения как свойства); после смены — «Очистить решение».

Проверка, что собрался нужный профиль: строка запуска в логе
`Хост ISC.AI запущен с профилем investigation (СледствиеAI)`.

## 3. База данных

У поставки «Следствие» **своя** БД PostgreSQL с расширением `pgvector` (ADR-0006): на одной БД с
«ИнспекторAI» профиль не разворачивается — словари подразделений (`inspector.division` и
`investigation.division`) разные, а `core.clearance.division_scope` один на всех.

Схемы и порядок наката миграций (у каждой своя история `<схема>.__ef_migrations_history`):

| № | Схема | Контекст | Проект | Переменная окружения со строкой подключения |
|---|---|---|---|---|
| 1 | `core` | `CoreDbContext` | `src/core/ISC.AI.Persistence` | `ISCAI_CORE_CONNECTION` |
| 2 | `docflow` | `DocFlowDbContext` | `src/modules/docflow/ISC.AI.Modules.DocFlow.Data` | `ISCAI_DOCFLOW_CONNECTION` |
| 3 | `media` | `MediaDbContext` | `src/modules/media/ISC.AI.Modules.Media.Data` | `ISCAI_MEDIA_CONNECTION` |
| 4 | `investigation` | `InvestigationDbContext` | `src/profiles/investigation/ISC.AI.Profile.Investigation.Data` | `ISCAI_INVESTIGATION_CONNECTION` |

Пример для схемы `media` (строка с паролем — только в переменной окружения, не в файлах):

```bash
ISCAI_MEDIA_CONNECTION="Server=...;Database=ISC_AI_INV;Username=...;Password=...;SSL Mode=Require" \
dotnet ef database update --project src/modules/media/ISC.AI.Modules.Media.Data --startup-project src/modules/media/ISC.AI.Modules.Media.Data --context MediaDbContext
```

То же из **консоли диспетчера пакетов** Visual Studio (Package Manager Console) — строка подключения
задаётся переменной окружения текущей сессии консоли, затем накат по одному контексту:

```powershell
$env:ISCAI_CORE_CONNECTION="Host=localhost;Port=55432;Database=ISC_AI_INV;Username=postgres"
$env:ISCAI_DOCFLOW_CONNECTION=$env:ISCAI_CORE_CONNECTION
$env:ISCAI_MEDIA_CONNECTION=$env:ISCAI_CORE_CONNECTION
$env:ISCAI_INVESTIGATION_CONNECTION=$env:ISCAI_CORE_CONNECTION

Update-Database -Context CoreDbContext          -Project ISC.AI.Persistence                 -StartupProject ISC.AI.Persistence
Update-Database -Context DocFlowDbContext       -Project ISC.AI.Modules.DocFlow.Data        -StartupProject ISC.AI.Modules.DocFlow.Data
Update-Database -Context MediaDbContext         -Project ISC.AI.Modules.Media.Data          -StartupProject ISC.AI.Modules.Media.Data
Update-Database -Context InvestigationDbContext -Project ISC.AI.Profile.Investigation.Data  -StartupProject ISC.AI.Profile.Investigation.Data
```

`-Project` и `-StartupProject` указывают на ОДИН и тот же проект слоя данных: у каждого есть своя
design-фабрика, которая берёт строку подключения из переменной окружения выше и не требует запуска хоста.
Без переменной фабрика подставляет заглушку без пароля и накат не пройдёт.

Ошибка вида `42P01: relation "investigation.user_role_assignment" does not exist` означает ровно одно:
хост запущен на базе, где схема профиля ещё не создана. Либо накатите четыре миграции выше на эту базу,
либо укажите в `appsettings.Development.json` строки подключения к базе, где они уже применены.

Миграция `InitialMedia` создаёт HNSW-индекс (`m=16, ef_construction=512`) на `media.face_template`:
сервер должен иметь исправный `pgvector` (`SELECT extversion FROM pg_extension WHERE extname='vector'`)
и достаточный `maintenance_work_mem`. Отдельная БД нужна не из-за pgvector (он исправен), а по ADR-0006:
справочники подразделений у профилей разные, а `core.clearance.division_scope` — один на базу, поэтому
номера подразделений двух профилей в одной БД перемешались бы в допусках.

## 4. Конфигурация хоста (`appsettings.json`, секреты — user-secrets / переменные окружения)

| Ключ | Назначение |
|---|---|
| `ConnectionStrings:Core/DocFlow/Media/Investigation` | одна БД профиля, четыре схемы; пароль — общий секрет `Database:Password` (`Database__Password` в окружении) |
| `Storage:BasePath` | корень файлового хранилища ядра (носители `media-originals`, вырезки `media-faces`, вырезки проб `media-probes`); в проде — защищённый том (ТБ-062) |
| `Vision:Detector:Path/Sha256`, `Vision:Embedder:Path/Sha256` | модели YuNet и SFace из `deploy/offline/models` с пинами SHA-256; при несовпадении модель не загружается (ТИ-004) |
| `Vision:Ffmpeg:Folder` | папка с бинарником ffmpeg LGPL-сборки (без него видео не индексируется; фото — работает) |
| `Vision:Detection:*`, `Vision:Quality:*` | пороги детекции и пригодности лиц (стартовые, калибруются на пилоте — ТО-мат-08) |
| `Media:Search:CandidateListSize/Min/Max` | длина кандидат-листа по умолчанию 20, допустимо 5..50 (ТН-008) |
| `Media:Search:MaxCosineDistance` / `MaxAllowedCosineDistance` | порог отсечения и потолок, выше которого пользователь ослабить порог не может (ТФ-ПЛ-06) |
| `Media:Search:HnswEfSearch` | ширина обхода HNSW (200 — проверенная пара к `ef_construction=512`, ADR-0019) |
| `Media:Search:ProbeCopyMaxBytes` | до какого размера копия пробного изображения кладётся в аудит (ТБ-072) |
| `Media:Video:SampleFps` | частота выборки кадров при раскадровке (ТО-мат-06) |
| `Auth:Mode` | только `Local`: в режиме `Dev` у субъекта нет идентификатора, все гварды по ролям отказывают, администрирование недоступно |

## 5. Первый вход и первичная настройка

1. Учётка по умолчанию создаётся на пустом реестре (`Auth:DefaultAccount`) с временным паролем; первый вход уводит на `/account/password`.
2. Пока нет ни одного Администратора, роли, допуски и справочник подразделений открыты любому вошедшему (режим первичной настройки, `AdministrationRule`); назначьте себе роль **Администратор** на `/admin/roles` — режим закрывается.
3. Заведите подразделения (`/admin/divisions`) — их идентификаторы попадают в допуски.
4. Выдайте допуски (`/admin/clearances`): гриф и подразделения; без допуска ни одно дело не видно (fail-closed, ТБ-020/021).
5. Назначьте роли следователей, экспертов по лицам и верификаторов (ТП-004): одно лицо не может быть экспертом и верификатором одного результата (ТБ-073).
6. Поиск по лицу возможен только в деле, у которого есть **основание** (поручение, постановление, ОРМ) — добавляется в карточке дела (ТБ-071).

## 6. Что не входит в первый срез (ЭС3-01)

- Учётные записи и журнал аудита из интерфейса — после выноса администрирования платформы в общий пакет модулей (отдельная задача; до этого учётки заводятся командой `create-account` хоста, журнал — запросом к `core.audit_record`).
- ffmpeg в офлайн-поставке и живой прогон раскадровки (отдельная задача).
- Изображения TIFF/HEIC и воспроизведение MKV/AVI/MOV в браузере (ADR-0020): TIFF/HEIC не принимаются, видео в этих контейнерах индексируется, но смотрится через скачивание оригинала.
- Потоковый приём больших видео: файл принимается целиком в память (предел 200 МБ на файл).
- Регламент удаления шаблонов по закрытию дела с актом (ТФ-ДЕЛ-04, ТБ-074), протокол сравнения .docx (ТФ-ВЕР-04), метрики верификации (ТФ-ВЕР-05), справки (ТФ-ОТЧ) — P1 по ТЗ.
