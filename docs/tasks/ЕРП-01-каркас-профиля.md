| | |
|---|---|

## Цель
Завести каркас второго профиля на **неизменённом** ядре — и тем самым проверить на практике центральное обещание платформы: «тот же код подходит другому ведомству без переписывания ядра».

## Что сделано
Пять проектов в `src/profiles/erp/` по образцу профиля «Инспектор»:

| Проект | Содержимое |
|---|---|
| `ISC.AI.Profile.ERP` | Манифест `ErpProfile : IProfile` (id `erp`, один модуль-заглушка) |
| `.Domain` | Сущности — пусто (преступление/эпизод/лицо/дело — по деталям проекта) |
| `.Application` | Точка регистрации сценариев — пусто |
| `.Data` | `ErpDbContext`, **схема `erp`**, своя история миграций, дизайн-фабрика (миграций нет — нечего мигрировать) |
| `.UI` | RCL со страницей-заглушкой `/erp` |

## ✅ Проверка §3.2.5 — переиспользуемость подтверждена запуском
Профиль ЕРП подключён к хосту вместо «Инспектора», приложение **успешно поднялось**. Замеры:

| Показатель | Факт |
|---|---|
| Изменений в ядре | **0 строк** |
| Цена переключения профиля | **3 строки в хосте**: ссылка на проект профиля + `using` + строка в точке композиции |
| Что второй профиль получил из ядра готовым | корпус и загрузка, семантический поиск, RAG-конвейер с грунтовкой, неизменяемый аудит, фильтр доступа (гриф/подразделение), очередь фоновых задач, экспорт |
| Правки вне профиля | **1 строка в арх-тесте**: правило «на `Persistence` ссылается только слой данных профиля» было захардкожено на имя `Inspector.Data` → обобщено на любой `<Профиль>.Data` |

Сборка 0/0, юнит-тесты 97/97. После проверки хост возвращён на профиль «Инспектор».

## Что НЕ сделано осознанно
- **В хост не подключён**: действует инвариант «ровно один профиль в хосте» (ТС-004, §5.1.1.9, арх-тест). Смена профиля = сборка другой поставки, а не тумблер в рантайме — следствие требования физической изоляции контуров (§5.1.1.5, не мультиарендность).
- **Ядро не трогали** — по условию задачи и по инварианту.
- Сущностей и миграций нет — состав домена определится по деталям проекта.

## Открытые вопросы (нужны детали проекта)
- **API АИС ЕРП** — доступа к системе нет; ожидается, что дадут API. До контракта интеграцию не проектируем; подключаться — коннектором-адаптером (антикоррупционный слой), чтобы чужая модель не протекала в ядро/профиль.
- **Рукописные документы** — главный технический риск: Tesseract рукопись не берёт, нужна локальная vision-модель. **Требуется пилот на 20–30 реальных документах** до любых обещаний по качеству. Режим — только «машина даёт черновик, человек правит» (HITL).
- **Связывание преступлений** — юридически чувствительно: жёсткие признаки считает код, семантика подсказывает похожее, но результат — только **подсветка для проверки человеком**, не автоматический вывод (тот же принцип, что риск в «Инспекторе»).
- Объёмы, качество сканов, класс защищённости — неизвестны.

## Следующие шаги
1. Пилот распознавания рукописи (главная неизвестность — от неё зависят сроки и обещания).
2. Получить контракт API АИС ЕРП → спроектировать коннектор-адаптер.
3. По деталям — домен ЕРП (сущности + миграция) по той же схеме, что домен «Нарушение» ([Э5-01](Э5-01-домен-нарушение.md)).
