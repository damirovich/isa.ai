## Находка (по коду)
В ядро **жёстко вшита** конкретная модель режимной безопасности «гриф × подразделение» (мандатный доступ,
стиль Bell-LaPadula):
- `IClassified { short Classification; int DivisionId }` — обязателен на каждом ресурсе корпуса
  (`DocumentEntity`/`ChunkEntity`/`EmbeddingEntity`), колонки `NOT NULL`, денормализованы на строку вектора.
- `AccessContext { MaxClassification; AllowedDivisions[] }` — монотонная решётка допуска.
- `BaselineAccess.Filter` строит `Classification ≤ MaxClassification AND AllowedDivisions.Contains(DivisionId)`
  и применяется ретривером **ВСЕГДА** как pre-filter; профиль (`IAccessPolicy`) может только **сузить**.

**Вывод оценки:** для целевого класса (гос./режимные системы внутреннего контроля) это ПРАВИЛЬНЫЙ дизайн.
Но это доменное допущение: коммерческое/RBAC/ABAC/мультиарендное приложение так доступ не моделирует. Ядро
универсально **в рамках класса**, но не безусловно. Чтобы поднять систему ВНЕ класса, пришлось бы менять
само ядро, а не профиль.

## Развилка (нужно решение до реализации)

### Вариант A — оставить как есть (не универсализировать)
«Гриф × подразделение» — и есть целевой дизайн для ведомственных систем (цель ТЗ — переиспользование ядра
для ДРУГИХ ОТДЕЛОВ, а не для произвольных ИИ-приложений). Ядро уже безусловно универсально внутри этого
класса. Стоимость 0, риск 0. Минус: за пределы класса не переиспользуется.

### Вариант B — нейтральные имена, та же форма (косметика)
Переименовать `Classification`→`SecurityLevel`, `DivisionId`→`Scope`, оставив решётку «уровень + скоуп».
Убирает из ядра доменный СЛОВАРЬ, но не СУТЬ: «один int-уровень + один скоуп» остаётся, RBAC/ABAC так и не
ложится. Стоимость средняя (переименование + миграция). По-честному — «косметика», не настоящая универсальность.

### Вариант C — по-настоящему подключаемая модель доступа (реальная универсализация)
- Ретривер применяет `IAccessPolicy`, поставляемый профилем **ЦЕЛИКОМ** (не «baseline + сужение»). Ядро даёт
  **fail-closed дефолт = deny-all**; для одноарендных/нережимных систем — опциональная `AllowAll`-политика.
- Данные доступа на строках корпуса становятся **профиль-определяемыми**:
  - **C1 (типизированные обобщённые колонки):** ядро держит нейтральные индексируемые колонки, смысл которых
    задаёт профиль. Быстро для SQL-pre-filter, но по сути это Вариант B (форма «уровень+скоуп» сохраняется).
  - **C2 (непрозрачная метка доступа):** ядро хранит обобщённую метку (`AccessTags int[]` / `security_label
    jsonb`), а профильная `IAccessPolicy` транслирует её в EF/SQL-предикат. Поддерживает RBAC/ABAC/мультиаренду;
    сложнее, нужен индекс (GIN по int[]) и аккуратность с производительностью pre-filter.
- **Инвариант fail-closed сохраняется:** нет политики → выдачи нет. `BaselineAccess` «гриф × подразделение»
  переезжает В ПРОФИЛЬ «Инспектор» как его политика доступа; все текущие GATE-1 тесты обязаны остаться зелёными.
- **Миграция:** затрагивает схему `core` (обобщённая колонка доступа) — это правка САМОГО ядра безопасности,
  с блендированием на существующий денормализованный pre-filter. Отдельный эпик с отдельным ревью.

## Рекомендация (честно)
- Если дорожная карта — только ведомственные/режимные профили (как в ТЗ), доступ **уже** универсален для этого
  класса → **Вариант A**, а универсализация дальше — спекулятивная сложность (YAGNI) на самой критичной по
  безопасности части системы.
- Если есть реальная близкая потребность в НЕрежимном профиле (коммерция/RBAC) → **Вариант C2** (непрозрачная
  метка + политика профиля целиком). Это значимый, аккуратный, миграционный рефактор ядра безопасности.
- **Вариант B не рекомендуется** — даёт видимость нейтральности без сути.

## Критерии приёмки (для Варианта C, если выбран)
- ⏳ `IAccessPolicy` — единственный источник фильтра доступа; ядро без политики = deny-all (fail-closed тест).
- ⏳ «Гриф × подразделение» реализован как политика ПРОФИЛЯ «Инспектор»; GATE-1 (`RetrieverAccessFilterTests`) зелёный.
- ⏳ Второй, НЕрежимный профиль поднимается с `AllowAll`/своей политикой, не трогая схему ядра.
- ⏳ Миграция схемы `core`; pre-filter остаётся на стороне БД и индексируется.
- ⏳ Арх-тест: ядро не содержит доменной модели доступа «гриф/подразделение» (нейтральность).
