## Замысел

Влить СКИД (контроль исполнения документов, ~38 тыс. строк) в ISC.AI так, чтобы инспектор
получил **одно приложение с одним входом**, где «Документы» и «Поручения» стоят рядом с «Чат-ассистентом»
и «Генератором», а ИИ работал по **живым** документам и поручениям, а не по отдельной копии.

Форма слияния (обоснование — в ADR-0017): СКИД **не** становится вторым профилем (профиль в ISC.AI ровно
один на развёртывание), а становится переиспользуемым пакетом модулей, который профиль включает в свой
реестр.

## Целевая структура

```
src/modules/docflow/
  ISC.AI.Modules.DocFlow/              манифест: дескрипторы модулей + AddDocFlow(...)
  ISC.AI.Modules.DocFlow.Domain/       сущности и перечисления (из SKID.Domain)
  ISC.AI.Modules.DocFlow.Application/  сценарии Mediator, валидаторы, DTO
  ISC.AI.Modules.DocFlow.Data/         DocFlowDbContext (схема docflow) + миграции
  ISC.AI.Modules.DocFlow.UI/           RCL: страницы модулей
```

Зависимости (ядро не трогаем): `модуль → Abstractions` (и `Persistence` — только `*.Data`);
`профиль → модуль`; **ядро → НЕ ссылается на модуль** (арх-тест ТС-009 расширить).

Подключение — одной строкой в манифесте профиля: `InspectorProfile.Modules` дополняется секцией меню
«Документооборот», `RegisterServices`/`RegisterDataContexts` вызывают `AddDocFlow(...)`.

## Как ложатся RAG и грунтовка (частый вопрос)

**Заблуждение:** «документы лягут в схему `docflow` ⇒ RAG должен искать по схеме `docflow`».
**На самом деле:** RAG не ищет по доменным таблицам вообще. Он ищет по **индексу**, а индекс всегда в `core`.

Это два разных хранилища с разными задачами:

| | Схема `docflow` — **домен** | Схема `core` — **индекс** |
|---|---|---|
| Что лежит | Документ как объект работы: рег. №, исполнитель, срок, статус, поручения, файл | Текст, порезанный на фрагменты, + векторы |
| Кто читает | Страницы «Документы» / «Поручения» | Только `IRetriever` (RAG) |
| Зачем | Вести документооборот | Искать по смыслу |

Мост между ними — существующий конвейер загрузки (`IIngestionPort`):

```
docflow.document              core.document              core.chunk + вектор
рег.№ 12-345, срок,    ──→    текст, гриф,        ──→    фрагменты, гриф,
исполнитель, файл             подразделение,             подразделение,
                              StorageUri                 IsCurrent
```

Далее всё работает без изменений: `IRetriever` фильтрует по допуску **прямо в SQL** (гриф ≤ допуска И
подразделение ∈ разрешённых И `IsCurrent`) — гриф и подразделение денормализованы на сам чанк
(`ChunkEntity`) именно для того, чтобы не джойнить через границы схем; затем грунтовка разрешает ссылаться
ТОЛЬКО на выданные фрагменты и проверяет каждую ссылку валидатором (ТБ-040/041). **Схема-источник в этом
не участвует** — ядро не знает и не должно знать, откуда пришёл текст.

**Архитектурный паттерн уже в коде** (⚠️ уточнение по итогам этапа 7.2, 2026-08-06: сама схема-прецедент
`inspector.norm_document_link` — таблица без единого писателя/читателя нигде в коде, задел на будущее,
не рабочий образец; ссылка чат→НПА сегодня не работает тоже). Валиден именно ПАТТЕРН — слабая ссылка
по значению **без FK через границу схем** (ТО-инф-06), домен в схеме профиля, индекс в `core`.
Документооборот получил рабочий мостик `docflow.document_index_link` — и, в отличие от НПА, довёл его
до конца: `docflow_document_id` в `core.document.metadata` → `RetrievedChunk.Metadata` → ссылка в ответе
чата на карточку поручения (этап 7.2). НПА тем же путём пока не прошли.

Отсюда следует, что работа не в «поиске по docflow», а в **подаче** документов СКИД в существующий
конвейер — это отдельный этап 7 ниже.

### Этап 7.1 — ✅ КОД ГОТОВ (2026-08-05); сквозная проверка чата — после применения миграции
- **`IDocumentIndexer` + `DocFlowDocumentIndexer`**: краткое содержание + полный текст →
  `IIngestionPort` с грифом/подразделением ДОКУМЕНТА (fail-closed по построению); Title =
  «рег№ · содержание»; Metadata несёт обратную ссылку `docflow_document_id` (для карточек-источников
  в ответах чата — следующий шаг); при переиндексации прежняя корпусная версия гасится supersede;
  осиротевший мостик (после purge ядра) чинится сбросом; успех аудируется (`Ingest`, гриф документа).
- **Мостик `docflow.document_index_link`** (миграция `DocumentIndexLink`): одна строка на документ,
  слабая ссылка на `core.document` без FK (ТО-инф-06), `IndexedAt` — диагностика.
- **Первый прод-потребитель очереди Э4-20**: регистрация ставит задачу «Индексация документа в корпус
  ИИ» и НЕ ждёт эмбеддинги; делегат резолвит сервисы из свежего scope. Делегаты не переживают
  перезапуск (свойство очереди) — для этого `ReindexDocumentCommand` + пункт «Переиндексировать в
  корпусе ИИ» на карточке; там же чип «в корпусе ИИ»/«не в корпусе» (`DocumentDetails.IndexedAt`).
- **Разведка ядра** выполнена workflow-агентами (очередь/конвейер/вызовы); зафиксирован разрыв UI:
  пользователь чата пока НЕ видит источник фрагмента (Metadata до `RetrievedChunk` не доходит) —
  «ссылка ответа → карточка документа» через мостик остаётся следующим шагом этапа 7.
- **Живая проверка формой поймала баг**: «Хранение» требовало единый срок (скрытый чекбокс
  «Исполнения» по умолчанию true) — исправлено, форма шлёт флаг только для «Исполнения».
- Проверено: сборка 0 ошибок; юнит 218/218; интеграционные **5/5** — новый сквозной тест индексатора
  (гриф на чанках, мостик, дедуп Unchanged, замена текста → supersede: старые чанки погашены,
  `SupersededByDocumentId` проставлен, мостик перенаправлен). Регистрация через UI на реальной БД
  прошла (документ №1 «Восток»); карточка/индексация ждут применения миграции `DocumentIndexLink`.

### Этап 7.2 Ссылки на источники в ответах чата — ✅ ГОТОВО (2026-08-06)
Три последовательных разрыва (найдены точным разбором кода, не предположением; «прецедент НПА»
`inspector.norm_document_link`, на который ссылалась постановка задачи, при проверке оказался мёртвой
схемой — ни одной записи/чтения нигде в коде, реального образца «клик → карточка» в системе не было
вообще):
- **Разрыв 1 — retrieval терял Metadata.** `PgVectorRetriever.RetrieveAsync` заходил в навигацию
  `Embedding.Chunk.DocumentId`, но не на шаг дальше — `Chunk.Document.Metadata` (где физически лежит
  jsonb, записанный `DocFlowDocumentIndexer` при индексации). Контракт `RetrievedChunk.Metadata` менять
  не пришлось (поле уже существовало под нужды НПА) — только доснять его в проекции.
- **Разрыв 2 — `ChatReply` не имел поля под источники.** `ChatService.SendAsync`/`SendStreamingAsync`
  отбрасывали `GroundedResponse.UsedFragments` при сборке ответа — физически было некуда его положить.
  `ChatReply` получил новый опциональный параметр `UsedFragments` (обратно совместимо — 3 места
  конструирования внутри `ChatService.cs`, тестов, строящих `ChatReply` напрямую, не нашлось).
- **Разрыв 3 — `ChatAssistant.razor` не рендерил источники вовсе.** Была только агрегатная плашка
  «не все ссылки подтверждены» (`GroundingResult.AllConfirmed`), самого списка источников — ни
  разметки, ни заготовки. Добавлено: `Msg.Sources` (per-message, не общий «последний» флаг — история
  переживает несколько ответов, каждый показывает СВОИ источники) заполняется из `reply.UsedFragments`
  на финальном обновлении потока; под пузырём ответа — список источников, `DistinctBy(DocumentId)`
  (несколько чанков одного документа не дублируют строку). Ядро не интерпретирует `Metadata` —
  доменный смысл ключа `docflow_document_id` знает только этот рендер: есть ключ → `MudLink` на
  `/docflow/documents/{id}`; есть `reg_number` без `docflow_document_id` (пока не наш случай, задел
  под будущее) или вообще ничего — обычный текст `«Документ №{DocumentId}»` без ссылки, никакая ссылка
  не выдумывается сверх того, что подтверждено метаданными.
- **Обратный резолв мостика `document_index_link` не понадобился.** Рассматривались два пути: (а)
  читать `docflow.DocumentIndexLinks.Where(CoreDocumentId == …)`, (б) `RetrievedChunk.Metadata["docflow_
  document_id"]` напрямую — он уже лежит в `core.document.metadata` с самой индексации. Выбран (б):
  ноль новых зависимостей на уровне рендера чата (ядро/профиль по-прежнему не тянут докфлоу-типы),
  меньше связности, чем у (а).
- **Область: только текущая сессия.** `Msg.Sources` не сохраняется в БД диалога — история
  (`GetConversationHistoryQuery`) не несёт `UsedFragments`, только текст. При перезагрузке страницы или
  выборе старого диалога источники под старыми ответами не показываются (сам ответ и агрегатная плашка
  грунтовки — показываются, это `GroundingResult`, он персистится). Осознанно НЕ в этом заходе —
  требует новой колонки/миграции в хранилище диалогов; см. «куски без этапа-владельца» ниже.
- Затронутые файлы: `RetrievedChunk`/`PgVectorRetriever`/`ChatReply`/`ChatService` (ядро, доменно-
  нейтрально — ни один тип докфлоу не импортирован); `ChatAssistant.razor` (профиль — здесь и только
  здесь `docflow_document_id` получает смысл).
- Проверено: сборка 0 ошибок; юнит **220/220** (+2 — `ChatServiceTests`: `UsedFragments` доезжает
  и обычным, и потоковым путём); интеграционные **33/33** (+1 — новый тест на РЕАЛЬНОМ Postgres:
  `Document.Metadata` (jsonb) корректно транслируется через `PgVectorRetriever`'овскую проекцию с
  распределением по векторному расстоянию, не только не ломает существующий SQL, а доезжает до
  `RetrievedChunk.Metadata` со значением). Живая проверка в браузере — не проводилась (по решению
  заказчика этой сессии агент не открывает превью сам); проверить: спросить в грунтованном режиме про
  зарегистрированный докфлоу-документ, под ответом ассистента должен появиться список «Источники:»
  со ссылкой на `/docflow/documents/{id}`.

## Что уточнило ТЗ СКИД (прочитано 2026-08-05)

**Заказчик тот же** — Главная инспекция при Председателе ГКНБ КР. Это снимает последние сомнения в форме
слияния: одни и те же люди, один продукт (ADR-0017).

**1. Доступ в СКИД — построчный, он НЕ выражается решёткой «гриф × подразделение».** Это главная находка,
она расширяет этап 6:

| Роль | Что видит по ТЗ (разд. 2.1) |
|---|---|
| Администратор | По ТЗ: **доступ к документам ПОЛНОСТЬЮ ЗАКРЫТ**; только пользователи, справочники, журнал действий. ⚠️ **В РЕАЛИЗАЦИИ ИНАЧЕ** — видит все документы (решение заказчика 2026-08-06, обоснование в этапе 6.4) |
| Руководитель | Все документы системы; единственный, кто ставит «Снято с контроля» |
| Инспектор | **Только свои документы** (где он назначен инспектором) — включая отчёты и дашборд |
| Исполнитель | **Только назначения, где он ответственный** |

Наш фильтр ядра — «гриф ≤ допуска И подразделение ∈ разрешённых». Правила выше **ортогональны** ему
(владение/назначение, а не гриф). Ложатся они на подключаемую сужающую политику `IAccessPolicy`
([ADR-0014](../06_ADR/ADR-0014-rezhim-podklyuchaemaya-politika-dostupa.md): «floor ядра + сужающая
политика»), а не на простое сопоставление «роль → политика», как было написано в этапе 6 изначально.
Отдельно отмечено: «администратор не видит документов» — правило **на снятие** доступа у самой
привилегированной роли; его нельзя реализовать как «больше прав = больше видно».

**2. Отчёты — состав известен, риск №1 сузился** (разд. 6): **6 отчётов** (по лицу/инспектору, по
подразделению, по срокам, по просроченным, по типам документов, по периоду) × **3 формата** (PDF, Excel,
Word). Плюс п. 8.3 — **персонализация печати**: колонтитул с именем пользователя, датой и временем печати
(режимно значимо — прослеживаемость печати ДСП, смыкается с нашим аудитом ТБ-030).

**3. Подразделения — конфликт справочников конкретизировался** (вопрос 3): в СКИД справочник **плоский**,
ключ — **Guid**; в профиле «Инспектор» — **иерархический** `Division` (ТУ→РО) с `Code`, ключ — **int**, и
он уже сопоставляется со СКИД по значению кода. Плюс архитектурная тонкость: `docflow` — переиспользуемый
модуль, он **не может зависеть от профиля**, поэтому «просто взять `Division` профиля» нельзя.

**4. Требования, которые надо сохранить при переносе:**
- **Двуязычие рус/кырг** (п. 7.1) — требование ТЗ, а не опция; в «ИнспекторAI» аналога пока нет.
- **Файлы только для просмотра в интерфейсе, без скачивания** (п. 3.3) — согласуется с режимом ДСП.
- Версионирование файла при замене (п. 3.3); история статусов, продлений и переназначений (п. 4.8).
- Уведомления за 7 дней и в день срока, **только в интерфейсе, без email** (разд. 5) — согласуется с air-gap.
- Журнал действий доступен **только Администратору** (разд. 10) — у нас журнал строже (неизменяемый,
  хеш-цепочка), правило видимости переносится.
- Производительность: ≥20 одновременных пользователей, отклик ≤3 с (п. 8.2).

**5. Несовпадения типов ключей при переносе:** СКИД — `Guid` (пользователи, подразделения, документы),
ядро ISC.AI — `int` (`AppUserEntity.Id`, `DivisionId` в `core`). Решается на этапе 2; данных нет, поэтому
выбор свободный, но он влияет на связку с `AccessContext.AllowedDivisions` (там `int`).

**6. Грифа в ТЗ СКИД нет вообще** — подтверждает вопрос 2: правило назначения грифа определяет режим
«ИнспекторAI», из СКИД его взять неоткуда. При этом сам документ ТЗ имеет пометку **ДСП**, то есть
предметная область режимная по факту.

  означало переоформление документа целиком. Новое назначение — всегда «Зарегистрировано», со СВОИМ
  сроком («единый срок» действует только на назначения из формы регистрации — решение СКИД).
- **Переназначение исполнителя (§4.7)**: статус, срок и контролёр не меняются — новый исполнитель
  наследует срок прежнего.

**Ошибка нашего плана, найденная разбором:** вид уведомления `InspectorReassigned` рождается НЕ при
переназначении исполнителя, а при РЕДАКТИРОВАНИИ документа (смена ответственного инспектора).
Редактирование не перенесено ⇒ вид не заводится; в 2.2b он был записан как «отложен вместе с §4.7».

**Дефекты СКИД, которые НЕ перенесены (каждый — с исправлением):**
1. **Переназначение проходило из ЛЮБОГО статуса**, включая «Исполнено» и «Снято с контроля»: можно
   было переписать исполнителя уже закрытого поручения. Запрещено, граница та же, что у продления §4.6.
2. **Переназначение на ТОГО ЖЕ человека** проходило: писало в аудит запись с одинаковыми «было/стало»
   и слало ему «вы назначены исполнителем». Теперь операция идемпотентна и молчалива; в диалоге
   текущий исполнитель вообще исключён из списка.
3. **Запрет дубля подразделения жил ТОЛЬКО в валидаторе формы** — уникального индекса не было, и два
   одновременных запроса создавали два назначения на одно подразделение. Добавлен уникальный индекс
   `(document_id, division_id)`; проверка в коде осталась ради внятного сообщения.
4. **Переназначение не попадало ни в историю, ни в ленту** — след оставался только в журнале аудита у
   администратора; для пользователя исполнитель молча менялся. Заведена сущность
   `AssignmentReassignment` (отдельная таблица, а не запись в истории статусов: смена исполнителя —
   не переход статуса, подмешивать её туда значило бы врать про переход, которого не было).
5. **Уведомления при добавлении назначения слались только при указанном исполнителе** — назначение
   «на подразделение» проходило совсем молча. Теперь идёт общий путь: исполнителю «вам назначено»,
   инспектору «создано назначение».
6. **Сообщение «назначения только для группы Исполнение» пользователю не показывалось** — из-за
   привязки правила к полю оно вырождалось в «Ошибка валидации». Отдаётся содержательный текст.

**Правило, которое пришлось ЗАМЕНИТЬ, а не скопировать:** в СКИД исполнитель обязан состоять В ТОМ ЖЕ
подразделении, что и назначение (`user.DepartmentId`). У нас поля «подразделение пользователя» НЕТ:
реестр — `core.app_user` (вопрос 4), связь человека с подразделениями выражена ДОПУСКОМ
(`core.clearance.division_scope`). Проверяем по нему (`IUserDirectory.CanSeeDivisionAsync`): смысл тот
же и строже по последствиям — иначе исполнителю поручат документ, которого он не увидит.

**Свойство §4.3, которое стоит знать (не дефект):** добавление назначения ОТКАТЫВАЕТ агрегированный
статус назад. У документа, где все назначения были «Исполнено» или «Снято», после добавления одного
«Зарегистрировано» агрегат станет «Зарегистрирован» — закрытый документ снова становится незакрытым.

- **Требуется миграция** `AssignmentReassignments`: новая таблица + УНИКАЛЬНЫЙ индекс
  `(document_id, division_id)`. На контуре с уже накопленными дублями индекс не применится — сначала

номера отбивалось бы им же самим); неактивный тип не мешает править документ, если тип не меняется;
конкурентная правка (`xmin`) даёт 409 с предложением перечитать карточку, а не молча затирает чужое.

  поиск ИИ продолжал бы отвечать по старой редакции.

**Аудит:** отдельная запись сверх сквозной — с ИМЕНАМИ изменённых полей, без значений (ТБ-032: копия
содержания под грифом сделала бы журнал второй базой документов).

### Мелкие пробелы, режим и эксплуатация — ✅ ГОТОВО (2026-08-07)

**Эксплуатация**
- `GET /health` — анонимно и БЕЗ обращения к БД. Анонимно: проверяющий (docker healthcheck,
  балансировщик) учётки не имеет. Без БД: отвечает на «поднялся ли процесс», а не «здорова ли
  система» — иначе недоступность базы перезапускала бы приложение по кругу, ничего не починив.
  Наружу не уходит ничего о системе (ни версии, ни профиля) — это разведданные (ТБ-010).
- **Ручной запуск проверки сроков.** Логика вынесена из `BackgroundService` в `IDeadlineChecker`:
  раньше позвать её иначе, чем дождавшись часового тика, было нельзя — ни при развёртывании,
  ни при разборе жалобы «уведомление не пришло». Задача стала тонким циклом. Повтор безопасен:
  перевод в «Просрочено» идемпотентен, уведомления отсекает дедупликация.
- **Отметка получателя на выдаваемых PDF** («ФИО · дата и время», перенос СКИД). Файл, покинувший
  систему, живёт своей жизнью; отметка привязывает КОПИЮ к тому, кто её получил. Честно про
  границы: это не защита от копирования — отметку можно снять редактором; она поднимает цену
  анонимной утечки. Только PDF (конвертация в закрытом контуре отвергнута ещё на 4.3). Битый или
  защищённый паролем файл отдаётся КАК ЕСТЬ: сорвать выдачу из-за неудавшегося оформления хуже.

**Мелкие пробелы**
- **Удаление типа документа** — только пока по нему нет документов (иначе у них пропала бы группа,
  а с ней правила поведения, §3.1). Признак `CanDelete` считается вместе со списком; проверка
  повторяется в хранилище — признак мог устареть, пока экран открыт.
- **Удаление вложения** — физически, вместе с файлом; файл с диска ПОСЛЕ записи в БД (обратный
  порядок при сбое оставил бы строку, указывающую в пустоту). Версионируемые файлы документа так
  не удаляются — у них своя история.
- **Предпросмотр отчёта** до выгрузки: отбор задаётся семью полями, промах виден только в скачанном
  файле. Усечение названо честно («показаны первые N, в файл попадут все»). В журнал как выгрузка
  НЕ пишется — файла не возникло. Отбор для предпросмотра и выгрузки собирает один метод: разойдись
  они, на экране показывалось бы одно, а в файл попадало другое.

#### 6.3 Stored-XSS в предпросмотре файлов — ✅ ГОТОВО (2026-08-06)

## Границы и примечания

- **Пересечение модулей.** У ISC.AI уже есть «Дашборд», «Архив», «Мониторинг»; у СКИД — свой дашборд и
  работа с документами. При переносе решается: сливать в один модуль или держать раздельно. Не «само
  собой» — фиксируется решением при этапе 5(UI)/6.
- **API у СКИД нет** (только вход, файловый эндпоинт, SignalR-хаб, Blazor UI) — вариант «интеграция по API»
  физически отсутствует; переносится исходный код.

  аналога пока нет. Влияние на оболочку оценить на этапе 5: либо двуязычие остаётся внутри модуля, либо
  поднимается до общей оболочки — второе шире по объёму.
- ⚠️ **Найдено аудитом (2026-08-06), этапа-владельца пока нет:** экран журнала действий администратора
  СКИД (`AuditLogsPage`, правило видимости «только Администратору» уже зафиксировано, работы — нет);
