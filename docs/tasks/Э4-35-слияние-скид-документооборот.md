## Замысел

Влить СКИД (контроль исполнения документов, ~38 тыс. строк) в ISC.AI так, чтобы инспектор
получил **одно приложение с одним входом**, где «Документы» и «Поручения» стоят рядом с «Чат-ассистентом»
и «Генератором», а ИИ работал по **живым** документам и поручениям, а не по отдельной копии.

Форма слияния (обоснование — в ADR-0017): СКИД **не** становится вторым профилем (профиль в ISC.AI ровно
один на развёртывание), а становится переиспользуемым пакетом модулей, который профиль включает в свой
реестр.

## Целевая структура

```
src/modules/docflow/
  ISC.AI.Modules.DocFlow/              манифест: дескрипторы модулей + AddDocFlow(...)
  ISC.AI.Modules.DocFlow.Domain/       сущности и перечисления (из SKID.Domain)
  ISC.AI.Modules.DocFlow.Application/  сценарии Mediator, валидаторы, DTO
  ISC.AI.Modules.DocFlow.Data/         DocFlowDbContext (схема docflow) + миграции
  ISC.AI.Modules.DocFlow.UI/           RCL: страницы модулей
```

Зависимости (ядро не трогаем): `модуль → Abstractions` (и `Persistence` — только `*.Data`);
`профиль → модуль`; **ядро → НЕ ссылается на модуль** (арх-тест ТС-009 расширить).

Подключение — одной строкой в манифесте профиля: `InspectorProfile.Modules` дополняется секцией меню
«Документооборот», `RegisterServices`/`RegisterDataContexts` вызывают `AddDocFlow(...)`.

## Как ложатся RAG и грунтовка (частый вопрос)

**Заблуждение:** «документы лягут в схему `docflow` ⇒ RAG должен искать по схеме `docflow`».
**На самом деле:** RAG не ищет по доменным таблицам вообще. Он ищет по **индексу**, а индекс всегда в `core`.

Это два разных хранилища с разными задачами:

| | Схема `docflow` — **домен** | Схема `core` — **индекс** |
|---|---|---|
| Что лежит | Документ как объект работы: рег. №, исполнитель, срок, статус, поручения, файл | Текст, порезанный на фрагменты, + векторы |
| Кто читает | Страницы «Документы» / «Поручения» | Только `IRetriever` (RAG) |
| Зачем | Вести документооборот | Искать по смыслу |

Мост между ними — существующий конвейер загрузки (`IIngestionPort`):

```
docflow.document              core.document              core.chunk + вектор
рег.№ 12-345, срок,    ──→    текст, гриф,        ──→    фрагменты, гриф,
исполнитель, файл             подразделение,             подразделение,
                              StorageUri                 IsCurrent
```

Далее всё работает без изменений: `IRetriever` фильтрует по допуску **прямо в SQL** (гриф ≤ допуска И
подразделение ∈ разрешённых И `IsCurrent`) — гриф и подразделение денормализованы на сам чанк
(`ChunkEntity`) именно для того, чтобы не джойнить через границы схем; затем грунтовка разрешает ссылаться
ТОЛЬКО на выданные фрагменты и проверяет каждую ссылку валидатором (ТБ-040/041). **Схема-источник в этом
не участвует** — ядро не знает и не должно знать, откуда пришёл текст.

**Прецедент уже в коде:** ровно так живут НПА — домен норм в схеме `inspector`, индекс в `core`, связь
таблицей-мостиком `inspector.norm_document_link` (слабая ссылка по `document_id`, **без FK через границу
схем** — ТО-инф-06). Документооборот получает такой же мостик `docflow.document_index_link`, чтобы ответ
чата мог сослаться на конкретное поручение и открыть его.

Отсюда следует, что работа не в «поиске по docflow», а в **подаче** документов СКИД в существующий
конвейер — это отдельный этап 7 ниже.

### Этап 7.1 — ✅ КОД ГОТОВ (2026-08-05); сквозная проверка чата — после применения миграции
- **`IDocumentIndexer` + `DocFlowDocumentIndexer`**: краткое содержание + полный текст →
  `IIngestionPort` с грифом/подразделением ДОКУМЕНТА (fail-closed по построению); Title =
  «рег№ · содержание»; Metadata несёт обратную ссылку `docflow_document_id` (для карточек-источников
  в ответах чата — следующий шаг); при переиндексации прежняя корпусная версия гасится supersede;
  осиротевший мостик (после purge ядра) чинится сбросом; успех аудируется (`Ingest`, гриф документа).
- **Мостик `docflow.document_index_link`** (миграция `DocumentIndexLink`): одна строка на документ,
  слабая ссылка на `core.document` без FK (ТО-инф-06), `IndexedAt` — диагностика.
- **Первый прод-потребитель очереди Э4-20**: регистрация ставит задачу «Индексация документа в корпус
  ИИ» и НЕ ждёт эмбеддинги; делегат резолвит сервисы из свежего scope. Делегаты не переживают
  перезапуск (свойство очереди) — для этого `ReindexDocumentCommand` + пункт «Переиндексировать в
  корпусе ИИ» на карточке; там же чип «в корпусе ИИ»/«не в корпусе» (`DocumentDetails.IndexedAt`).
- **Разведка ядра** выполнена workflow-агентами (очередь/конвейер/вызовы); зафиксирован разрыв UI:
  пользователь чата пока НЕ видит источник фрагмента (Metadata до `RetrievedChunk` не доходит) —
  «ссылка ответа → карточка документа» через мостик остаётся следующим шагом этапа 7.
- **Живая проверка формой поймала баг**: «Хранение» требовало единый срок (скрытый чекбокс
  «Исполнения» по умолчанию true) — исправлено, форма шлёт флаг только для «Исполнения».
- Проверено: сборка 0 ошибок; юнит 218/218; интеграционные **5/5** — новый сквозной тест индексатора
  (гриф на чанках, мостик, дедуп Unchanged, замена текста → supersede: старые чанки погашены,

## Что уточнило ТЗ СКИД (прочитано 2026-08-05)

**Заказчик тот же** — Главная инспекция при Председателе ГКНБ КР. Это снимает последние сомнения в форме
слияния: одни и те же люди, один продукт (ADR-0017).

**1. Доступ в СКИД — построчный, он НЕ выражается решёткой «гриф × подразделение».** Это главная находка,
она расширяет этап 6:

| Роль | Что видит по ТЗ (разд. 2.1) |
|---|---|
| Администратор | **Доступ к документам ПОЛНОСТЬЮ ЗАКРЫТ**; только пользователи, справочники, журнал действий |
| Руководитель | Все документы системы; единственный, кто ставит «Снято с контроля» |
| Инспектор | **Только свои документы** (где он назначен инспектором) — включая отчёты и дашборд |
| Исполнитель | **Только назначения, где он ответственный** |

Наш фильтр ядра — «гриф ≤ допуска И подразделение ∈ разрешённых». Правила выше **ортогональны** ему
(владение/назначение, а не гриф). Ложатся они на подключаемую сужающую политику `IAccessPolicy`
([ADR-0014](../06_ADR/ADR-0014-rezhim-podklyuchaemaya-politika-dostupa.md): «floor ядра + сужающая
политика»), а не на простое сопоставление «роль → политика», как было написано в этапе 6 изначально.
Отдельно отмечено: «администратор не видит документов» — правило **на снятие** доступа у самой
привилегированной роли; его нельзя реализовать как «больше прав = больше видно».

**2. Отчёты — состав известен, риск №1 сузился** (разд. 6): **6 отчётов** (по лицу/инспектору, по
подразделению, по срокам, по просроченным, по типам документов, по периоду) × **3 формата** (PDF, Excel,
Word). Плюс п. 8.3 — **персонализация печати**: колонтитул с именем пользователя, датой и временем печати
(режимно значимо — прослеживаемость печати ДСП, смыкается с нашим аудитом ТБ-030).

**3. Подразделения — конфликт справочников конкретизировался** (вопрос 3): в СКИД справочник **плоский**,
ключ — **Guid**; в профиле «Инспектор» — **иерархический** `Division` (ТУ→РО) с `Code`, ключ — **int**, и
он уже сопоставляется со СКИД по значению кода. Плюс архитектурная тонкость: `docflow` — переиспользуемый
модуль, он **не может зависеть от профиля**, поэтому «просто взять `Division` профиля» нельзя.

**4. Требования, которые надо сохранить при переносе:**
- **Двуязычие рус/кырг** (п. 7.1) — требование ТЗ, а не опция; в «ИнспекторAI» аналога пока нет.
- **Файлы только для просмотра в интерфейсе, без скачивания** (п. 3.3) — согласуется с режимом ДСП.
- Версионирование файла при замене (п. 3.3); история статусов, продлений и переназначений (п. 4.8).
- Уведомления за 7 дней и в день срока, **только в интерфейсе, без email** (разд. 5) — согласуется с air-gap.
- Журнал действий доступен **только Администратору** (разд. 10) — у нас журнал строже (неизменяемый,
  хеш-цепочка), правило видимости переносится.
- Производительность: ≥20 одновременных пользователей, отклик ≤3 с (п. 8.2).

**5. Несовпадения типов ключей при переносе:** СКИД — `Guid` (пользователи, подразделения, документы),
ядро ISC.AI — `int` (`AppUserEntity.Id`, `DivisionId` в `core`). Решается на этапе 2; данных нет, поэтому
выбор свободный, но он влияет на связку с `AccessContext.AllowedDivisions` (там `int`).

**6. Грифа в ТЗ СКИД нет вообще** — подтверждает вопрос 2: правило назначения грифа определяет режим
«ИнспекторAI», из СКИД его взять неоткуда. При этом сам документ ТЗ имеет пометку **ДСП**, то есть
предметная область режимная по факту.

### Этап 6. Доступ, роли и идентичность — 1–1.5 недели ⚠️ РИСК (проектное решение, не код)

**Доступ и роли:**
- Каждый документ/поручение получает **гриф и подразделение**; выдача — через существующий фильтр
  (fail-closed, ТБ-020/021). Понятия грифа в СКИД нет — правило назначения при регистрации определяет
  режим (вопрос 2). Унаследованных документов нет, поэтому «правило для старых записей» не требуется.
- Подразделения: `departments` СКИД и подразделения ISC.AI сводятся к одному справочнику (вопрос 3).
- Роли СКИД (Администратор/Руководитель/Инспектор/Исполнитель) → именованные политики
  `IModule.RequiredPolicy` (закрывает отложенный пункт
  [ADR-0016](../06_ADR/ADR-0016-skid-istochnik-identichnosti-dopusk-lokalno.md)).
- ⚠️ **Построчные правила ТЗ (разд. 2.1) — сверх решётки, через `IAccessPolicy`** (ADR-0014, сужающая
  политика поверх floor ядра). Их четыре, и они про владение/назначение, а не про гриф:
  «Администратор НЕ видит документов вообще» (снятие доступа у привилегированной роли — нельзя выразить
  как «больше прав»); «Руководитель — все»; «Инспектор — только свои документы»; «Исполнитель — только
  свои назначения». Это отдельная проектная работа, а не сопоставление ролей политикам.

**Идентичность — реестр пользователей переезжает к нам (решено 2026-08-05, вопрос 4):**
- Таблицы `users`/`departments` переносятся вместе с остальной схемой; администрирование учёток
  (создание, временный пароль, сброс, блокировка) наследуется из СКИД как экраны модуля.
- Порт `IExternalIdentityProvider` в `Abstractions` **СОХРАНЯЕТСЯ** — это шов под будущий SSO; под ним
  появляется **локальная** реализация вместо адаптера чужой БД. Проверка Argon2id (`SkidPasswordHash`,
  Sodium.Core) переезжает как есть.
- **Выводятся из решения:** проект `src/integrations/ISC.AI.Identity.Skid` (read-only контекст чужой БД),
  строка `ConnectionStrings:Skid`, секрет `Database:Passwords:Skid` и организационное требование
  read-only учётки `iscai_ro`. Минус внешняя БД, минус секрет, минус сетевая зависимость в контуре.
- Вход, cookie, security stamp и ревалидация сессий (`ISC.AI.Web/Security`) **не меняются** — меняется
  только реализация под портом.
- Собственный вход СКИД (`/auth/login`, своя cookie, своя ревалидация) выбрасывается — вход один, наш.
- ⚠️ **Порядок обязателен:** адаптер выводится ТОЛЬКО после того, как локальная идентичность заработала,
  иначе система остаётся без аутентификации.
- Инвариант сохраняется: **допуск НЕ выводится из учётки** (default-deny, ТБ-012) даже после того, как
  и идентичность, и допуск стали локальными.
