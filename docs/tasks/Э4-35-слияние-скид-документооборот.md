| | |
|---|---|

| Требования ТЗ | ТС-002/003/004/006/007 (ядро, профиль, реестр модулей); ТО-инф-01 (схемы); ТБ-012/020/021 (допуск, fail-closed); ТБ-030 (аудит); ТСТ-001 (лицензии) |

## Замысел

Влить эксплуатируемую СКИД (контроль исполнения документов, ~38 тыс. строк) в ISC.AI так, чтобы инспектор
получил **одно приложение с одним входом**, где «Документы» и «Поручения» стоят рядом с «Чат-ассистентом»
и «Генератором», а ИИ работал по **живым** документам и поручениям, а не по отдельной копии.

Форма слияния (обоснование — в ADR-0017): СКИД **не** становится вторым профилем (профиль в ISC.AI ровно
один на развёртывание), а становится переиспользуемым пакетом модулей, который профиль включает в свой
реестр.

## Целевая структура

```
src/modules/docflow/
  ISC.AI.Module.DocFlow/              манифест: дескрипторы модулей + AddDocFlow(...)
  ISC.AI.Module.DocFlow.Domain/       сущности и перечисления (из SKID.Domain)
  ISC.AI.Module.DocFlow.Application/  сценарии Mediator, валидаторы, DTO
  ISC.AI.Module.DocFlow.Data/         DocFlowDbContext (схема docflow) + миграции
  ISC.AI.Module.DocFlow.UI/           RCL: страницы модулей
```

Зависимости (ядро не трогаем): `модуль → Abstractions` (и `Persistence` — только `*.Data`);
`профиль → модуль`; **ядро → НЕ ссылается на модуль** (арх-тест ТС-009 расширить).

Подключение — одной строкой в манифесте профиля: `InspectorProfile.Modules` дополняется секцией меню
«Документооборот», `RegisterServices`/`RegisterDataContexts` вызывают `AddDocFlow(...)`.

## Как ложатся RAG и грунтовка (частый вопрос)

**Заблуждение:** «документы лягут в схему `docflow` ⇒ RAG должен искать по схеме `docflow`».
**На самом деле:** RAG не ищет по доменным таблицам вообще. Он ищет по **индексу**, а индекс всегда в `core`.

Это два разных хранилища с разными задачами:

| | Схема `docflow` — **домен** | Схема `core` — **индекс** |
|---|---|---|
| Что лежит | Документ как объект работы: рег. №, исполнитель, срок, статус, поручения, файл | Текст, порезанный на фрагменты, + векторы |
| Кто читает | Страницы «Документы» / «Поручения» | Только `IRetriever` (RAG) |
| Зачем | Вести документооборот | Искать по смыслу |

Мост между ними — существующий конвейер загрузки (`IIngestionPort`):

```
docflow.document              core.document              core.chunk + вектор
рег.№ 12-345, срок,    ──→    текст, гриф,        ──→    фрагменты, гриф,
исполнитель, файл             подразделение,             подразделение,
                              StorageUri                 IsCurrent
```

Далее всё работает без изменений: `IRetriever` фильтрует по допуску **прямо в SQL** (гриф ≤ допуска И
подразделение ∈ разрешённых И `IsCurrent`) — гриф и подразделение денормализованы на сам чанк
(`ChunkEntity`) именно для того, чтобы не джойнить через границы схем; затем грунтовка разрешает ссылаться
ТОЛЬКО на выданные фрагменты и проверяет каждую ссылку валидатором (ТБ-040/041). **Схема-источник в этом
не участвует** — ядро не знает и не должно знать, откуда пришёл текст.

**Прецедент уже в коде:** ровно так живут НПА — домен норм в схеме `inspector`, индекс в `core`, связь
таблицей-мостиком `inspector.norm_document_link` (слабая ссылка по `document_id`, **без FK через границу
схем** — ТО-инф-06). Документооборот получает такой же мостик `docflow.document_index_link`, чтобы ответ
чата мог сослаться на конкретное поручение и открыть его.

Отсюда следует, что работа не в «поиске по docflow», а в **подаче** документов СКИД в существующий
конвейер — это отдельный этап 7 ниже.

## Этапы

### Этап 0. Подготовка — 2–3 дня
- [x] ADR-0017 — форма слияния зафиксирована.
- [ ] Скелет пакета: 5 проектов, ссылки, CPM (`Directory.Packages.props`), пустой манифест модуля.
- [ ] Расширить архитектурный тест: ядро не ссылается на `src/modules/*`.
- [ ] **Реестр отличий по лицензиям** — список файлов под замену (MediatR / FluentAssertions / QuestPDF).

### Этап 1. Калибровочный заход — 2–3 дня 🎯
Один модуль **сквозняком**: Domain → Data → Application → UI → пункт меню (кандидат: справочник типов
документов либо подразделения — маленький и самодостаточный).
- Цель не функциональная, а измерительная: подтвердить, что схема «пакет модулей» держит код СКИД, и
  получить **реальный темп** переноса вместо оценки.
- **После этого этапа оценка 7–10 недель пересчитывается в измеренную.**

### Этап 2. Domain + Data — ~1 неделя
- Перенос сущностей и перечислений (~440 строк, 29 файлов) — правки минимальны.
- 17 таблиц: EF-конфигурации, `DocFlowDbContext`, схема **`docflow`**, своя история миграций,
  регистрация через `IDbContextFactory` (ТС-008).
- Сохранить оптимистичную блокировку СКИД (`xmin` на документах, поручениях, комментариях).
- Добавить в сущности поля решётки доступа (гриф, подразделение) — см. этап 6.

### Этап 3. Application — 1–1.5 недели
- **~116 обработчиков MediatR → Mediator (martinothamar)**: `IRequest`/`IRequestHandler` → наши контракты,
  `Task` → `ValueTask`, генератор — только в хосте.
- `AuthorizationBehavior` СКИД (атрибут `[RequireRole]`) заменяется нашими сквозными поведениями
  (аудит, авторизация, проверка грунтовки).
- FluentValidation остаётся (одна и та же библиотека, Apache 2.0) — правки минимальны.

### Этап 4. Инфраструктура — ~1 неделя
- Хранилище файлов, конвертер DOCX→PDF (LibreOffice, внешний процесс — учесть в деплое контура),
  уведомления (SignalR-хаб), системные настройки, фоновая проверка дедлайнов.
- **Аудит СКИД сливается с нашим неизменяемым журналом** (хеш-цепочка, append-only) — не два журнала.

### Этап 5. Отчёты — 0.5–1.5 недели ⚠️ РИСК
- **QuestPDF → PDFsharp / OpenXml** (лицензия, ТСТ-001). Не переименование: у QuestPDF декларативный
  layout, у PDFsharp низкоуровневый API — отчёты переписываются.
- **Первым делом** — инвентаризация отчётов (сколько, какой сложности). До неё срок этапа не фиксируется.

### Этап 6. Доступ и роли — ~1 неделя ⚠️ РИСК (проектное решение, не код)
- Каждый документ/поручение получает **гриф и подразделение**; выдача — через существующий фильтр
  (fail-closed, ТБ-020/021). В СКИД грифа нет ⇒ нужно **явное правило по умолчанию** от режима.
- Сопоставление `departments` СКИД → подразделения ISC.AI.
- Роли СКИД (Admin/Manager/Inspector/Executor) → именованные политики `IModule.RequiredPolicy`
  (закрывает отложенный пункт [ADR-0016](../06_ADR/ADR-0016-skid-istochnik-identichnosti-dopusk-lokalno.md)).
- Собственный вход СКИД выбрасывается — вход один, наш.

### Этап 7. Индексация документов в корпус (RAG) — 0.5–1 неделя 🎯 РАДИ ЭТОГО ВСЁ ЗАТЕВАЕТСЯ
Без этого этапа слияние даёт только «одно меню»; ИИ по документам инспекции работать не начнёт.
- **Мостик** `docflow.document_index_link`: слабая ссылка `документ docflow ↔ core.document` по значению,
  **без FK через границу схем** (ТО-инф-06) — по образцу `inspector.norm_document_link`.
- **Подача в конвейер:** документ/вложение docflow → извлечение текста (DOCX/PDF; сканы — OCR, Э4-29) →
  `IIngestionPort` с **обязательными** грифом и подразделением (правило этапа 6; не задано ⇒ отказ, ТБ-024).
- **Триггер и переиндексация:** при регистрации, добавлении вложения и изменении. При замене версии старые
  фрагменты гасятся (`IsCurrent=false` / `SupersededByDocumentId` — механизм в ядре уже есть, Э4-14).
- **Асинхронно** — через очередь фоновых задач ядра (`AddCoreBackgroundTasks`): регистрация документа в
  СКИД не должна ждать эмбеддинги.
- **Удаление:** гарантированное удаление гасит И оригинал в хранилище, И фрагменты в индексе (ТБ-064).
- **Проверка этапа:** в грунтованном режиме чат отвечает по реальному поручению и даёт ссылку на него.

### Этап 8. Тесты — 0.5–1 неделя
- Перенос 116 тестов; **FluentAssertions → Shouldly** (механически).
- Интеграционные — на Testcontainers с настоящим Postgres (InMemory запрещён правилами проекта).
- Новые тесты: фильтр доступа над документами/поручениями (гриф и подразделение соблюдаются);
  документ docflow доходит до индекса и находится retrieval'ом только в пределах допуска.

### Этап 9. Перенос данных и приёмка — 1–1.5 недели ⚠️ РИСК
- Скрипт переноса `skid_Dev.public` → `docflow`, **обратимый**; проверка сверкой количеств и
  контрольных выборок; сначала на копии, только потом на бою.
- Назначение грифа/подразделения существующим документам по правилу этапа 6.
- Сквозная приёмка на реальных данных; деплой одного хоста (с LibreOffice) в контур.

## Границы и примечания

- **Пересечение модулей.** У ISC.AI уже есть «Дашборд», «Архив», «Мониторинг»; у СКИД — свой дашборд и
  работа с документами. При переносе решается: сливать в один модуль или держать раздельно. Не «само
  собой» — фиксируется решением при этапе 5(UI)/6.
- **API у СКИД нет** (только вход, файловый эндпоинт, SignalR-хаб, Blazor UI) — вариант «интеграция по API»
  физически отсутствует; переносится исходный код.
- Двуязычие СКИД (рус/кырг) — переносится как есть; в ISC.AI аналога пока нет, влияние на оболочку
  оценить на этапе 5.
- Оценка 8–11 недель — **до** калибровочного захода (этап 1). Точная цифра появляется после него.
  (Изначально было 7–10; +1 неделя — добавлен пропущенный этап 7 «индексация в корпус».)
- Коммиты и мёрдж выполняет заказчик; работы ведутся в ветке `feature/skid-docflow-merge`.
