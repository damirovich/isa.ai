## Цель
Ввести аутентификацию и разграничение по допуску — вход для фильтра доступа на retrieval.

## Решение (см. ADR-0016)
СКИД — источник идентичности (вход по его учёткам, read-only чтение его БД, проверка Argon2id-хешей);
допуск (потолок грифа + подразделения) — локально в `core.clearance`, default-deny, читается на каждую
операцию (отзыв — немедленный).

## Что сделано
- ✅ Аутентификация (ТБ-010): cookie-сессия, запрет анонимного доступа фолбэк-политикой; страница `/login`;
  вход — аудируемое событие (fail-closed). Троттлинг попыток входа (5/мин с IP; опционально —
  `ForwardedHeaders:KnownProxies` для развёртывания за обратным прокси контура).
- ✅ Нейтральный порт `IExternalIdentityProvider` (Abstractions) + адаптер `ISC.AI.Identity.Skid`
  (read-only БД СКИД, Argon2id через Sodium.Core, выравнивание времени отказов, тримминг логина как в
  СКИД, отказ для временного пароля `must_change_password`).
- ✅ Привязка локального субъекта к внешней учётке — **строго по `ExternalId`**, никогда по имени входа
  (иначе переиспользованный логин во внешней системе наследует чужой допуск — default-deny обходится).
  Коллизия имени при новой внешней учётке — явный отказ + аудит конфликта, не автопривязка.
- ✅ Допуск как обязательный вход (ТБ-012): `ClearanceEntity.DivisionScope` (миграция `AddAuthIdentity`),
  `ClearanceAccessReader` — per-op чтение, `ClearanceAccessContextProvider` — боевой `IAccessContextProvider`
  (fail-closed). JIT-создание локальной учётки при первом входе — БЕЗ допуска (default-deny); частичные
  уникальные индексы (`user_name`, `external_id`, `clearance.user_id`) учитывают мягкое удаление — отзыв
  и повторная выдача допуска/переиспользование логина не падают на уникальном ограничении.
- ✅ Немедленный отзыв (ТБ-016): допуск не кэшируется — отзыв/деактивация действуют со следующей операции
  (интеграционные тесты `ClearanceAccessReaderTests`, `LoginServiceTests`, Testcontainers). Сессии
  (ТБ-014) — ДВЕ независимые линии ревалидации через общий `ExternalIdentityRevalidator`: cookie-уровень
  (`CookiePrincipalValidator`, гасит саму cookie) и circuit-уровень (реагирует быстрее для открытой
  вкладки); транзиентная недоступность СКИД при ревалидации не гасит сессии массово (см. ADR-0016 п.5).
- ✅ Политики модулей: фолбэк «только аутентифицированные» + именованные политики из
  `IModule.RequiredPolicy` (регистрируются хостом из манифеста — ядро профиля не знает).
- ✅ Рендер-режим — покомпонентно (ADR-0016 п.9): анонимные страницы статичны, защищённые страницы явно
  объявляют `@rendermode="InteractiveServer"` — иначе фолбэк-политика блокирует анонимный SignalR-хаб.
- ✅ `MainLayout` не раскрывает состав модулей/название профиля анонимам (ADR-0016 п.10).
- ✅ Dev-режим (`Auth:Mode=Dev`, только Development) — прежняя заглушка, каркас запускаем без БД СКИД.
- ✅ Аудит: субъект (`SubjectId`) пишется в записи `AuditBehavior` из контекста доступа; недоступность
  СКИД при попытке входа — отдельная ветка (не аудируется как попытка, нейтральное сообщение на форме).
- ✅ Защита от open-redirect после входа (`returnUrl`) и CSRF на `/auth/logout`.

### Состязательное ревью (проведено 2026-07-20/21)
Три независимые линзы (режимные инварианты / корректность ASP.NET Core Blazor / корректность интеграции
со СКИД) нашли 19 находок; каждая прошла адверсариальную верификацию (скептик пытался опровергнуть по
коду). Все 19 подтверждены и исправлены — включая одну **critical** (обход default-deny через
привязку по имени входа, см. выше) и одну **major**, для которой у меня самого была неверная память об
API (`ExcludeFromInteractiveRouting` не существует в .NET 10) — перепроверено по официальной документации
Microsoft, реализован правильный фикс (покомпонентный рендер-режим). Плюс один баг того же класса
(`clearance.user_id` без частичного индекса), не найденный ревью, — поймал собственный интеграционный
тест до того, как я успел отчитаться о завершении.

## Открытые хвосты (не блокируют базовую приёмку, отслеживать)
- ⏳ UI администратора для назначения/отзыва допусков — пока SQL/скриптом (ДОК-07); аудит операций
  выдачи/отзыва допуска (ТБ-016 «с фиксацией в аудите») — при появлении UI.
- ⏳ Роли (Admin/Manager/Inspector/Executor из СКИД) → ролевые политики — фаза Ф3 (ТП-001, ADR-0016).
- ⏳ 2FA — ждёт класс защищённости (ТБ-061); повторная аутентификация для привилегированных действий (ТБ-014).
- ⏳ Организационное разделение ролей эксплуатации (ТБ-015) — регламент ТО-орг-02 (за заказчиком).
- 👤 Read-only учётка БД СКИД `iscai_ro` (GRANT SELECT на users/departments) — создаёт администратор
  СКИД; секрет подключения — `Database:Passwords:Skid` (user-secrets/env, обязателен явно).

## Критерии приёмки
- Без допуска retrieval не выполняется (fail-closed) — покрыто `ClearanceAccessReaderTests` +
  существующими GATE-тестами; отзыв допуска действует немедленно — интеграционные тесты проходят.
- ✅ **Проверено вживую** (не только автотестами) на реальном контуре 2026-07-21: вход по учётке СКИД →
  без допуска — `AccessContextRequiredException` (fail-closed сработал, как задумано) → допуск выдан
  SQL-скриптом в `core.clearance` (см. этот файл выше) → повторный вход → Поиск по НПА нашёл документы.
  Сквозной путь «СКИД → допуск → фильтрованный retrieval» подтверждён целиком, не только по частям.
- Переиспользованный логин во внешней системе не наследует чужой допуск — `LoginServiceTests`.
