## Зачем

После инвентаризации остатка Core с адверсариальной проверкой (реально ли открыт / это код / это ядро) из
всех кандидатов «незакрытого» подтвердились как **ядро + код + реально открыто** ровно три пункта. Остальные
отсеяны с обоснованием (см. ниже «Сознательно НЕ делали»). Эта задача закрывает подтверждённые три.

## Что сделано

### 1. Управляемая деградация при недоступности модели (ТН-003/ТНД-001)
`ModelUnavailableException` (от `ModelCallResilience`) уже не роняла circuit — её глотал общий
`catch (Exception)` в `ExceptionHandlingBehavior` и показывал как обезличенную «Внутренняя ошибка», неотличимо
от дефекта. Это нарушало инвариант самого класса (ловить ОТДЕЛЬНО, показать понятное сообщение) и букву ТН-003.

- `ResponseStatusCode` (Abstractions) — добавлен член `ServiceUnavailable` (внешняя зависимость временно
  недоступна — управляемая деградация, не дефект приложения).
- `ExceptionHandlingBehavior` (Web-хост) — `catch (ModelUnavailableException)` ПЕРЕД общим catch: честный
  ответ «Сервер модели временно недоступен. Повторите попытку позже.» со `StatusCode = ServiceUnavailable` и
  логом уровня Warning (`BehaviorLog.ModelUnavailable`), а не Error — это ожидаемое временное состояние.
- Профилю дописывать не нужно: UI Генератора и Поиска по НПА уже рендерят `response.StatusMessage`.
- Место правок — ЯДРО (Abstractions + Web-хост), поэтому деградация работает для любого ИИ-сценария любого
  профиля через единую внешнюю точку конвейера. Правило зависимостей не нарушено.
- Тесты: `ExceptionHandlingBehaviorTests` (деградация → ServiceUnavailable + честный текст; прочее →
  InternalServerError; валидация → ValidationError; успех — насквозь).

### 2. Стриминговый путь модели больше не «голый passthrough» (ТН-003, прочёс кода)
Прочёс нашёл: `ResilientChatClient.GetStreamingResponseAsync` шёл напрямую в inner-клиент — без таймаута,
circuit breaker и учёта сбоя, — при этом комментарии в коде уверяли обратное («стримить ещё не умеет» /
«каждый клиент обёрнут таймаутом и circuit breaker»). Пока латентно (UI не стримит), но код и доки
противоречили друг другу, и защита включилась бы «сама» только после подключения стриминга к UI.

- `ModelCallResilience.ExecuteStreamingAsync` — новый потоковый путь: circuit breaker на старте (как у
  блокирующего) + **таймаут БЕЗДЕЙСТВИЯ между чанками** (сервер «завис» и не отдаёт очередной токен) + учёт
  сбоя в circuit breaker. Ошибка/таймаут потока → типизированный `ModelUnavailableException`; отмена самим
  вызывающим — как есть. **Повтора здесь НЕТ** осознанно: часть токенов уже могла уйти наружу, безопасно
  перезапустить поток нельзя (возобновление частично отданного потока — отдельная семантика).
- Учёт сбоя вынесен в общий `RegisterFailure()` (DRY с блокирующим путём).
- `ResilientChatClient` теперь маршрутизирует стриминг через resilience; комментарии в `ResilientChatClient`
  и `CoreAiModelsServiceCollectionExtensions` приведены в соответствие реальности.
- Тесты: `ModelCallResilienceTests` (+5): поток насквозь; отказ при открытом circuit ДО сервера; сбой посреди
  потока → `ModelUnavailableException` (отданные чанки сохранены); отмена вызывающим не оборачивается;
  таймаут бездействия → `ModelUnavailableException`.

### 3. Удалён мёртвый `Scriban` из `ISC.AI.Documents` (ТО-лнг-03, хвост)
Пакет был подключён в `ISC.AI.Documents.csproj`, но не использовался ни одним `.cs` (экспорт .docx — целиком
на `DocumentFormat.OpenXml`). Ссылка удалена, комментарий-интент про «связывание шаблонов» убран. Версия
Scriban остаётся в CPM для реальных потребителей (`ISC.AI.AI`, `Inspector.Application`) — удаление безопасно.

## Сознательно НЕ делали (и почему — не забывчивость)

Проверено адверсариально, вердикты приложены:
- **ТНД-005 (redelivery очереди индексации)** → `PREMATURE`. Очередь `ChannelBackgroundTaskQueue` не
  подключена ни к одному производителю (`EnqueueAsync` только в юнит-тестах). Redelivery для очереди, которую
  никто не наполняет, делать бессмысленно — сначала нужен реальный продюсер (оркестратор индексации).
- **IndexingJobEntity / IndexingJobStatus** (нашёл прочёс) — мёртвая схема того же незапущенного
  async-индексинга: сущность + enum + конфиг + DbSet + миграции есть, но НИКТО не создаёт задание (ingestion
  синхронный). Вырывать = миграция и риск; тесно связано с тем же отсутствующим продюсером. Держим до его
  появления.
- **ТО-прог-01 (подключить стриминг к UI)** → `PROFILE_OR_UI`. Ядро закрыто (Э4-24 + эта задача усилила
  потоковый путь); остаток — сценарий `IStreamRequest` + `Generator.razor` целиком в профиле
  (`Inspector.Application` + `Inspector.UI`), не в Core.
- **ТО-инф-06 (ADR границы схем)** → `NON_CODE`. Правило (без FK через границу, ссылки по значению) в коде
  соблюдается; остаток — консолидировать в отдельный ADR-0010 (документ), правок кода не требует.

## Границы

- Стриминговая resilience протестирована синтетически (fake-потоки: успех, обрыв, отмена, таймаут
  бездействия). Поведение на реальном сервере инференса — на стенде; но путь UI ещё не подключён (ТО-прог-01,
  профиль), так что в проде стриминг пока не активен.
- `ErrorBoundary` в оболочке хоста НЕ добавлял: типизированная деградация уже даёт пользователю честный ответ
  через штатный конверт, а `ErrorBoundary` — это подстраховка на НЕобработанные исключения рендера, отдельный
  UI-вопрос (при желании — оболочка `MainLayout`, тривиально).
