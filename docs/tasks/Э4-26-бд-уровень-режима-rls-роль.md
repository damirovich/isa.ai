## Почему один эпик, а не два пункта

ТБ-020 и ТБ-031 — по сути одно требование: **enforcement режима на стороне БД под не-суперпользовательской
ролью**. Разделять их нельзя:

- **ТБ-020** требует, чтобы решётка грифа/подразделения применялась к хранилищу эмбеддингов «при ЛЮБОМ
  обращении, а не только через штатный retriever», с обязательным GATE-1 тестом прямого доступа к таблице.
  Сейчас фильтр живёт ТОЛЬКО в коде `PgVectorRetriever` (application-side `.Where`); прямой `SELECT` в обход
  ретривера отдаёт всё.
- **ТБ-031** требует, чтобы приложение НЕ работало под суперпользователем (сейчас — `Username=postgres`), а
  append-only аудит держался ролью без прав UPDATE/DELETE + триггером.
- **Связка:** PostgreSQL RLS **не действует на суперпользователя** (даже с `FORCE ROW LEVEL SECURITY`).
  Значит DB-side enforcement ТБ-020 «укусит» только когда приложение переведут на ограниченную роль — а это
  и есть ТБ-031. Реализовывать порознь бессмысленно.

## Почему отложено на Э1 (а не «недоделано»)

- **ADR-0007 прямо откладывает выбор стратегии на Э1.** Дословно: статус «Предложено (решение на Э1)»;
  «окончательная стратегия (pre-filter, либо раздельные индексы/коллекции по грифу, либо их сочетание)
  выбирается и фиксируется на рабочем этапе Э1 по результатам теста полноты/утечки на фактической
  конфигурации и объёме корпуса». Реализовать RLS сейчас = закоммитить архитектурное решение раньше срока.
- **Требует инфраструктуры, которой нет:** ограниченная роль БД провижинится администратором (аналог
  `iscai_ro` для СКИД, ADR-0016), реальный корпус для теста полноты/recall — тоже Э1.
- **Полное закрытие — предусловие режим-гейта ТБ-063** (обработка реальных ДСП), до которого только
  тестовые/обезличенные данные — острой утечки сегодня нет.

## Предлагаемый подход (к проработке на Э1)

Базовая стратегия ADR-0007 — **pre-filter на стороне БД**, реализуемый как RLS:

1. **Ограниченная роль приложения** (`iscai_app`, не суперпользователь): SELECT/INSERT на корпус, БЕЗ
   UPDATE/DELETE на `core.audit_record` (ТБ-031), с `FORCE ROW LEVEL SECURITY`.
2. **RLS-политики** на `core.embedding` / `core.chunk` / `core.document`: `USING (classification <=
   current_setting('isc.max_classification')::int AND division_id = ANY(...))` — допуск берётся из
   session-переменных (GUC), которые ставит приложение на КАЖДУЮ операцию из `AccessContext`.
3. **Проброс допуска в сессию БД:** перехватчик `DbConnection`/`DbCommand` в `CoreDbContext` (или явный
   `SET LOCAL` в транзакции), читающий текущий `AccessContext`. Без установленного допуска — fail-closed
   (пустая выдача / отказ), не «всё».
4. **Application-side фильтр `PgVectorRetriever` СОХРАНИТЬ** как defense-in-depth (belt-and-suspenders).
5. **GATE-1 тест прямого доступа** (обязательная подпроверка, docs/09 §GATE-1): в Testcontainers создать
   ограниченную роль, применить RLS, выставить GUC на лимитированный допуск, выполнить СЫРОЙ `SELECT` к
   `core.embedding` в обход ретривера — убедиться, что строки выше допуска НЕ возвращаются. Именно этого
   теста сейчас нет.

Альтернативы для рассмотрения на Э1 (ADR-0007): раздельные индексы/коллекции по грифу; сочетание. Выбор —
по результатам теста полноты/утечки на реальном корпусе.

## Что уже готово (опора)

- Гриф/подразделение ДЕНОРМАЛИЗОВАНЫ на `embedding`/`chunk`/`document` и проиндексированы — RLS-политикам
  есть на что опираться, без джойнов.
- `PgVectorRetriever` уже применяет floor доступа (`BaselineAccess.Filter`) + профильную `IAccessPolicy`
  на стороне БД как pre-filter — application-side половина ТБ-020 закрыта, не хватает DB-side «при любом
  обращении» под ограниченной ролью.
- Хеш-цепочка аудита (append-only) + триггер — есть; не хватает роли без UPDATE/DELETE (ТБ-031).

## Критерии приёмки (на Э1)

- ⏳ Стратегия зафиксирована в ADR-0007 (перевод статуса в «Принято») по результатам теста полноты/утечки.
- ⏳ Приложение работает под не-суперпользовательской ролью; провижининг роли задокументирован для DBA.
- ⏳ RLS (или выбранная стратегия) enforced на уровне БД; допуск пробрасывается из `AccessContext`.
- ⏳ GATE-1 тест прямого доступа к таблице эмбеддингов — зелёный (сырой SELECT под ограниченной ролью не
  отдаёт строки выше допуска).
- ⏳ Роль БД без прав UPDATE/DELETE на `core.audit_record` (ТБ-031); проверено тестом.
