## Проблема
Инфраструктура аудита полная (хеш-цепочка, append-only триггер). Но:
- Сценарии **загрузки корпуса** (`IngestFileCommand`, `ImportBundleCommand`) **не пишут аудит**; `AuditAction.Ingest` нигде не используется → загрузка материалов (в т.ч. с грифом) проходит **мимо журнала** (нарушение ТБ-030).
- Нет **сквозного `AuditBehavior`**: каждый новый сценарий должен помнить ручной вызов `IAuditWriter` (Search/Generate/Export пишут, загрузка — нет). Системный риск.
- `SubjectId` не проставляется (анонимные записи до Э3-08).

## Цель
Сделать аудит **поведением по умолчанию** для всех обращающихся/генерирующих сценариев и закрыть дыру с загрузкой.

## Что сделано
- ✅ Маркер `IAuditableRequest` (Action + опц. `AuditSummary`) в `Abstractions.Audit`.
- ✅ Сквозное `AuditBehavior<TMessage,TResponse>` в **ядре** (`ISC.AI.AI/Audit`), `where TMessage : IAuditableRequest`; пишет `AuditEntry` через `IAuditWriter` после хендлера. Регистрация в хосте: `Exception → Audit → Logging → Validation → Grounding → handler`.
- ✅ **Централизация**: ручной аудит УБРАН из `SearchNpaQuery`/`ExportReferenceCommand` (был), помечены все 5: Generate/Search/Export/Ingest(файл)/Ingest(пакет). Дыра с загрузкой корпуса закрыта.
- ✅ Тесты: `AuditBehaviorTests` (успех / ошибка хендлера всё равно аудируется / fail-open при сбое журнала) + обновлены `SearchNpaHandlerTests`/`ExportReferenceHandlerTests`. Сборка 0/0; юнит 89/89.

## Зафиксированные решения (после состязательной проверки)
- **Generate НЕ помечен** `IAuditableRequest`: его аудит пишет RAG-оркестратор ядра (`GroundedGenerator`) с ТОЧНЫМ грифом (=max грифов фрагментов), id фрагментов и payload запрос/ответ. Маркер на команде дал бы ДВОЙНУЮ запись — снят (критичная находка ревью).
- **Гриф записи = `max(допуск субъекта, объявленный гриф объекта)`** (`IAuditableRequest.AuditClassification`). Для Ingest/Export объявленный гриф документа может быть ВЫШЕ допуска оператора — так запись журнала никогда не недо-классифицируется относительно данных.
- **Нет контекста доступа ⇒ МАКСИМАЛЬНЫЙ гриф** (`short.MaxValue`), не 0 — чтобы чувствительное содержимое не попало под нижнюю решётку (fail-closed по грифу; было ошибочно 0 — major-находка).
- **FAIL-CLOSED**: сбой записи журнала ПРОБРАСЫВАЕТСЯ (ExceptionHandlingBehavior → неуспешный ответ), результат пользователю не выдаётся — «нет записи, нет выдачи» (инвариант №4). ⚠️ **Режимное решение** — при необходимости смягчить до fail-open согласует владелец режима.
- **Отменённое обращение аудируется** (данные могли быть уже извлечены) — фиксация попытки.
- `SubjectId` анонимен до Э3-08 (аутентификация).

## Осталось (минорные находки ревью — отдельными шагами)
- **Login/View/Print** (§5.1.6.15) объявлены в `AuditAction`, но команд ещё нет — пометить `IAuditableRequest` при их появлении (связано с Э3-08). Опц. арх-тест «обращающиеся к корпусу/модели команды реализуют `IAuditableRequest`».
- **Полное разделение метаданных и содержимого (ТБ-032)**: сейчас `PayloadSensitive` в той же строке и в хеше цепочки, из-за чего обезличивание по срокам (ТБ-043/064) рвёт цепочку. Правильно — вынести payload в отдельное хранилище под своей решёткой, в хеш класть только его криптохеш. Отдельная задача по `AuditWriter`.
- Аудит запросов, отклонённых валидацией, — оставлен намеренно (журнал всех попыток обращения).

## Критерии приёмки
- ✅ Загрузка корпуса фиксируется в неизменяемом журнале (ТБ-030).
- ✅ Новый сценарий получает аудит одним маркером — без ручного вызова.
