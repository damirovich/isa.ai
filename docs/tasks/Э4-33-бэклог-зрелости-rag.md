Пункты, найденные оценкой, но **сознательно не взятые сразу** (в отличие от [Э4-31](Э4-31-упрочнение-llm-ядра.md),
где закрыты 4 критичных). Каждый — с честной оценкой важности для ЭТОГО класса систем.

## Ingest / extraction
- **PDF-извлечение текста** (major). `CompositeTextExtractor` знает `.docx/.txt/изображения`, но не `.pdf` —
  а для гос-корпуса НПА PDF доминирует. Ручная загрузка файлом PDF-слепа (импорт из сборщика берёт уже
  извлечённый текст). Нужен PDF-экстрактор (+ растеризация скан-PDF в изображения для OCR, см. Э4-29). Проверить
  лицензию библиотеки (MIT/Apache).
- **Чанкинг с перекрытием (overlap)** (minor). `SimpleTextChunker`/`NpaStructuralChunker` режут без sliding-window
  overlap → факт на границе чанка может не попасть целиком ни в один фрагмент. Структурный чанкер по «Статья N»
  частично снимает риск для НПА; уязвим фолбэк и не-НПА документы.

## Retrieval / качество
- **Шов реранкера** (minor). Извлечение одностадийное (ANN top-K по косинусу). Нет контракта `IReranker` и точки,
  куда вставить cross-encoder rerank/MMR без правки ядра. Реранкер поднял бы precision@k (особенно для юридических
  формулировок и кросс-язычного ru/ky), но требует ещё одной модели (VRAM) — разумно отложить, но шов стоит завести.
- **Версионирование модели эмбеддингов** (minor). `EmbeddingEntity.ModelKey` пишется КОНСТАНТОЙ (имя роли), а
  ретривер НЕ фильтрует по `ModelKey`. При смене эмбеддера старые и новые векторы сравнивались бы как одно →
  тихая порча ранжирования до полной переиндексации. Нужен реальный ключ версии + фильтр в retrieval.

## Эксплуатация
- **Асинхронная индексация** (major, связан с ТНД-005 / [Э4-20](Э4-20-очередь-фоновых-задач.md)). `IngestAsync`
  генерирует эмбеддинги СИНХРОННО inline в запросе; `IndexingJobEntity`/`DbSet` существует, но НИГДЕ не создаётся
  (мёртвый скелет). Для корпуса 170К+ импорт блокирует вызывающего, без прогресса/возобновления/батчинга.
  Инфраструктура фоновых задач в ядре есть, но конвейер индексации её не использует. **Требует продюсера** (см.
  ТНД-005 — сейчас PREMATURE); при подключении — либо оживить `IndexingJob`, либо убрать мёртвый скелет.
- **Наблюдаемость RAG-пути** (minor). Ни `ILogger`, ни `ActivitySource/Meter` в `IngestionPort`/`PgVectorRetriever`/
  `GroundedGenerator`/экстракторах. `ChatResponse.Usage` (токены/латентность) не читается. Аудит закрывает комплаенс
  (кто/что/когда), но не операционную телеметрию (задержки, доля Unverified-грунтовок, частота circuit-breaker).
  Для изолированного контура без внешнего APM это ограничивает диагностику. (Частично начато в Э4-31 — лог усечения.)

## Guardrails / вывод
- **Изоляция инструкций из контента** (minor, defense-in-depth). Фрагменты (в т.ч. из пакетов «от недоверенного
  производителя», ТБ-001) вставляются в user-сообщение без делимитации/экранирования — теоретический
  prompt-injection через НПА-документ. Ущерб ограничен инвариантом грунтовки (сфабрикованная ссылка → Unverified)
  и системным правилом первым, поэтому не major; как defense-in-depth — явная разметка/экранирование содержимого.
- **Структурированный вывод (JSON-schema)** (nice-to-have, forward-looking). Цитаты извлекаются регэкспом по
  свободному тексту. Будущие модули (анализ/сверка, риски, извлечение нарушений) выиграли бы от schema-constrained
  JSON; сейчас для свободнотекстовой справки не критично.

## Функциональность (вне scope строгого one-shot)
- **Многоходовый диалог / память** (minor, продуктовое решение). Сценарии stateless single-shot; уточняющие
  вопросы невозможны. Для одноразовой справки допустимо (чище для аудита); при позиционировании как «ассистент»
  потребует расширения контракта `GroundedRequest` историей.
- **Faithfulness-evals** (minor). `ISC.AI.Evals` покрывает только retrieval recall@k раздельно по языку. Нет
  автоматической оценки доли Confirmed/Unverified грунтовки и качества генерации. Пороги/прогон ждут Э1.
