# Требования из UI-прототипов заказчика vs возможности Core

Источник: 6 экранов профиля «ИнспекторAI» (Дашборд, Методики проверок, Генератор, Риски и внутренний
контроль, Мониторинг нарушений, Анализ и сравнение), воссозданных по скриншотам прототипа, присланным
заказчиком. Анализ — 10 параллельных агентов (по экрану + по области Core: Abstractions / ISC.AI.AI /
Persistence+Documents+Ingestion), затем один агент-архитектор свёл результаты. Только чтение кода, без
изменений.

## Итог одной фразой

Core уже закрывает почти весь ИИ/доступ/аудит-конвейер как по-настоящему нейтральный, переиспользуемый слой —
но вся «бизнес-начинка» самих экранов прототипа (проверки, реальные сигналы риска, программы, находки
анализа) существует пока только как демо-константы или логика прямо в `@code` Blazor-страниц. Это не 6
разных недоделок, а один системный разрыв: между «конвейер генерации готов» и «сущности, которые он должен
обрабатывать, ещё не созданы».

## Что Core уже реально покрывает (строить заново не нужно)

| Требование экрана | Чем закрыто в Core |
|---|---|
| Retrieval с фильтром доступа → модель → грунтовка → HITL-черновик | `PgVectorRetriever` + `GroundedGenerator` + `GroundingValidator` + `GroundingPrompt.SystemRule` — весь путь end-to-end, профиль не может обойти |
| Итоговый гриф результата = максимум грифов использованных фрагментов | `GroundedGenerator` считает сам |
| Экспорт .docx с обязательной маркировкой грифа | `DocxDocumentExporter` (ТБ-033) |
| Каждый генерирующий вызов — в неизменяемый аудит | `IAuditWriter`/`AuditWriter` (hash-chain) + `AuditBehavior<TMessage,TResponse>` |
| Пользователю не выдаются фрагменты выше допуска, гриф не смешивается | `BaselineAccess.Filter<T>` — fail-closed SQL pre-filter, профиль не отключает |
| Air-gap — только локальная модель | `CoreAiModelsServiceCollectionExtensions` — keyed `IChatClient`/`IEmbeddingGenerator` только по конфигу |
| Долгая генерация не блокирует UI, переживает рестарт | `ChannelBackgroundTaskQueue`/`BackgroundTaskRunner`/`BackgroundTaskWorker` |
| Новый модуль регистрируется без правки ядра | `IModule`/`IProfile` — уже профиле-нейтрально |

## Разрывы, которые блокируют MVP

1. **Сущности «Проверка» (Check) нет вообще** — ни в Core, ни в профиле. Счётчик «Всего проверок» и
   «Последние проверки» на Дашборде — захардкоженные демо-числа.
2. **`RiskScoreCalculator` реализован и покрыт тестами, но ничем не запитан.** Нет сборщика `RiskSignals` из
   реальных `Violation`, нет истории для `TrendDelta`. Дашборд вообще не вызывает калькулятор, хотя в шапке
   файла заявлена «свёртка в цвет светофора».
3. **Нет персистентного объекта черновика генерации** (черновик → утверждён/отклонён, кем и когда). Сейчас
   результат `GenerateReferenceCommand` живёт только в памяти Blazor-компонента — нельзя посмотреть историю
   или повторно открыть черновик.
4. **Движок сравнения НПА (Анализ и сравнение) не реализован вообще** — ни вызова модели, ни промпта, ни
   сохранения находок. Кнопка «ИИ-анализ НПА» декоративна. Модуля «Архив» тоже нет.
5. **Нет UI/сущности подтверждения находки человеком** (принять/отклонить/редактировать) — при том что
   инвариант HITL прямо продекларирован текстом на экране Анализа.
6. **Методики проверок — плоские демо-record'ы**, без Id/статуса/структуры; счётчик пунктов чек-листа
   фиктивный.
7. **`IAccessContextProvider` — dev-заглушка** (Э3-08, уже известный P0 в бэклоге). Пока не заменена реальной
   аутентификацией, фильтр доступа на всех экранах декоративен, что бы ни показывал UI.

## Разрывы «нужно скоро» / «можно отложить»

- Нет `Violation.ResolvedAt` и персистентного `RemediationDeadline` — «скорость устранения» и корректная
  просрочка физически не считаются.
- Нет истории отметок хода устранения (`RemediationUpdate`) — хранится только последнее состояние.
- **OCR не реализован**: пакет Tesseract подключён в `.csproj`, но ни один класс его не использует — сканы
  старых приказов извлекать нечем.
- **Scriban подключён (и в `ISC.AI.AI`, и в `ISC.AI.Documents`), но нигде не используется** — промпты всё ещё
  хардкод-строки в C#, что прямо противоречит собственной конвенции CLAUDE.md «промпты — файлы-шаблоны».
- Нет справочника сотрудников (ФИО/должность) для атрибуции «кто утвердил отчёт» — только техническая учётка
  доступа.
- Интеграция со СКИД (поручения/сроки/справочник подразделений) — пока только комментарии-намерения.
- Устойчивость к сбою сервера инференса (retry/timeout) и стриминг длинных ответов — оба заявлены конвенцией,
  ни один не реализован в `GroundedGenerator`.

## Что лежит не на своём месте

Это самое важное для тебя как для архитектора решение, а не просто список нехваток:

1. **Вся агрегационная логика (счётчики, `AverageProgress`, `CountOf`, группировки) сидит в `@code`
   Blazor-страниц**, а не в Mediator-запросах `Inspector.Application`. Это системно — Дашборд, Мониторинг,
   Анализ, Методики одинаково. Прямое нарушение собственной конвенции CLAUDE.md («обработчики — в
   `*.Application`, команды/запросы — через Mediator») и практическая проблема: пока логики нет за
   Mediator-сообщением, сквозные `AuditBehavior`/`GroundingBehavior` физически не могут на неё сработать.
2. **Реестр типов документов Генератора — статический массив прямо в `@code`** UI-компонента. Это и граница
   профиль/ядро нарушена (бизнес-конфигурация в UI-слое), и повтор той же проблемы с промптами не как
   файлами.
3. **Две независимые точки записи аудита**: `AuditBehavior` (по `IAuditableRequest`) и прямая запись внутри
   `GroundedGenerator.GenerateAsync`. Для `GenerateReferenceCommand` (который одновременно и то, и другое) это
   значит **две отдельные записи в неизменяемый журнал** без задокументированного правила их соотношения —
   при росте числа генерирующих сценариев (программы, отчёты, находки анализа) проблема будет расти
   количественно.
4. **Персистентный workflow черновика** (Draft/Approved/Rejected) — с моей точки зрения его стоит сразу
   спроектировать в Core как generic-объект (Id, RequestType, DraftText, Citations, ResultClassification,
   Status, ReviewedBy/At), а не позволять четырём экранам профиля (справка/программа/отчёт/находка анализа)
   независимо изобретать четыре похожих таблицы.
5. **Движок сравнения документов** для «Анализа и сравнения» — по своей природе домен-нейтрален (сравнить
   набор текстов через RAG+грунтовку и вернуть типизированные находки; таксономия находок и профильная
   обвязка остаются в профиле). Если его один раз захардкодить в `Inspector.Application`, второй профиль
   (ERP, ему тоже придётся связывать документы) будет вынужден копировать, а не переиспользовать — тот же
   риск, что чуть не произошёл с `RiskScoreCalculator`.

## Рекомендации по порядку

1. Прежде чем добавлять новые сущности — вынести агрегационную логику экранов из `@code` в Mediator-запросы
   `Inspector.Application` по CQRS-lite конвенции. Это предпосылка для того, чтобы аудит/грунтовка вообще
   могли сработать на этих экранах.
2. **Не** выносить в Core `RiskScoreCalculator`, иерархию `Division` — по правилу проекта («ядро никогда не
   ссылается на профиль», «сначала скелет, затем по одному модулю») такой вынос оправдан только когда второй
   профиль (ERP) подтвердит идентичную потребность.
3. **Исключение** — персистентный workflow черновика и движок сравнения документов разумнее сразу
   спроектировать в Core, потому что они строятся с нуля впервые: иначе профиль неизбежно захардкодит их под
   себя, и переносить придётся не «вынос», а «переписывание».
4. Реализовать сборщик реальных `RiskSignals` из `Violation` (+ заглушку для СКИД-сигналов) и минимальный
   `RiskSnapshot` для тренда — самая дешёвая и самая ценная доработка, поскольку сам калькулятор уже готов и
   протестирован.
5. Добавить в `Inspector.Domain` (без участия ядра): `Check`, `Violation.ResolvedAt`, персистентный
   `RemediationDeadline`, `RemediationUpdate`, `Division.Kind` (ТУ/линейное).
6. Для Методик и Анализа переиспользовать паттерн `GenerateReferenceCommand → IGroundedGenerator`, подключив
   реальные Scriban-шаблоны, а не изобретать генерацию заново.
7. Отдельным треком закрыть три инфраструктурных гэпа ядра, которые тормозят качество ВСЕХ генерирующих
   сценариев одинаково: подключить Scriban по-настоящему, реализовать OCR-экстрактор, довести
   `IAccessContextProvider` до продакшн-реализации (Э3-08, уже P0 в бэклоге).
8. Разрешить архитектурное решение по двум путям аудита явным документом/правилом — до того как число
   grounded-сценариев профиля вырастет с одного до пяти.
9. Модуль «Архив» сознательно отложить последним — он зависит и от OCR, и от решения по хранилищу документов
   с версионированием.
