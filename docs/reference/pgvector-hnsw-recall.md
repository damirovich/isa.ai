# pgvector / HNSW: полнота поиска и обязательные параметры

> Справочник по инциденту 26.08.2026 и его последствиям для эксплуатации. Аудитория —
> администратор БД и разработчики ядра. Связанные требования: ТБ-022 (индексация/поиск),
> ТО-мат-04 (ранжирование конфигурацией), КИ-03 (метрики качества поиска).

## Инцидент: индекс «не видит» существующий документ

**Симптом.** Загруженный документ не находится семантическим поиском (чат «По документам»,
Генератор), хотя присутствует в корпусе с корректными грифом/подразделением. Точный скан
(`ORDER BY embedding <=> :q` без индекса) находит его первым; HNSW-индексный скан по тому же
вектору запроса не возвращает его вовсе.

**Диагноз.** Малый семантический «остров»: группа из нескольких документов, непохожих на
основной корпус (в инциденте — 4 тестовых документа среди ~12 тыс. юридических фрагментов).
При сборке графа HNSW с параметрами по умолчанию (`m=16, ef_construction=64`) отбор соседей
отсекает связи острова с основным графом, и жадный поиск с внешним вектором запроса до острова
не добирается. Воспроизведено на чистой копии данных.

**Что причиной НЕ является** (проверено экспериментально): REINDEX и пересоздание индекса с
теми же параметрами; параллельная сборка; нехватка `maintenance_work_mem`; дубликаты векторов
(в корпусе — 51 из 11 868); версия расширения (0.8.3, самопроверка вектором из таблицы и
контрольные пробы работают корректно).

## Рабочая конфигурация (доказана пробами)

Работает только **пара** настроек — по отдельности каждая из них остров не возвращает:

| Этап | Параметр | Значение | Где задаётся |
|---|---|---|---|
| Сборка индекса | `ef_construction` | **512** (дефолт 64) | Миграция `HnswIslandRecall`; `EmbeddingEntityConfiguration` |
| Сборка индекса | `m` | 16 (дефолт, зафиксирован явно) | там же |
| Поиск | `hnsw.ef_search` | **200** (дефолт 40) | `PgVectorRetriever` выставляет `SET LOCAL` на каждую поисковую транзакцию; конфиг `Retrieval:HnswEfSearch` |

Контрольная точка инцидента: с этой парой индексный топ-5 совпал с точным полностью (4/4
островных документа, верный порядок); с дефолтами остров не находился даже при `ef_search=1000`.

## Контрольная проба полноты (после массовой загрузки и миграций индекса)

Сравнить точный и индексный топ **одним и тем же** вектором запроса (вектор эмбеддера
недетерминирован между вызовами — получать один раз). Запросы для пробы: 2–3 типовых
предметных + 1 «редкий» (по свежезагруженному нетипичному документу).

```sql
BEGIN;
SET LOCAL enable_indexscan = off;   -- эталон: точный скан
SELECT chunk_id, embedding <=> :qvec AS d FROM core.embedding ORDER BY d LIMIT 5;
COMMIT;

SET LOCAL hnsw.ef_search = 200;     -- боевой режим (в транзакции)
SELECT chunk_id, embedding <=> :qvec AS d FROM core.embedding ORDER BY d LIMIT 5;
```

Критерий: пересечение топ-5 ≥ 4 и совпадение топ-1. Провал — снять индекс до разбирательства
(система остаётся корректной на точном скане; на ~12 тыс. векторов это ~80 мс).

## Масштаб продакшена (~209 тыс. НПА + документы инспекции)

- Ожидаемый порядок: миллионы векторов dim 768 (≈3 КБ/вектор). Точный скан на таком объёме
  непригоден (секунды и хуже) — индекс обязателен, отсюда обязательность пары параметров выше.
- **Сборка на большом корпусе**: поднять `maintenance_work_mem` так, чтобы граф влез в память
  (порядок: ~15–30 ГБ на 5 млн векторов dim 768); признак нехватки — NOTICE
  `hnsw graph no longer fits in maintenance_work_mem` и замедление сборки на порядки.
  `max_parallel_maintenance_workers` ≈ CPU/2. `ef_construction=512` удорожает сборку ~в 4 раза
  против дефолта (на 12 тыс. векторов: 5,7 с против 1,4 с) — закладывать окно на массовую загрузку.
- **RAM СУБД**: индекс должен помещаться в память (правило: RAM ≥ 2× размера индекса; ориентир —
  ~19–20 ГБ индекса на 10 млн векторов dim 768). При росте за пределы RAM — вариант `halfvec`
  (fp16, pgvector 0.7+): −50 % хранения и индекса, потеря recall < 1 % на нормированных векторах.
- **Версия pgvector**: минимум 0.8.4 (в 0.8.3 — ложная ошибка `hnsw graph not repaired` при
  VACUUM, issue #993). Известная незакрытая на 0.8.6 гонка INSERT+VACUUM (PR #1010) со временем
  деградирует recall живого индекса — после эпизодов массовой доливки с одновременным VACUUM
  выполнять REINDEX и контрольную пробу; следить за выходом версии с фиксом.

## Состояние на 26.08.2026

На дев-сервере (10.10.0.115, PostgreSQL 18.6, pgvector 0.8.3) слепой индекс снят вручную в ходе
инцидента — поиск идёт точным сканом и корректен. Миграция `HnswIslandRecall` создаёт индекс с
рабочими параметрами (`DROP INDEX IF EXISTS` учитывает ручное снятие); ретривер выставляет
`hnsw.ef_search` из конфигурации с дефолтом 200. После накатки миграции выполнить контрольную
пробу полноты.
