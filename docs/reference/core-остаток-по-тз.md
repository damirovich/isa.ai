## Найдено при чтении кода — прямые нарушения формулировок ТЗ, ещё нигде не заведено как задача

Это новое: агенты построчно прочитали весь `src/core` и нашли места, где **код прямо расходится с уже
согласованным текстом ТЗ**, а не просто «недоделано».

| Требование ТЗ | Что там написано дословно | Что в коде |
|---|---|---|
| **ТО-лнг-03** | «Промпты хранятся файлами-шаблонами... загружаются через провайдер промптов, подставляются шаблонизатором» | Пакет **Scriban подключён в двух проектах ядра (`ISC.AI.AI`, `ISC.AI.Documents`), но ни один файл его не использует.** `GroundingPrompt.SystemRule` — хардкод-константа C#. Прямое расхождение с текстом ТЗ, не домысел. |
| **ТО-мат-04** | «Ранжирование результатов и пороги отсечения по релевантности задаются конфигурацией» | `PgVectorRetriever` **не применяет порог similarity/distance** — всегда отдаёт top-K, даже если ни один фрагмент не релевантен. Отсева нет вообще, не то что не конфигурируем. |
| **ТБ-064** | «Процедура гарантированного удаления документа и всех его производных (чанки, эмбеддинги, журнал промптов...)» | Такого сценария в `Persistence`/`Ingestion` нет. Есть мягкое удаление (`IsDeleted`) через `AuditedDbContext`, но не полное каскадное удаление по требованию. |
| **ТН-003 / ТНД-001** | «Управляемая деградация... сбой одного фонового процесса не должен приводить к отказу интерактивной части» | Вокруг вызовов `IChatClient`/`IEmbeddingGenerator` в `GroundedGenerator` и `PgVectorRetriever` нет `retry`/`timeout`/circuit breaker — недоступность сервера инференса пробрасывается необработанным исключением прямо в UI. |
| **ТНД-005** | «Незавершённые задания индексации не теряются сверх RPO» при перезапуске | `ChannelBackgroundTaskQueue` персистит только **статус** задачи, сам делегат-работа живёт в памяти. После падения процесса «Running»-задачи помечаются `Failed`, а не переставляются в очередь — то есть настоящего redelivery нет. |
| **ТО-прог-01** (по смыслу — CLAUDE.md: «стримить через `IAsyncEnumerable`») | Длинные вызовы модели должны стримиться | `GroundedGenerator` вызывает блокирующий `GetResponseAsync`, а не `GetStreamingResponseAsync`, хотя doc-комментарий в `CoreAiModelsServiceCollectionExtensions` сам утверждает про стриминг. |
| **ТБ-030/032** (косвенно) | «Ведётся полный неизменяемый журнал... кто/что/когда» без задвоения | На один вызов `GenerateReferenceCommand` пишутся **две отдельные записи аудита**: `AuditBehavior` (по `IAuditableRequest`) и прямая запись внутри `GroundedGenerator.GenerateAsync`. Не факт, что это баг, но нигде не задокументировано, что это осознанно. |
| ПОДГ-02 (OCR сканов) | «Основной объём работ на старте — именно OCR, чистка и разметка» | Пакет **Tesseract подключён в `ISC.AI.Ingestion.csproj`, но ни один класс его не использует.** Извлечение текста поддерживает только `.docx`/`.txt` — сканы старых приказов индексировать нечем. |

## Формальные пункты ТЗ, которые не про код (заказчик/инфраструктура/регламент)

Это тоже часть «Core», но их не закрыть кодом — они по тексту ТЗ явно за заказчиком или требуют отдельного
организационного результата:

- **ТБ-061** — класс защищённости и обязательность сертификации СрЗИ/СКЗИ — запрос заказчику, помечен «👤» в
  README.
- **ТБ-043/ТБ-044** — защита промежуточных артефактов инференса (логи, KV-cache, своп GPU) и канала
  хост↔сервер инференса — конфигурация инфраструктуры, не код.
- **ТБ-051, ТБ-060, ТБ-062** — регламент переноса артефактов, резервное копирование с шифрованием, at-rest
  защита БД/хранилища — организационные регламенты (ТО-орг-02) и настройка окружения.
- **ТИ-001..003** — состав дистрибутива и офлайн-инсталлятор — не начато, естественно позже (ближе к Э5/Э6).
- **ТО-инф-06** — модель целостности на границе схем `core`/`inspector` должна быть зафиксирована ADR-ом; сам
  паттерн (без FK через границу, ссылки по значению) в коде соблюдается последовательно, но отдельного ADR-
  документа под этим конкретным пунктом я не нашёл — стоит проверить `docs/06_ADR/`.

## Что уже реально готово (для контраста, чтобы не читалось как «всё плохо»)

- `IRetriever`/`PgVectorRetriever` — фильтр доступа fail-closed на этапе retrieval (ТБ-020/021), в SQL, не
  обходится профилем.
- `GroundingValidator` + `GroundingPrompt.SystemRule` — грунтовка как контракт, а не опция (ТБ-040/041).
- `AuditWriter` — hash-chain, append-only на уровне БД-триггера (ТБ-031, сама механика).
- `IngestionPort` — fail-closed без грифа/подразделения, дедуп по SHA-256, версионирование через
  `SupersededByDocumentId`/`IsCurrent` (ТБ-024, ТО-инф-04/07).
- `DocxDocumentExporter` — маркировка грифа в теле и метаданных файла (ТБ-033).
- `ChannelBackgroundTaskQueue`/`BackgroundTaskWorker` — асинхронные ИИ-задачи с восстановлением осиротевших
  задач при рестарте (частично — см. ТНД-005 выше).
- `ISC.AI.Evals` — фреймворк для КИ-01..04 (`EvalRunner`, `RecallCalculator`, `LanguageRecall`) уже существует
  как проект, просто не прогонялся на реальном корпусе/моделях с порогами — пороги и сам прогон ждут Э1
  (согласование с заказчиком) и наполненного корпуса.

## Итог

Самый крупный рычаг — один: **Э3-08 (аутентификация)**. Пока `IAccessContextProvider` — заглушка, весь
режимный контроль (ТБ-010..023) формально не работает, даже там, где код по факту готов. После него по
влиянию на реальную приёмку — **три находки из таблицы «прямые нарушения ТЗ»**: отсутствие порога
релевантности (ТО-мат-04) и неиспользуемый Scriban (ТО-лнг-03) — потому что это не «мы ещё не дошли», а
код прямо расходится с уже согласованным текстом ТЗ, который заказчик увидит при сверке.
