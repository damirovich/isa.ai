## Контекст

До сих пор в репозитории жил один профиль, и хост знал его «тремя строками» (`ProjectReference`, `using`,
`new InspectorProfile()`). Профиль «Следствие» — второй полноценный профиль **в том же репозитории**, при
этом инвариант ТС-004 не меняется: в поставке ровно один профиль, «тумблера в рантайме» нет (решение
заказчика, ЕРП-01). Архитектурный тест `Host_references_exactly_one_profile` читает `ProjectReference`
хоста без учёта условий MSBuild — два условных `ProjectReference` без правки теста дали бы «два профиля».
Требование заказчика: «ИнспекторAI» не должен ломаться — по умолчанию всё собирается и работает как прежде.

## Решение

1. **Свойство MSBuild `IscProfile`** в `ISC.AI.Web.csproj`, по умолчанию `inspector`. `ProjectReference` на манифест профиля — в `ItemGroup` с условием по этому свойству; точка композиции — файл `Composition/<профиль>/HostProfile.cs`, компилируемый по тому же условию; в `Program.cs` — `var profile = HostProfile.Create();` и ноль `#if`.
2. **Сборка поставки «Следствие»**: `dotnet build -p:IscProfile=investigation` (или переменная окружения `IscProfile` — так переключается и Visual Studio). Перед возвратом к сборке по умолчанию — `dotnet clean src/core/ISC.AI.Web` (общий `obj/`, генератор Mediator собирает диспетчер по видимым сборкам).
3. **Арх-тест учитывает условие**: граф ссылок строится для заданного значения `IscProfile`, и тест «ровно один профиль» проверяется для **каждого** известного значения; отдельный тест закрепляет умолчание `inspector`. Прочие тесты — на графе по умолчанию.
4. **Данные**: у поставки «Следствие» **своя БД** (ADR-0006 — экземпляр на профиль): схемы `core`, `docflow`, `media`, `investigation`. На общей с Инспектором БД профиль не разворачивается — словари подразделений (`inspector.division` и `investigation.division`) разные, а `core.clearance.division_scope` один.
5. Что общее для обоих профилей и **не копируется**: ядро, документооборот, учётные записи/допуски/аудит ядра, `wwwroot` хоста (эмблемы лежат рядом, хост их не различает).

Отклонено: второй хост-проект (второй `Program.cs`, дубль композиции и конфигурации; в `src/core` считается ядром и ломает арх-тест); один `ProjectReference` с вычисляемым путём (тест проходит «случайно», по плейсхолдеру имени, и ничего не проверяет); переключение в рантайме (противоречит ТС-004).

## Последствия

- (+) Поставка Инспектора по умолчанию не меняется ни на строку поведения; профиль «Следствие» собирается из того же репозитория одним параметром.
- (+) Инвариант «ровно один профиль» стал проверяемым для всех вариантов сборки, а не для единственного.
- (−) Общий `obj/` хоста: при смене профиля нужен `clean`; CI собирает оба варианта отдельными шагами.
- (!) Обязательство: страницы «учётные записи / допуски / журнал аудита» сегодня живут в профиле Инспектора; для второго профиля они либо копируются (первый срез ЭС3), либо выносятся в пакет модулей «Администрирование платформы» (отдельная задача, единственная правка Инспектора).
