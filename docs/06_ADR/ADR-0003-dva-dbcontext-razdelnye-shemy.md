# ADR-0003. Два контекста данных (DbContext) в раздельных схемах

| | |
|---|---|
| **Документ** | ДОК-06 / ADR-0003 |
| **Система** | ISC.AI («ИнспекторAI») |
| **Версия** | 0.1 (черновик) |
| **Статус** | **Принято** |
| **Связь с ТЗ** | ТО-инф-01 (основное); ТО-инф-06, ТС-008, ТО-прог-08, ТС-003 |

## Контекст

Архитектура разделяет нейтральное ядро и сменный профиль (ADR-0002). Это разделение должно отражаться и в данных: универсальные таблицы движка (документы, чанки НПА, эмбеддинги, аудит, пользователи, задания индексации) принадлежат ядру и одинаковы для любого профиля, а доменные сущности (Проверка, Нарушение, Риск, Поручение) специфичны для профиля «Инспектор» (ТО-инф-05). Смешение их в одной модели данных нарушило бы границу ядро/профиль и помешало бы смене профиля без затрагивания ядра.

При этом обе группы данных живут в одной СУБД PostgreSQL (изолированный контур, единое резервное копирование), и между ними есть операции, требующие согласованности (например, доменная операция профиля + запись аудита ядра).

## Решение

Данные размещаются в **одной СУБД PostgreSQL в двух схемах** с двумя контекстами EF Core (ТО-инф-01):
- схема `core` — универсальные таблицы движка (документы, чанки НПА, эмбеддинги, аудит, пользователи, задания индексации);
- схема `inspector` — доменные сущности профиля.

Каждая схема имеет **собственную историю миграций**; порядок применения детерминирован — `core`, затем `inspector` (ТО-прог-08). Под Blazor Server каждый контекст создаётся через фабрику `IDbContextFactory` на операцию, а не как долгоживущий scoped-сервис (ТС-008). Оба контекста регистрируются профилем через манифест (ТС-006, см. ADR-0002).

Согласованность через границу схем: EF Core **не** создаёт внешних ключей между разными контекстами; модель целостности (единица работы, компенсация, проверка ссылок на уровне приложения) специфицируется отдельно. Кросс-контекстная атомарность (доменная операция + аудит) обеспечивается общим соединением и транзакцией там, где это необходимо (ТО-инф-06).

Отклонённые альтернативы: (а) единый DbContext на все таблицы — нарушает границу ядро/профиль, делает миграции профиля и ядра неразделимыми; (б) две отдельные базы данных — усложняет общие транзакции, резервное копирование и развёртывание в офлайн-контуре без выигрыша.

## Последствия

Положительные:
- Граница ядро/профиль воспроизводится на уровне данных; профиль можно сменить, не трогая схему `core` (поддержка ТС-003).
- Раздельные истории миграций: ядро и профиль эволюционируют независимо, откат предсказуем (ТО-прог-08, ТНД-004).
- Единая СУБД сохраняет простое резервное копирование и возможность общей транзакции для критичных кросс-контекстных операций.
- Фабрика контекстов соответствует модели конкурентности Blazor Server (ТС-008).

Отрицательные / обязательства:
- Отсутствие внешних ключей через границу схем перекладывает контроль целостности на уровень приложения — это **обязательство**, требующее отдельной проработки (ТО-инф-06; на Э1 выделяется в самостоятельную ADR по модели целостности контекстов).
- Кросс-контекстные транзакции требуют аккуратного управления общим соединением; ошибка ведёт к рассогласованию данных и аудита.
- Два контекста и две цепочки миграций повышают сложность сборки дистрибутива миграций (ТИ-001).

## Связь с ТЗ

- **ТО-инф-01** — одна СУБД PostgreSQL, две схемы (`core`, `inspector`), у каждой своя история миграций.
- **ТО-инф-06** — модель целостности на границе схем; отсутствие FK между контекстами; кросс-контекстная атомарность через общую транзакцию.
- **ТС-008** — контекст создаётся через фабрику на операцию (Blazor Server).
- **ТО-прог-08** — порядок применения миграций `core` → `inspector`, офлайн-регламент и откат.
- **ТС-003** — разделение данных отражает разделение ядра и профиля.
