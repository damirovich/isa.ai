## Контекст

После показа 05.11.2026 Заказчик попросил: (1) пункт меню «Помощь», где по каждому разделу описано, для чего он и что
нажимать; (2) возможность спрашивать у ИИ, как пользоваться системой, — чтобы ИИ отвечал, что нажать.

Справка — описание интерфейса, а не нормативный материал. Самый простой путь — загрузить её в корпус документом —
ломает назначение корпуса: Генератор, Анализ и сверка проекта ищут по всему доступному корпусу, нашли бы фрагменты
«Руководства пользователя» и сослались бы на них как на источник; валидатор грунтовки такую ссылку подтвердил бы —
фрагмент действительно найден. Исключить документ из общего поиска нечем: `RetrievalFilter` умеет только сузить
выдачу до списка документов, но не исключить. Кроме того, файл справки меняется с каждой поставкой, а корпус пришлось
бы переиндексировать отдельно.

## Решение

### 1. Справка — один файл в профиле

Текст справки — файл `user-guide.md` слоя приложения профиля (встроенный ресурс сборки, без грифа). Формат — узкое
подмножество Markdown: `## Раздел`, служебные строки `Раздел меню:` и `Страница: /адрес` под заголовком,
`### Подзаголовок`, шаги `1.`, пункты `-`, абзацы, выделение `**…**`. Разбор — свой (`UserGuideParser`): известные
парсеры Markdown для .NET распространяются не под MIT/Apache. Имя файла — без суффикса культуры (`*.ru.md` MSBuild
уносит в сателлитную сборку, и ресурс «пропадает» из основной).

Страница «Помощь» (`/help`, секция меню «Справка», видна каждому вошедшему — правило без прав в матрице доступа)
показывает разделы по секциям меню, поиск по тексту и кнопку «Открыть раздел». Тест сверяет справку с меню: каждый
адрес меню описан, каждая кнопка «Открыть раздел» ведёт на пункт меню.

### 2. Ядро: материалы, поданные вызывающим, вместо поиска

`GroundedRequest` получает необязательный `Materials` — готовые фрагменты. Если он задан, `GroundedGenerator` не
вызывает ретривер и работает с поданными фрагментами по тому же конвейеру: правило грунтовки ядра первым (ТБ-041),
задачный промпт профиля вторым, гвард бюджета токенов, проверка ссылок по фактически поданным фрагментам (ТБ-040),
наследование грифа, запись генерации в журнал (ТБ-030), черновик для человека (ТБ-042).

**Инвариант (fail-closed).** Поданные материалы — только несекретный справочный материал поставки: ядро оставляет
лишь фрагменты с грифом 0 и отбрасывает остальные с предупреждением в журнале приложения. Всё, что имеет гриф, идёт
только через ретривер с полным floor доступа (ТБ-020: гриф ≤ допуска и подразделение ∈ разрешённых). Подразделение
у поданного материала не проверяется: справочный материал без грифа не принадлежит подразделению.

**Инвариант грунтовки не ослабляется.** Ссылки на НПА по-прежнему подтверждаются только найденными в поданных
фрагментах; в справке норм нет, поэтому ссылка на закон в ответе помощника будет помечена как непроверенная.

### 3. Пакет чата: область с единственным режимом и поданными материалами

- `ChatScope.Materials` — фрагменты области, поданные профилем без поиска; пакет передаёт их ядру в
  `GroundedRequest.Materials`. Подпись источника — как обычно, делегатом `Describe`.
- `ChatArea.OnlyMode` — единственный режим ответа области: другой режим и поиск по смыслу сервер отклоняет
  (`ChatMessages.ModeNotInArea`), панель прячет переключатель. Область с поданными материалами — только `Grounded`
  (поиск в корпусе дал бы чужие документы). `null` — режимы по настройкам профиля, как было (у «Следствия» без изменений).

### 4. «ИнспекторAI»: область «Как пользоваться системой»

- Область чата с ключом `help` (в 0.2 — третий помощник, см. п. 5). Материалы — все разделы справки, по фрагменту на раздел. Источник ответа —
  «справка · <раздел>», щелчок ведёт на страницу раздела (или на «Помощь» для общих разделов).
- Задачный промпт — файл-шаблон `chat-help.scriban`: отвечать только по справке, шагами, называть кнопки и разделы как
  в справке; нет ответа в справке — так и сказать и предложить «Помощь» или администратора; вопросы о законах —
  в область «Документы и правовая база».
- Подсказки — типовые вопросы («Как подготовить справку по итогам проверки?», «Как сменить пароль?» …).
- Гриф вопросов области 0 (вопрос — слова сотрудника о работе с системой); запись журнала о вопросе — с допуском
  сотрудника, как в основной области (сотрудник мог вписать в вопрос лишнее).
- На странице «Помощь» — кнопка «Спросить у ИИ», открывающая чат в этой области (`/chat?area=help`).

### 5. Чат «ИнспектораAI»: три помощника вместо «Где искать» и переключателя (редакция 0.2)

После показа сотрудники и сам Заказчик путали: выбор стоял в двух местах («Где искать» и «Свободный чат / По
документам»), названия не говорили главного — видит ли ИИ документы, а чат открывался в свободном режиме, так что
вопрос о законе получал уверенный ответ «из головы» модели. Решение — каждое назначение стало отдельной областью с
единственным режимом, выбор — карточками «Что нужно» (`ChatSettings.AreaCards`):

| Помощник | Ключ | Режим | Что делает |
|---|---|---|---|
| «Ответ по документам» | по умолчанию (`null`) | по материалам | весь доступный корпус, ответ со ссылками; открывается первым |
| «Помощь с текстом» | `text` | свободный | формулировки, планы, черновики; «документы и законы не видит» — сказано на карточке |
| «Как пользоваться системой» | `help` | по материалам справки | что открыть и что нажать |

- У каждого помощника своя история диалогов (диалоги хранятся по области). Прежние диалоги, в том числе свободные,
  остались в области по умолчанию — «Ответ по документам»; продолжение в ней идёт уже по документам.
- **Подсказка «вопрос не туда»** (`ChatArea.Redirects`, `ChatRedirect`): до отправки набранный вопрос сверяется с
  признаками другой области (начало слова «закон», «кодекс», «статья»…, фразы «какой срок», «какая ответственность»; для
  текста — «перепиши», «сократи»…; для системы — «кнопк», «пароль», «меню»…). Совпало — над полем предупреждение и
  кнопка перехода: страница меняет область, новая панель сразу задаёт тот же вопрос; «Всё равно отправить» — как есть.
  Признаки — без ИИ: мгновенно и предсказуемо; подсказка ничего не запрещает, сервер её не знает. Подсказки-чипы и
  перенесённый вопрос не проверяются — они заданы для своей области.
- **Подпись под ответом**: «По документам · источников: N», «По справке · источников: N», «Без документов — проверьте
  сами» — видно и в старом диалоге.
- Значок области — смысловой (`ChatAreaIcon`: документы, текст, справка), картинку выбирает панель пакета: слой
  приложения профиля не ссылается на библиотеку интерфейса.
- Правило свободного режима ядра вместо «переключателя над полем ввода» называет помощника «Ответ по документам».

Отклонено: **автоматический выбор помощника моделью** — медленнее, а ошибку выбора сотрудник не увидит: путаница
осталась бы, только скрытой.

## Последствия

- Справка и ИИ-помощник читают один файл и не расходятся; правка текста — без программиста.
- Корпус и поиск не меняются: Генератор, Анализ и сверка не видят справку и не могут на неё сослаться.
- Вся справка подаётся модели целиком (~35 разделов, порядка 10 тыс. токенов): ответ медленнее обычного вопроса на
  время разбора промпта, зато не нужен отдельный индекс. Если справка вырастет больше бюджета промпта, гвард ядра
  отбросит хвост с предупреждением; тогда — отбор разделов по вопросу (отдельное решение).
- Изменение ядра действует и в «Следствии», но там поданными материалами никто не пользуется; поведение ретривера и
  прежних областей не меняется.

## Отклонённые варианты

- **Справка — документ корпуса.** Генерация и сверка стали бы цитировать её как источник (см. «Контекст»).
- **Свободный режим с текстом справки в системном промпте.** Нет источников и проверки ответа, а свободный режим ядра
  не принимает задачный промпт профиля — пришлось бы ослаблять его правило.
- **Отдельный индекс справки с поиском эмбеддингами.** Для ~35 разделов избыточно: вся справка помещается в промпт.
