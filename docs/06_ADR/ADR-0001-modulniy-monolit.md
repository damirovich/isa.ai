# ADR-0001. Модульный монолит вместо микросервисов

| | |
|---|---|
| **Документ** | ДОК-06 / ADR-0001 |
| **Система** | ISC.AI («ИнспекторAI») |
| **Версия** | 0.1 (черновик) |
| **Статус** | **Принято** |
| **Связь с ТЗ** | ТС-001 (основное); ТС-002, ТС-004, ТС-009, ТНД-001 |

## Контекст

Система разворачивается в изолированном контуре (air-gap), on-premise, под управлением небольшой команды сопровождения заказчика и разрабатывается малой командой (2–4 человека, см. раздел 6.2 ТЗ). Объём пользователей и нагрузки — ведомственный, не интернет-масштаба (ТН-001 уточняется на Э1, но порядок величин — десятки пользователей). Эксплуатация офлайн исключает использование облачных оркестраторов и управляемых сервисов; каждое дополнительное разворачиваемое приложение увеличивает стоимость инсталляции, обновления и сопровождения в режимном контуре (ТИ-001..003).

Микросервисная декомпозиция в таких условиях даёт отрицательный баланс: распределённые транзакции, сетевые границы доверия, отдельные конвейеры доставки и наблюдаемость — всё это операционная сложность без выигрыша, поскольку независимое масштабирование отдельных частей не требуется, а единый изолированный контур и так является границей.

## Решение

Система реализуется как **модульный монолит** — единое разворачиваемое приложение (хост `ISC.AI.Web`), внутри которого модули профиля логически разделены, но физически собираются и поставляются вместе. Микросервисная декомпозиция не применяется (ТС-001).

Логическая модульность обеспечивается архитектурой, а не сетью: многослойная Clean Architecture с правилом зависимостей внутрь к контрактам `Abstractions` (ТС-002), единая точка композиции в хосте (ТС-004) и автоматический архитектурный тест, охраняющий границы (ТС-009). Тяжёлый инференс вынесен на отдельный GPU-узел (vLLM) как внешний сервис по сетевому API — это не нарушает монолитность прикладного приложения, а отражает аппаратную границу.

Отклонённые альтернативы: (а) набор микросервисов по модулям — отклонён по причинам выше; (б) разворачивание модулей как отдельных процессов на одном узле — даёт сложность IPC без выигрыша.

## Последствия

Положительные:
- Простая инсталляция и офлайн-обновление одного дистрибутива (ТИ-001..003), один процесс развёртывания миграций.
- Внутрипроцессные вызовы вместо сетевых: ниже задержки, проще транзакции и согласованность данных.
- Меньше поверхностей атаки и границ доверия в режимном контуре.
- Сбой фонового процесса (индексации) изолируется внутри приложения архитектурно, не превращаясь в распределённый отказ (поддерживает ТНД-001).

Отрицательные / обязательства:
- Модульность держится только на дисциплине зависимостей — её необходимо охранять автоматически (обязателен архитектурный тест ТС-009), иначе монолит деградирует в «большой ком грязи».
- Вертикальное масштабирование ограничено одним узлом приложения; при росте нагрузки масштабируется прежде всего GPU-узел инференса и СУБД, а не дробление приложения.
- Долгие фоновые задачи (индексация) живут в том же приложении и требуют аккуратной изоляции ресурсов (увязано с ТНД-001).

## Связь с ТЗ

- **ТС-001** — прямое требование «модульный монолит, микросервисы не применяются».
- **ТС-002, ТС-004** — модульность реализуется слоями и единой точкой композиции.
- **ТС-009** — архитектурный тест охраняет границы модульного монолита.
- **ТНД-001** — изоляция сбоя фонового процесса от интерактивной части.
