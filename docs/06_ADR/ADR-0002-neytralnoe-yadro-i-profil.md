# ADR-0002. Нейтральное ядро и сменный профиль

| | |
|---|---|
| **Документ** | ДОК-06 / ADR-0002 |
| **Система** | ISC.AI («ИнспекторAI») |
| **Версия** | 0.1 (черновик) |
| **Статус** | **Принято** |
| **Связь с ТЗ** | ТС-002, ТС-003 (основные); ТС-006, ТС-004, ТС-009, Ц-05 |

## Контекст

ISC.AI задумана как переиспользуемая платформа: первый профиль — «Инспектор» для Главной инспекции, но архитектура должна допускать подключение новых доменных вертикалей без переписывания общего движка (цель Ц-05). Движок (RAG, интеграция с моделями, грунтовка, ingestion, персистентность, аудит, оболочка хоста) доменно-нейтрален; знания о конкретном ведомстве (корпус НПА, типы документов, доменные сущности, критерии, роли, набор модулей, промпты, привязки моделей) специфичны для внедрения.

Если доменная логика просочится в движок, каждое новое внедрение потребует правок ядра — это противоречит цели переиспользуемости и создаёт регрессионный риск для уже работающих профилей.

## Решение

Система делится на **нейтральное ядро (core)** и **сменный профиль (profile)** (ТС-003). Доменно-специфичная логика размещается **только** в профиле; ядро не содержит знаний о конкретном ведомстве и не зависит от профиля.

Связывание реализуется по правилу зависимостей Clean Architecture: и ядро, и профиль зависят внутрь — к контрактам в проекте `ISC.AI.Abstractions` (ТС-002). Профиль предоставляет **манифест** с программными контрактами (`IProfile`, `IModule`, `IModelContributor`, `IPromptProvider` и др., см. ТО-прог-04): регистрация модулей, доменных контекстов данных, привязок моделей и источников промптов (ТС-006). Знание о том, какой профиль загружен, имеет только хост (ТС-004, см. ADR-0001 и ADR-0003).

Отклонённые альтернативы: (а) единый монолит без выделения профиля — невозможно переиспользовать без форка; (б) конфигурация доменной логики «данными» без программного манифеста — недостаточно выразительна для регистрации сервисов, контекстов данных и keyed-моделей.

## Последствия

Положительные:
- Подключение нового профиля не требует изменения ядра (прямая поддержка Ц-05); проверяется архитектурным тестом ТС-009.
- Чёткая граница ответственности: инварианты безопасности и грунтовки живут в ядре и не могут быть ослаблены профилем (увязано с ADR-0005, ТБ-041).
- Профиль «Инспектор» разрабатывается и эволюционирует независимо от движка.

Отрицательные / обязательства:
- Требуется заранее спроектировать полный и устойчивый набор контрактов в `Abstractions` (ТО-прог-04); ошибки в контрактах дороги в исправлении, так как затрагивают и ядро, и профили. На момент ТЗ контракты ещё не реализованы (рабочий этап Э0) — черновые контракты разрабатываются на Э1.
- Появляется косвенность (регистрация через манифест вместо прямых ссылок), что повышает порог входа для разработчика.
- Граница «что в ядре, что в профиле» должна поддерживаться дисциплиной и тестом ТС-009, иначе размывается.

## Связь с ТЗ

- **ТС-002** — Clean Architecture, зависимости направлены к `Abstractions`; ядро не зависит от профиля.
- **ТС-003** — выделение нейтрального ядра и сменного профиля; доменная логика только в профиле.
- **ТС-006** — профиль предоставляет манифест с программными контрактами.
- **ТС-004** — единственная точка композиции (хост) знает о загруженном профиле.
- **ТС-009** — архитектурный тест проверяет, что ядро не ссылается на профиль.
- **Ц-05** — переиспользуемость платформы: новый профиль без изменения ядра.
