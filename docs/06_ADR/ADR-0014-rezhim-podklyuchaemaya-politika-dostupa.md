# ADR-0014. Режим как подключаемая политика доступа (floor ядра + IAccessPolicy)

| | |
|---|---|
| **Документ** | ДОК-06 / ADR-0014 |
| **Система** | ISC.AI («ИнспекторAI») |
| **Версия** | 0.1 (черновик) |
| **Статус** | **Принято** |
| **Связь с ТЗ** | ТБ-020, ТБ-021, ТБ-022, ТБ-002 (основные); ТС-003, ADR-0005/0013, GATE-1 |

## Контекст

Режимные метаданные — гриф (`Classification`) и подразделение (`DivisionId`) — лежат в ядре на ресурсах корпуса (документ/чанк/эмбеддинг), потому что без них ядро не может выполнить свой инвариант: фильтр доступа на стороне БД (ТБ-020) и наследование грифа в аудите (ТБ-032). Это режимные примитивы платформы, а не домен (в отличие от НПА, см. ADR-0013).

Возник вопрос гибкости: что если у профиля иная модель доступа (нет грифов, другая структура подразделений)? Хочется сделать решётку **подключаемой профилем**. Но есть жёсткое ограничение (логика ADR-0005): профиль — сменная, менее доверенная часть, и ему **нельзя позволить ослабить** разграничение доступа (ТБ-020/021, блокирующий GATE-1).

## Решение

Трёхслойная модель «нейтральные данные → неизменяемый floor ядра → подключаемое сужение профиля»:

1. **Нейтральные данные.** Контракт `IClassified` (`Classification`/`DivisionId`) в `Abstractions`; реализуется ресурсами ядра. Доменно-нейтрален.
2. **Неизменяемый ядровой floor.** `BaselineAccess.Filter<T>(AccessContext)` — EF-транслируемый предикат `гриф ≤ допуск И подразделение ∈ разрешённых`. Ретривер (Э3-05) применяет его **всегда**, на стороне БД, и профиль его **не отключает**. Без субъекта — отказ (fail-closed, ТБ-012/021).
3. **Подключаемое сужение.** `IAccessPolicy.BuildFilter<T>(AccessContext)` — дополнительный предикат профиля, применяемый **поверх** floor'а (`.Where(baseline).Where(policy)` = логическое И в SQL). По умолчанию — `AllowAllAccessPolicy` (без доп. ограничений). Профиль регистрирует свою реализацию, чтобы доуточнить доступ (например, поддерево подразделений, тип дела).

Ключевое свойство: политика может **только сужать** доступ. Даже ошибочная/широкая `IAccessPolicy` не выдаёт материал выше допуска, потому что floor применяется отдельным `Where` и профилем неотключаем. Профиль без грифов работает на вырожденных значениях (один уровень `0`, одно подразделение) — floor проходит, политика `AllowAll`; менять схему не нужно.

Предикаты строятся по **конкретному типу** `T` (через `Expression.Property`), а не через интерфейсный член, — иначе EF Core не транслирует доступ к свойству в SQL.

Отклонённые альтернативы: (а) политика владеет ВСЕМ предикатом доступа (максимальная гибкость, но профиль может РАСШИРИТЬ доступ выше допуска — нарушение ТБ-020, отвергнуто); (б) вынести гриф/подразделение в профиль (ядро не сможет фильтровать само — теряется GATE-1).

## Последствия

Положительные:
- Гибкость (профиль доуточняет решётку под свою модель) **без потери** режим-гарантии: floor неотключаем, fail-closed в ядре, проверяется GATE-1.
- Ядро остаётся доменно-нейтральным (гриф/подразделение — режимные примитивы, не домен).
- Профиль без секретности поддерживается вырожденными значениями, без изменения схемы.

Отрицательные / обязательства:
- Floor предполагает **иерархическую** модель уровней (`гриф ≤ допуск`). Принципиально иная модель (например, чисто ролевой ACL без уровней) потребует пересмотра floor отдельным ADR, а не просто `IAccessPolicy`.
- Предикаты `IAccessPolicy`/floor должны быть EF-транслируемыми; невыполнение даёт фильтрацию в памяти (риск утечки/потери полноты) — проверяется на Э3-05 и GATE-1.
- Регистрация `IAccessPolicy` (дефолт ядра vs переопределение профилем) выполняется при реализации ретривера (Э3-05).

## Связь с ТЗ

- **ТБ-020** — фильтр доступа на стороне БД; floor применяется всегда, до выдачи модели.
- **ТБ-021 / ТБ-012** — fail-closed: без субъекта с допуском фильтр не строится.
- **ТБ-022** — стратегия фильтрации (pre/post-filter) — ADR-0007; настоящий ADR определяет, ЧТО фильтруется и кем.
- **ТБ-002** — решётка «гриф × роль × подразделение»: floor покрывает гриф+подразделение, роль/доуточнение — через `IAccessPolicy`.
- **ТС-003 / ADR-0013** — нейтральность ядра: профиль поставляет семантику поверх неотключаемого ядрового инварианта.
- **GATE-1** — невыдача материала выше допуска проверяется при активной политике.
