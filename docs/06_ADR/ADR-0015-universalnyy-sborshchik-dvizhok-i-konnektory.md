# ADR-0015. Универсальный сборщик корпуса: нейтральный движок + подключаемые коннекторы (вне контура)

| | |
|---|---|
| **Документ** | ДОК-06 / ADR-0015 |
| **Система** | ISC.AI («ИнспекторAI») |
| **Версия** | 0.1 (черновик) |
| **Статус** | **Принято** |
| **Связь с ТЗ** | ТФ-НПА (корпус); ТБ-режим (air-gap — инвариант 2 CLAUDE.md); ТБ-024 (fail-closed гриф); ПОДГ-02; аналогия ADR-0002 (нейтральное ядро + профиль), ADR-0013 |

## Контекст

Корпус нужно пополнять из внешних источников (`gov.kg` и далее — минюст/ЦБД, ведомственные порталы, архивы). Боевой контур — air-gap (инвариант 2), поэтому сбор вынесен за контур в отдельное приложение `ISC.AI.Harvester` (см. [Э4-08](../tasks/Э4-08-harvester-vne-kontura.md)), а внутрь попадает только пакет данных.

Возникает риск: если писать сборщик «под gov.kg/под НПА», он превратится в жёстко привязанный к одному сайту и одному типу документа код, который придётся переписывать под каждый новый источник. Требование — **универсальность**: уметь брать данные с **любой ссылки** (хотя бы текст) и точно — с известных источников, для **любого типа документа** (НПА, положения, приказы, архивы), переиспользуемо.

## Решение

Тот же принцип, что и в самой платформе (ADR-0002): **нейтральный движок + подключаемые адаптеры**. Сборщик ничего не знает ни про НПА, ни про gov.kg; это — коннектор и маппер (аналог «профиля»).

**1. Нейтральный движок** (`Harvester.Core`) — конвейер `Discover → Fetch → Extract → Map → (курирование оператором) → Bundle`. Не содержит знаний о конкретном источнике/типе.

**2. Универсальная модель документа** `HarvestedDocument` — типонезависима (как ядро): `SourceUrl`, `FetchedAt`, `ContentType`, `Lang` (ru/ky/…), `Title`, `Text`, **`DocType` — свободная строка**, **`Metadata` — открытый словарь** (источник-специфичные поля), `ContentHash`. Режимные поля **декларируются**: `Classification = открытый`, `DivisionId` — из конфига оператора (не авто-детект, согласовано с инвариантом ingestion).

**3. Подключаемые адаптеры:**
- `ISourceConnector` — источник: `Discover` (перечислить ссылки/идентификаторы, пагинация/обход) + `Fetch` (получить контент). Реализации:
  - `GenericUrlConnector` — **любой URL**, best-effort, **всегда доступен** (zero-config);
  - `ConfigurableSiteConnector` — точное извлечение по **правилам из конфига** (CSS-селекторы: список → ссылки → пагинация → поля карточки). Любой структурированный сайт (gov.kg, минюст ЦБД и т. д.) описывается КОНФИГОМ, а не кодом: **новый источник = новые правила, без нового класса и пересборки**. Селекторы поставляет оператор (видит сайт);
  - адаптер-КЛАСС под источник — лишь редкое исключение для нестандартных источников (API/JS-рендеринг), когда правил-селекторов недостаточно.
- `IContentExtractor` — по типу контента: `HtmlReadabilityExtractor` (основной текст, универсально), далее PDF/DOCX (пути OCR Э4-01).
- `IMetadataMapper` (опц., на источник) — маппит источник-специфичные поля в `Metadata`/`DocType`; generic = best-effort.

**4. Реестр коннекторов** (DI/plugin): web-консоль оператора показывает доступные источники; оператор выбирает источник + конфиг (seed, глубина, фильтры, целевые `DocType`/`DivisionId`). `GenericUrlConnector` доступен всегда.

**5. Универсальный пакет/манифест** → на импорте в контуре маппится в `IngestionRequest` (`DocType`/`Title`/`Text`/`Classification`/`DivisionId`/`Metadata`). Манифест универсален — годится для любого типа документа.

**Стресс-проверка модели (архетипы источников ложатся без изменения движка):** HTML-страница → `GenericUrl`+`HtmlReadability`; структурированный сайт со списком/пагинацией (gov.kg, минюст) → `ConfigurableSiteConnector` по правилам-селекторам из конфига; PDF/скан → PDF-экстрактор (+OCR); JSON/REST-API → свой `ISourceConnector` (Discover/Fetch по API); sitemap/RSS → коннектор читает карту/ленту как discovery; файловая выгрузка → коннектор «папка». Все — за счёт открытого `Metadata` и свободного `DocType`.

Отклонённые альтернативы: (а) **хардкод класса-на-сайт** (`GovKgNpaConnector` с селекторами в коде) — быстро, но НЕ универсально: ломается при смене вёрстки, на каждый источник новый класс и пересборка; (б) один «волшебный» парсер для всех сайтов — недостижимо, структура HTML у каждого своя. Выбран средний путь: generic best-effort + точное извлечение по **правилам-конфигу** (`ConfigurableSiteConnector`); классы-адаптеры — лишь для экзотики (API/JS).

## Последствия

Положительные:
- Переиспользуемость: новый источник = **конфиг правил** (классы-коннекторы — редкое исключение), движок и модель документа не трогаем; единый web-UI оператора.
- Тот же ментальный паттерн, что и ядро (ADR-0002) — низкий когнитивный налог, согласованность архитектуры.
- Режим сохранён: движок и коннекторы — **вне контура**; пакет — единственное, что пересекает зазор.

Отрицательные / обязательства:
- Качество метаданных у `GenericUrlConnector` ограничено (best-effort); точность — только через адаптер источника.
- Вежливый сбор (robots.txt, rate-limit, User-Agent, ToS источника) — ответственность коннектора.
- Библиотеки парсинга (HTML/PDF) — только **MIT/Apache** (проверять перед добавлением).
- Маппинг «источник → гриф/подразделение» — декларативный (оператор/конфиг), не авто-детект.

## Связь с ТЗ

- **ТБ-режим / air-gap** — движок и коннекторы вне контура; в контур пересекает только пакет.
- **ТФ-НПА** — корпус собирается из источников; gov.kg — первый коннектор, не единственный.
- **ТБ-024** — на импорте гриф/подразделение обязательны (fail-closed), декларируются оператором.
- **ADR-0002** — аналогия: нейтральный движок + подключаемые коннекторы, как ядро + профиль.
- **ADR-0013** — типонезависимость (свободный `DocType`, открытый `Metadata`), как нейтральный корпус ядра.
- **ПОДГ-02** — подготовка корпуса.
