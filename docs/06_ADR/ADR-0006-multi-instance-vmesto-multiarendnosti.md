# ADR-0006. Multi-instance вместо мультиарендности

| | |
|---|---|
| **Документ** | ДОК-06 / ADR-0006 |
| **Система** | ISC.AI («ИнспекторAI») |
| **Версия** | 0.1 (черновик) |
| **Статус** | **Принято** |
| **Связь с ТЗ** | ТС-005 (основное); ТО-инф-03, ТФ-ДШ-01, ТФ-ДШ-03, ТФ-АРХ-03, ТБ-052 |

## Контекст

Система обрабатывает сведения ограниченного доступа (до грифа ДСП) в изолированном контуре (ТБ-052). Возможны два способа разделения данных между организационными единицами: мультиарендность (один экземпляр приложения и БД, арендаторы разделены логическим дискриминатором) либо multi-instance (отдельный экземпляр — своя БД, своё хранилище, свой контур — под каждую единицу).

В режимной системе логический дискриминатор как единственная граница между контурами разного грифа — слабая гарантия: ошибка в условии запроса или обход штатного пути ведёт к утечке между арендаторами. Одновременно внутри одной организационной единицы (Главная инспекция) нужны сводные представления по подчинённым подразделениям (дашборд, аналитика архива — ТФ-ДШ, ТФ-АРХ-03), что требует, чтобы их данные жили вместе.

## Решение

Развёртывание — **multi-instance** (ТС-005): отдельный экземпляр (своя БД, своё хранилище, свой контур) под каждый **отдел/контур верхнего уровня**. Мультиарендность с дискриминатором между отделами **не применяется**.

**Граница экземпляра — Главная инспекция в целом.** Подчинённые подразделения (по презентационным материалам — 7 ТУ и 6 линейных) представлены **не отдельными экземплярами**, а атрибутом «подразделение» данных внутри одного экземпляра (ТО-инф-03). Именно это обеспечивает сводные представления дашборда и аналитики архива (ТФ-ДШ-01/03, ТФ-АРХ-03) из данных одного экземпляра.

Если для конкретного внедрения потребуется экземпляр на подразделение, вводится отдельное требование к консолидации данных в пределах контура, а формулировки «в реальном времени» уточняются (ТС-005).

Отклонённые альтернативы: (а) мультиарендность с дискриминатором между отделами — отклонена как недостаточно надёжная граница для режимных данных; (б) экземпляр на каждое подразделение — разрушил бы сводные представления и усложнил консолидацию.

## Последствия

Положительные:
- Сильная физическая граница между контурами разного уровня: отдельные БД и хранилища исключают межарендную утечку через ошибку запроса.
- Сводные представления (дашборд, аналитика) строятся из данных одного экземпляра по атрибуту «подразделение» — без распределённых запросов (ТФ-ДШ, ТФ-АРХ-03).
- Соответствует изолированному on-premise развёртыванию (ТБ-052): каждый экземпляр самодостаточен.

Отрицательные / обязательства:
- Несколько экземпляров (при будущих внедрениях для разных отделов) означают дублирование инсталляции, обновления и сопровождения — операционная нагрузка растёт с числом экземпляров.
- Атрибут «подразделение» обязателен и `NOT NULL` для документов/чанков/эмбеддингов и доменных сущностей (ТО-инф-03); разграничение по подразделению внутри экземпляра выполняется решёткой доступа (ТБ-002, ТБ-011), а не границей экземпляра.
- Кросс-инстансная консолидация (если понадобится) — отдельная задача, не покрытая базовым решением (ТС-005).

## Связь с ТЗ

- **ТС-005** — multi-instance; граница экземпляра — Главная инспекция; подразделения — атрибутом данных, не отдельными экземплярами; мультиарендность не применяется.
- **ТО-инф-03** — обязательный атрибут «подразделение» (`NOT NULL`) у документа/чанка/эмбеддинга.
- **ТФ-ДШ-01, ТФ-ДШ-03, ТФ-АРХ-03** — сводные представления из данных одного экземпляра.
- **ТБ-052** — on-premise, изолированный контур: самодостаточный экземпляр.
