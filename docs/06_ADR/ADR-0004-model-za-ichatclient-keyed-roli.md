# ADR-0004. Доступ к модели за `IChatClient` и keyed-роли

| | |
|---|---|
| **Документ** | ДОК-06 / ADR-0004 |
| **Система** | ISC.AI («ИнспекторAI») |
| **Версия** | 0.1 (черновик) |
| **Статус** | **Принято** |
| **Связь с ТЗ** | ТО-прог-02, ТО-прог-03 (основные); ТСТ-003, ТО-прог-01, ТО-прог-04 |

## Контекст

Система использует локальные LLM, разворачиваемые через vLLM (OpenAI-совместимый API) в изолированном контуре (ТО-прог-01). Конкретные модели на старте не зафиксированы: названия из презентации («Gemma 4», «Qwen 3.5») не соответствуют реальным релизам и подлежат замене (ТО-прог-03); окончательный выбор весов, размера и квантизации зависит от бюджета VRAM узла и результатов бенчмарка на реальном корпусе (ТН-002, ТО-лнг-02). При этом разные задачи имеют разные требования к модели: быстрая генерация/форматирование документов и анализ/сверка НПА с длинным контекстом — это разные профили нагрузки, потенциально разные модели.

Ядро не должно знать конкретных названий моделей, иначе нарушается нейтральность ядра (ADR-0002) и переносимость (ТСТ-003): замена модели потребовала бы правок кода.

## Решение

Доступ к моделям осуществляется через **нейтральную абстракцию `IChatClient`** (`Microsoft.Extensions.AI`); ядро не знает конкретных названий моделей (ТО-прог-02). Связка «модель ↔ задача» задаётся **конфигурацией через keyed-регистрацию по роли**.

Определены **роли моделей (keyed)** (ТО-прог-03):
- `draft` — быстрая генерация и форматирование документов;
- `analysis` — анализ и сверка НПА, длинный контекст;
- эмбеддинги — отдельная модель векторизации (ru/ky) через `IEmbeddingGenerator`.

Конкретные веса, размер и квантизация фиксируются конфигурацией под бюджет VRAM, без изменения кода. Профиль декларирует привязки моделей через контракт `IModelContributor` (ТО-прог-04, см. ADR-0002).

Отклонённые альтернативы: (а) прямой вызов конкретного клиента модели из кода — привязывает ядро к модели, ломает переносимость; (б) единая модель на все роли — не оптимально по соотношению скорость/качество/VRAM и негибко при бенчмарке.

## Последствия

Положительные:
- Замена модели/источника выполняется конфигурацией и адаптером без изменения ядра (прямая поддержка ТСТ-003 и нейтральности ядра ADR-0002).
- Роли позволяют независимо подбирать и бенчмаркать модели под задачу (draft/analysis/embeddings), оптимизируя VRAM (ТН-002, ТО-лнг-02).
- Несуществующие названия из презентации не «зашиты» в код — их замена на реальные релизы безболезненна (ТО-прог-03).

Отрицательные / обязательства:
- Абстракция `IChatClient` должна покрывать реальные потребности (структурированный вывод, длинный контекст); расхождение возможностей конкретной модели и контракта потребует адаптера.
- Корректность keyed-разрешения ролей нужно покрыть проверкой (code review, ТО-прог-02): ошибочная привязка роли к модели — функциональный дефект.
- Выбор конкретных моделей и эмбеддера остаётся открытым и выносится в отдельную ADR на Э1 (ТО-прог-03 / ТО-лнг-02) по результатам бенчмарка; настоящая ADR фиксирует только механизм доступа, а не сам выбор.

## Связь с ТЗ

- **ТО-прог-02** — доступ к моделям через `IChatClient` (`Microsoft.Extensions.AI`); ядро не знает названий моделей; связка задаётся keyed-регистрацией по роли.
- **ТО-прог-03** — роли `draft` / `analysis` / эмбеддинги; веса и квантизация — конфигурацией; замена несуществующих названий моделей.
- **ТСТ-003** — независимость от облака и переносимость: замена модели без изменения ядра.
- **ТО-прог-04** — контракты `IModelContributor`, порт модели через `IChatClient`, `IEmbeddingGenerator`.
- **ТО-прог-01** — стек: vLLM с OpenAI-совместимым API.
