## Контекст

Заказчик хочет видеть на карточке объекта предупреждение вида «ПЕРЕСЕЧЕНИЕ! Данный автотранспорт также фигурирует
в карточке объекта „Шторм“ (Дело №19/26 УН)». Это первый сценарий профиля, который **показывает субъекту факт из
чужого дела** — дела, которое по правилу ТФ-ДЕЛ-03 он может и не видеть (следователь видит только свои дела).
Значит, пересечения затрагивают решётку доступа, и правило их видимости надо зафиксировать до кода.

Что уже есть: нормализованные ключи (ТО-мат-11, `RequisiteNormalizer`) и индексы по ним —
`person.name_normalized`, `person.residence_normalized`, `person_address.text_normalized`,
`person_vehicle.plate_normalized`. Решётка дел — `CaseAccessRule.Apply` (floor ядра → политика профиля →
сужение по роли/владению).

Противоречие, которое снимает ТБ-084: ТФ-ДЕЛ-03 сужает видимость дел по роли, а пересечения должны находиться «по
всем делам ОН и УН экземпляра». Если искать только среди дел субъекта, следователь не увидит главного — совпадения
с делом коллеги; если искать без решётки, раскроется дело выше допуска.

## Решение

1. **Где ищем.** Совпадения ищутся среди дел, проходящих **floor ядра и политику профиля** (гриф ≤ допуск,
   подразделение ∈ разрешённых — `BaselineAccess`, ТБ-020), но **без сужения по роли и владению**
   (`CaseAccessRule.Narrow` не применяется к «чужой» стороне). Floor ядра не ослабляется: дело выше допуска или
   чужого подразделения в поиск не попадает вовсе — ни реквизитами, ни счётчиком, ни временем ответа (один
   SQL-запрос с тем же планом, ТБ-021). Видимость ОН ↔ УН, таким образом, задаётся Администратором через
   разрешённые подразделения учётной записи — тем же механизмом, что и всё остальное; отдельного «обходного» пути
   нет. Floor применяется к **каждой** строке цепочки: к делу, к фигуранту другого дела и к строке реквизита.
2. **Откуда ищем.** Исходная сторона — фигурант, чью карточку открыли; он должен быть доступен субъекту по полной
   решётке (`PersonAccess`). Недоступный фигурант — пустой ответ «не найден» (fail-closed).
3. **Что считается совпадением** (умолчание вопроса 1 Приложения В): **точное** совпадение нормализованных ключей:
   - госномер — `person_vehicle.plate_normalized`;
   - адрес — `person_address.text_normalized` и место жительства из анкеты `person.residence_normalized`
     (адрес одного фигуранта сравнивается с обоими источниками другого);
   - ФИО + дата рождения — `person.name_normalized` и `person.birth_date`, оба заданы у обеих сторон
     (совпадение только по ФИО или по году рождения — нет: слишком много однофамильцев).
   Нечёткое сравнение (опечатки, кириллица ↔ латиница в ФИО, киргизская форма) — после ответа Заказчика; точка
   расширения — одно место (`IntersectionStore`). Совпадения внутри одного дела пересечением не считаются.
   Пересечение **по лицу** (ТФ-ПЕР-07, последний абзац) — отдельный шаг: оно строится из подтверждённых появлений
   (ТБ-073) и в этом ADR не реализуется.
4. **Что показываем** (умолчание вопроса 2): номер дела, вид дела, вид и значение совпавшего реквизита,
   ответственный сотрудник (ведущий дела). ФИО, анкета и материалы чужого фигуранта **не** показываются. Если
   субъект видит это дело и по роли (ТФ-ДЕЛ-03), номер дела — ссылка на карточку; иначе — просто текст.
   Несколько фигурантов чужого дела с одним и тем же ключом дают **одну** строку (не раскрываем их число).
5. **Когда ищем.** При открытии карточки фигуранта и после сохранения/удаления адреса или транспорта, при
   правке анкеты (ТФ-ПЕР-07 «при сохранении связи и при открытии карточки»). Совпадения **вычисляются при чтении**
   (ТО-инф-13): таблицы пересечений нет, поэтому нечего синхронизировать и нечего «забыть» удалить при уничтожении
   дела (ADR-0025).
6. **Подтверждение и отклонение.** Решение человека по пересечению — строка `investigation.intersection_review`
   на стороне **своего** дела: фигурант (FK, каскад), вид реквизита, нормализованный ключ, идентификатор чужого
   дела **по значению** (без FK — схема не связывает дела между собой), решение, кто и когда. Гриф и подразделение
   — с фигуранта своего дела (ТБ-070). Одна строка на (фигурант, вид, ключ, чужое дело); повторное решение её
   перезаписывает, история — в журнале аудита. Решение принимается, только если такое пересечение **сейчас**
   видно субъекту — иначе «не найдено» (строкой нельзя прощупать чужие дела). Автоматических связей между делами
   система не создаёт; пересечение — подсказка, а не вывод (§2.7 ТЗ).
7. **Аудит (ТБ-030).** Просмотр пересечений — `View` (`investigation:person:{id}:intersections:view`), решение —
   `Modify` (`investigation:person:{id}:intersection:{вид}:case:{чужое дело}:{решение}`). Значения реквизитов в
   сводку журнала не попадают (ТБ-032), только идентификаторы.
8. **Между экземплярами** (ОТМ ↔ ОН/УН, Офис №1 ↔ №2) пересечения не вычисляются: у экземпляров разные базы.

## Последствия

- **Плюсы.** Одно правило видимости для всех ключей; floor ядра не обходится; нет денормализованной таблицы
  совпадений; уничтожение дела автоматически убирает его из пересечений.
- **Минусы.** Каждое открытие карточки — несколько запросов по индексам нормализованных ключей. На объёмах ТН-005
  (сотни дел, тысячи реквизитов) это миллисекунды; при росте — материализованное представление, не меняя правила.
- **Риск.** Администратор, выдав учётке оба подразделения (ОН и УН), открывает ей пересечения с делами обоих
  направлений — это и есть требуемое «взаимный анализ ОН+УН» (ТБ-084), но должно быть явно описано в руководстве
  администратора.
- **Что проверяют тесты.** Интеграционные (Testcontainers): совпадение госномера с чужим делом в пределах допуска
  находится; с делом выше допуска и чужого подразделения — нет; совпадения внутри дела нет; признак «можно
  открыть» соответствует ТФ-ДЕЛ-03; решение по невидимому пересечению — «не найдено». Модульные: охрана команды и
  валидатор.
