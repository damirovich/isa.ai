## Контекст

Выяснилось, что в дела загружают и **аудио**: голосовые сообщения мессенджеров, записи разговоров,
диктофон. Пакет «Медиа» знал только фото и видео и аудио отклонял. Нужна расшифровка речи в текст.

Ограничения, которые определили выбор:

- **Язык:** русский и **киргизский**, нередко вперемешку в одной записи.
- **Изолированный контур:** модель работает локально, файлы переносятся офлайн, сеть не используется.
- **Лицензии:** только MIT/Apache/BSD — и для кода, и для **весов** модели.
- **.NET 10:** вызов из C#, без обязательного Python-сервиса.

Важные оговорки к выбранной модели: опубликованные метрики получены на чистых наборах; **смешанная
русско-киргизская речь никем не измерялась** (по устройству модели — один CTC-выход без языкового тега —
она должна переключаться внутри фразы, но это не доказано); выход — **строчные буквы без знаков
препинания**; модель берёт до ~25 с звука за раз.

## Решение

**Конвейер:**

```
Аудио / видео
   ↓ ffmpeg — WAV 16 кГц моно; из видео извлекается звуковая дорожка
   ↓ Silero VAD — участки речи; их границы и есть таймкоды фрагментов
   ↓ склейка соседних участков в куски до 20 с вместе с паузами (п. 13)
   ↓ GigaAM Multilingual 600M (CTC) через sherpa-onnx — дословный текст (ru / ky / смешанный),
     слова раскладываются обратно по участкам по меткам времени
   ↓ хранение в media.transcript_segment — ПЕРВИЧНЫЙ слой, под решёткой носителя
   ↓ поиск по словам в расшифровках дела; карточка носителя с переходом к месту записи
```

1. **Отдельный процесс-распознаватель `ISC.AI.Speech.Worker`.** Нативная библиотека sherpa-onnx
   несёт свой `onnxruntime.dll`, а распознавание лиц — свой (Microsoft.ML.OnnxRuntime 1.30). Проверено:
   оба лежат по одному пути `runtimes/win-x64/native/onnxruntime.dll` и это **разные сборки** (16,5 и
   17,8 МБ) — в одном процессе одна перезаписала бы другую. Вызов внешним процессом — тот же приём, что у
   ffmpeg; заодно длинная расшифровка (часы звука) не делит память и потоки с хостом. Протокол —
   JSON-строки в stdout; утилита не ссылается ни на один проект ISC.AI.
2. **Модель — за портом `IAudioTranscriber`.** Выбор подтверждается пилотом; если победит другая
   модель, меняется только реализация порта — как у распознавания лиц (ADR-0020).
3. **Дословный текст модели — первичный слой, и он неизменен.** Для следствия важна дословность.
   Будущая расстановка знаков языковой моделью — **отдельный слой «для чтения»** с пометкой, он никогда
   не заменяет исходник: модель могла бы «поправить» слово, нормализация — ошибиться в дате или сумме.
4. **Поиск — по подстроке без учёта регистра**, а не морфологический: у PostgreSQL нет словаря
   киргизского, а язык агглютинативный — «үйдө», «үйгө» должны находиться по «үй». Поиск ограничен
   носителями дела и проходит решётку на стороне БД. Отдельный поисковый сервер (Elasticsearch) не
   нужен и не допустим: SSPL/Elastic/AGPL-лицензии, второй контур доступа, дублирование фильтра ТБ-020.
5. **Режим:** фрагмент несёт гриф и подразделение носителя (решётка ТБ-020/021); чтения по прямому
   идентификатору — через сужение по делам субъекта; расшифровка — событие журнала (модель, число
   фрагментов); поиск по расшифровкам аудируется с искомым текстом; уничтожение носителя или дела
   сносит расшифровку каскадом (ADR-0025); в интерфейсе постоянная пометка «автоматическая расшифровка,
   требует проверки, не является протоколом» (ТЭ-002).
6. **Аудио — третий вид носителя** (`MediaKind.Audio`): лиц в нём нет, поэтому индексация лиц к нему
   **неприменима** (`MediaIndexStatus.NotApplicable`), а не «проиндексировано с нулём лиц» — иначе журнал
   утверждал бы, что биометрия обрабатывалась.
7. **Нативная библиотека sherpa-onnx — только сборка БЕЗ синтеза речи.** Находка при подготовке
   поставки (25.09.2026, проверена координатором): официальная нативная библиотека из NuGet
   `org.k2fsa.sherpa.onnx.runtime.*` 1.13.8 статически содержит движок синтеза речи **eSpeak NG
   (GPL-3.0)** — 25 функций `espeak_ng_*` в `sherpa-onnx-c-api.dll`. Нам нужен только распознаватель, но
   поставлять GPL-код нельзя (то же правило, что отсекло GPL-сборки ffmpeg, ADR-0020). Проект выпускает
   официальные сборки того же релиза **без синтеза речи** (`*-no-tts-lib`, Apache-2.0): в них 0 функций
   `espeak_ng_*`, распознавание и детектор речи на месте. Поставка: `export-sherpa-no-tts.ps1` (пины
   SHA-256 из digest релиза GitHub) → `publish-speech-worker.ps1` подменяет нативные библиотеки пакета
   сборкой no-tts и проверяет бинарник на отсутствие `espeak_ng_*`; без no-tts-библиотек публикация
   отказывает. Проверка по подстроке «espeak» без учёта регистра даёт ложные срабатывания на
   `OfflineSpeakerDiarization` («offlin-eSpeak-er») — проверять нужно по функциям движка.
   Проверяются **все** нативные файлы публикации, а не только две подменённые библиотеки; нативный файл сверх
   пары `sherpa-onnx-c-api` + `onnxruntime` — отказ «лишняя нативная библиотека» (в другом релизе пакет может
   развернуть ещё одну). Рядом с бинарниками кладутся тексты лицензий `LICENSE-sherpa-onnx.txt` (Apache-2.0) и
   `LICENSE-onnxruntime.txt` (MIT) из `deploy/offline/licenses`; без них публикация отказывает.
   Для Windows берётся вариант **MT** этой сборки (`*-win-x64-shared-MT-Release-no-tts-lib`): среда C++ в нём
   вшита статически, импортов `VCRUNTIME140`/`MSVCP140` нет — на сервере не нужен Microsoft Visual C++
   Redistributable (у варианта MD они есть). Проверено живым прогоном опубликованного распознавателя: русская
   речь распознаётся, результат побайтно совпадает со сборкой на библиотеке NuGet.
   На машине разработчика распознаватель из `bin/Debug` работает с библиотекой NuGet — это использование,
   а не поставка; в контур уходит только опубликованная no-tts сборка.
   **Пакеты утилиты (`org.k2fsa.sherpa.onnx*`) никогда не входят в общий офлайн-фид.** Утилита публикуется
   вне контура (`publish-speech-worker.ps1`, восстановления из офлайн-фида у него нет) и поставляется готовой
   папкой с манифестом `worker.sha256`. Фид собирается по фильтру решения `ISC.AI.Offline.slnf`: всё решение,
   кроме утилиты и её юнит-тестов — они вынесены в отдельный проект `tests/ISC.AI.Speech.Worker.Tests`, а
   `UnitTests`/`IntegrationTests` на утилиту не ссылаются. Состав фильтра и отсутствие ссылок на утилиту
   закрепляет тест `OfflineSolutionFilterTests`; `export-packages.ps1` и `verify-packages.ps1` отказывают, если в
   фиде есть пакет `org.k2fsa.sherpa.onnx*` или нативный файл (`runtimes/*/native/*`) с признаками eSpeak NG.
   Так GPL-код не уходит за периметр ни с одной поставкой, включая «ИнспекторAI», где речи нет.
8. **Порт отдаёт итог целиком.** `IAudioTranscriber.TranscribeAsync` возвращает `Task<AudioTranscription>`:
   фрагменты и длительность записи из итоговой строки `done` утилиты. Длительность аудио — длина записи, а не
   конец последней речи. Потока нет: расшифровка записывается одной транзакцией, частичный результат сбойного
   прогона не сохраняется.
9. **Предел длительности записи** — `Speech:MaxDurationHours`, по умолчанию 24 ч, допустимо 1–36. Потолок
   жёсткий: номер отсчёта в нативном детекторе речи — int32 (≈37,3 ч при 16 кГц), тот же порог у WAV (4 ГБ).
   Длительность берётся из ffprobe (наибольшая из контейнера и звуковых дорожек) до запуска ffmpeg; запись
   длиннее предела отклоняется («разбейте на части»). ffmpeg всегда ограничен ключом `-t` (предел + 1 с), а длина
   полученного WAV ещё раз сверяется с пределом: если ffprobe длительность не сообщил или занизил — тоже отказ, а
   не молча обрезанный хвост. Утилита сама отказывает кодом 2 на записи длиннее ≈37,1 ч — последний рубеж.
10. **Таймаут прогона** — `15 мин + Speech:TimeoutFactor × длительность WAV` (множитель по умолчанию 3,
    допустимо 0,5–20). По истечении процессы останавливаются, временный каталог удаляется, расшифровка —
    ошибка с упоминанием `Speech:TimeoutFactor`. Значения обоих ключей вне допустимого диапазона зажимаются в
    него, как у `Speech:MaxSegmentSeconds`.
11. **Настройки детектора речи.** Хвост записи дополняется тишиной, чтобы детектор не отбросил последнее
    слово (последнее неполное окно больше не теряется). У детектора большой `MaxSpeechDuration` (600 с): куски
    по пределу модели (`Speech:MaxSegmentSeconds`) режет `SegmentSplitter` встык, по самому тихому месту, — сам
    детектор резал бы посреди слова. Начало участка берётся с небольшим запасом предшествующего звука
    (~0,25 с), иначе детектор срезает первое короткое слово.
12. **«Видео» без видеопотока.** Браузер объявляет голосовое `.3gp` как `video/3gpp`, поэтому `.3gp` всегда
    принимается как видео; так же бывает звук в mp4/webm. Индексатор до раскадровки смотрит потоки через ffprobe
    (обложка звуковой записи видеопотоком не считается) и, не найдя видеопотока, переводит носитель в «Аудио» с
    индексацией лиц «неприменимо» (п. 6) — без записи в журнал об обработке биометрии. Дальше запись
    расшифровывается как аудио. Расширение имени файла при приёме нормализуется (`^\.[A-Za-z0-9]{2,5}$`, иначе
    `.bin`): путь к временной копии уходит ffmpeg текстом командной строки.
13. **Модель 600M и склейка участков в куски** (решение заказчика 25.09.2026; подтверждается пилотом КИ-10).
    **Основная модель — GigaAM Multilingual 600M** (`gigaam-multilingual-ctc-600m.int8.onnx`) вместо 220M; 220M
    остаётся запасным вариантом для слабых машин (`export-speech-models.ps1 -Variant 220m`, в конфигурации —
    другой путь и пин). **Распознаватель склеивает соседние участки детектора в кусок** не длиннее
    `Speech:MaxSegmentSeconds` (по умолчанию 20 с) и подаёт модели кусок целиком, **вместе со звуком пауз** между
    участками. Участок длиннее предела по-прежнему режется по п. 11.

    **Замер** (25.09.2026, живая киргизская запись заказчика, 30 с, чтение текста; запись в репозиторий не
    попадает). WER/CER — по тексту, который читал чтец:

    | Модель | Что подаётся модели | WER | CER | Казахские слова |
    |---|---|---|---|---|
    | 220M | участки детектора (1–3 с) | 30,9 % | 17,6 % | 2 фрагмента из 8 |
    | 600M | участки детектора (1–3 с) | 23,6 % | 15,5 % | 2 фрагмента из 8 |
    | 220M | куски ~15 с (те же паузы) | 16,4 % | 13,2 % | нет |
    | 600M | куски ~15 с (те же паузы) | **10,9 %** | **10,0 %** | нет |

    Остаток ошибки 600M на кусках — почти целиком отступления чтеца от текста («проект» вместо «долбоор»,
    «информационный безопасносту» вместо «маалыматтарды»): сказанное модель передала верно, включая киргизское
    окончание на русском слове. Одна запись — не пилот: выбор подтверждается пилотом (КИ-10).

    **Почему склейка — контекст языка.** Модель знает киргизский и близкий к нему казахский и выбирает язык
    сама, по звуку, без языкового тега. На участке 1–3 с звука для выбора мало, и киргизская речь иногда
    пишется казахскими словами и буквами (қ, ғ, і): «қауіпсіздік талаптарын талқыладық» вместо «коопсуздук
    талаптарын талкууладык». Для поиска по расшифровке такие слова потеряны. На куске ~15 с по тем же паузам
    казахских слов не было ни у одной модели. Предел куска прежний: модель берёт до ~25 с звука.

    **Таймкоды остаются по паузам.** Фрагменты и таймкоды в интерфейсе — по участкам детектора, как до склейки.
    Слова раскладываются обратно по участкам по меткам времени токенов CTC: GigaAM выдаёт метку на каждую букву
    с шагом 40 мс, слова разделены пробелом; слово относится к участку, в который попадает его первая буква
    (слово в паузе между участками — к ближайшему). Модель слышит и паузы и может найти в них слово, которое
    детектор речью не счёл (короткое тихое «да»); тогда границы фрагмента расширяются до места этого слова, чтобы
    переход к фрагменту не перематывал запись уже после него, — соседние фрагменты при этом не перекрываются
    (находка ревью 25.09.2026). Если меток нет или они расходятся с токенами — один фрагмент на весь кусок: текст не
    теряется, грубеет только таймкод. Кусок вызывает модель один раз, поэтому на склейке прогон ещё и быстрее
    (киргизская запись 30 с: 2 вызова модели вместо 8, 2,0 с вместо 3,6 с у 600M).

    **Цена.** 600M примерно вдвое медленнее: 30 с записи за ~3,6 с на 4 потоках (RTF ~0,12) против ~1,9 с у 220M
    (RTF ~0,06), то есть час записи — ориентировочно ~7 мин против ~4. На диске 592 МБ против 225 МБ. Память и
    скорость на серверном CPU — замеры пилота (6.4 методики).

**Не в этом шаге** (следующие): расстановка знаков препинания языковой моделью; индексация расшифровок
в корпус ядра для поиска по смыслу и чата по документам дела (вместе с ТФ-ДДЛ); разделение по голосам
(«кто говорит» — лицензии моделей diarization ещё проверять).

## Последствия

- **Пилот обязателен** до промышленного применения: 20–30 реальных записей заказчика с ручной эталонной
  расшифровкой — WER/CER отдельно на русском, киргизском и **смешанной** речи; телефон, допрос, шум,
  дальний микрофон; имена, топонимы, числа, даты; скорость и память на серверном CPU на записях 1–2 ч;
  точность таймкодов на стыках фрагментов; доля фрагментов с казахскими буквами на киргизских записях (п. 13).
  Основной прогон — GigaAM 600M со склейкой, 220M — для сравнения скорости; Vosk ky+ru; для чисто русских —
  Whisper large-v3-turbo. Реальные записи — не в репозиторий и не в тесты (как фото людей, ТО-прог-13).
- Файлы модели поставляются офлайн скриптом `deploy/offline/export-speech-models.ps1` с пинами SHA-256;
  при несовпадении пина распознавание не запускается. Для боевой поставки ONNX лучше экспортировать из
  официальных весов ai-sage, а не брать стороннюю конвертацию.
- Видео, загруженные до этой версии, не расшифрованы — их можно отправить на расшифровку кнопкой
  «Расшифровать» в карточке носителя.
- Без настроенной модели расшифровка **явно** отказывает («не настроена»), а не молча пропускается.
- Процесс-распознаватель в контуре из исходников не собирается: его пакетов в офлайн-фиде нет (п. 7). Решение
  в контуре восстанавливается и собирается по `ISC.AI.Offline.slnf`, распознаватель приходит готовой папкой;
  интеграционные тесты речи перед прогоном требуют собранной утилиты (тестовый проект на неё не ссылается).
- Временные копии материала дела (WAV, копия исходника, буфер приёма файла) удаляются в конце операции;
  остатки после аварийного останова хоста убираются при следующем старте, до приёма запросов (ТБ-064;
  подробности — Развёртывание «Следствия», §7.3). Там же расшифровки, прерванные перезапуском («в очереди»,
  «выполняется»), переводятся в «ошибку» с подсказкой запустить заново, а не висят вечно.
- Качество поиска по смыслу для киргизского зависит от модели эмбеддингов (EmbeddingGemma) — открытый
  пункт ADR-0011 (КИ-03); поиск по словам от неё не зависит.

## Альтернативы

**Whisper через Whisper.net (в процессе).** Лучшая .NET-интеграция (MIT, есть `ISpeechToTextClient`), но
киргизского языка у модели нет — отвергнуто как основной вариант; оставлен кандидатом для чисто русских
записей после пилота.

**sherpa-onnx в процессе хоста.** Отвергнуто: конфликт нативных `onnxruntime.dll` с распознаванием лиц.

**Python-сервис (faster-whisper и т.п.).** Отвергнуто: второй рантайм в контуре без выигрыша в качестве
на киргизском.
