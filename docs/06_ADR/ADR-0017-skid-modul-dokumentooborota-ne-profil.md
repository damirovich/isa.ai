# ADR-0017. СКИД — пакет модулей документооборота, а не второй профиль

## Контекст

СКИД — ведомственная система контроля исполнения документов: регистрация входящих/внутренних/исходящих,
поручения с дедлайнами по подразделениям, статусы и продления, комментарии с упоминаниями, уведомления,
отчёты, аудит. По итогам разбора кода (`C:\...\repos\skid`): .NET 10, Blazor Server + MudBlazor, EF Core +
PostgreSQL (схема `public`, БД `skid_Dev`), Clean Architecture из 5 проектов, ~38 тыс. строк, 116 тестов,
собственный Docker-деплой для изолированного контура.

**СКИД в эксплуатацию ещё не введена — это новый проект, боевых данных нет** (подтверждено заказчиком
2026-08-04). Это существенно меняет стоимость слияния: нет переноса боевых данных, нет пользователей,
которых затронет простой, и **нет схемы, зафиксированной данными** — структуру таблиц можно привести к
требованиям режима сразу, а не «донастраивать» поверх существующих записей.

ISC.AI уже связан со СКИД по одному шву — идентичность ([ADR-0016](ADR-0016-skid-istochnik-identichnosti-dopusk-lokalno.md)):
чтение `public.users`/`public.departments` **только на чтение**, сверка пароля тем же Argon2id (libsodium).
Заказчик поставил цель объединить продукты полностью.

Два факта, определивших решение:

1. **СКИД пользуется ТА ЖЕ Главная инспекция**, что и «ИнспекторAI» — это не другой отдел.
2. **Профиль в ISC.AI — ровно один на развёртывание.** Прямо зафиксировано в контракте
   (`IProfile`: «Реализуется ровно одним профилем на развёртывание») и в точке композиции хоста
   (`Program.cs`: `var profile = new InspectorProfile();` — одиночный singleton). Двух профилей в одном
   хосте не бывает по построению.

Дополнительно: у СКИД **нет никакого API** (только форма входа, файловый эндпоинт, SignalR-хаб и сам
Blazor UI — всё сессионно-cookie, для человека), поэтому «интеграция по API» как вариант отсутствует
физически. И у СКИД **нет понятия грифа/допуска** — доступ описывается только ролью и подразделением.

## Решение

**СКИД вливается в ISC.AI как ПАКЕТ МОДУЛЕЙ документооборота, подключаемый профилем. Вторым профилем СКИД НЕ делается.**

1. **Почему не профиль.** Профиль = доменная вертикаль отдела, и он один на развёртывание (см. контекст).
   Отдельный `SkidProfile` означал бы два хоста, два входа и два меню для одних и тех же людей — то есть
   текущее положение дел, переименованное в «слияние». Отклонено.

2. **Размещение — отдельный пакет модулей `src/modules/docflow/`** (Domain / Application / Data / UI-RCL),
   а НЕ внутрь `src/profiles/inspector/`. Документооборот (документы, поручения, сроки, исполнители)
   доменно **не инспекционен** — он нужен любому отделу-эксплуатанту. Похоронив его в профиле инспекции,
   мы вынудили бы следующий отдел копировать код, что прямо противоречит цели архитектуры
   ([ADR-0002](ADR-0002-neytralnoe-yadro-i-profil.md)): переиспользование без переписывания.
   Это **не гипотетическая** предосторожность: второй профиль «АИС ЕРП» уже заведён и его каркас поднят
   на неизменённом ядре ([ЕРП-01](../tasks/ЕРП-01-каркас-профиля.md)) — при размещении внутри профиля
   инспекции документооборот оказался бы ему недоступен.

3. **Правило зависимостей расширяется одним уровнем** (инвариант ядра не ослабляется):
   - пакет модуля зависит от `Abstractions` (и `Persistence` — только проект `*.Data`, как `Inspector.Data`);
   - **профиль** зависит от пакета модуля и включает его дескрипторы в свой `IProfile.Modules`;
   - **ядро по-прежнему НЕ ссылается ни на профиль, ни на модуль** — проверяется архитектурным тестом (ТС-009).

4. **Данные — третья схема `docflow`** со своей историей миграций, в той же БД PostgreSQL (прямое
   расширение [ADR-0003](ADR-0003-dva-dbcontext-razdelnye-shemy.md): было `core` + `inspector`).
   Контекст регистрируется через `IDbContextFactory` (ТС-008). Схема `public` БД СКИД в новую схему
   **переносится данными**, а не остаётся жить параллельно.

5. **Доступ — по решётке ISC.AI, fail-closed.** Каждый документ и поручение получают **гриф и
   подразделение**; выдача идёт через существующий фильтр доступа (ТБ-020/021). В СКИД такого понятия нет —
   поля закладываются в домен как обязательные (NOT NULL) и заполняются при регистрации документа.
   Поскольку боевых записей нет, «правило грифа для унаследованных документов» **не требуется вовсе** —
   это заметно снимает риск по сравнению с миграцией существующего корпуса. Сопоставление `departments`
   → подразделения ISC.AI решается при проектировании справочника. Роли СКИД
   (Admin/Manager/Inspector/Executor) отображаются в именованные политики модулей
   (`IModule.RequiredPolicy`) — закрывает отложенный пункт ADR-0016.

6. **Документы docflow ИНДЕКСИРУЮТСЯ в корпус ядра, а не ищутся «на месте».** RAG не обращается к
   доменным таблицам ни одной схемы: он работает только с индексом (`core.document` / `core.chunk` +
   векторы), куда текст попадает через существующий конвейер `IIngestionPort` с обязательными грифом и
   подразделением. Связь «домен ↔ индекс» — таблица-мостик `docflow.document_index_link`: слабая ссылка по
   значению, **без FK через границу схем** (ТО-инф-06), по образцу уже работающего
   `inspector.norm_document_link`. Следствия: (а) отдельная схема `docflow` фильтру доступа и грунтовке
   НЕ мешает — гриф и подразделение денормализованы на сам чанк, фильтр остаётся одним SQL без джойнов
   через схемы; (б) текст существует в двух местах (оригинал в хранилище docflow, фрагменты в индексе),
   поэтому гарантированное удаление (ТБ-064) обязано гасить оба; (в) переиндексация при замене версии
   опирается на существующий механизм гашения чанков (`IsCurrent` / `SupersededByDocumentId`).

7. **Идентичность остаётся по [ADR-0016](ADR-0016-skid-istochnik-identichnosti-dopusk-lokalno.md).**
   Собственный вход СКИД (`/auth/login`, cookie, свой revalidation) при слиянии **выбрасывается** — вход
   один, наш. Вопрос «кто владеет реестром пользователей после слияния» (СКИД остаётся мастером или
   реестр переезжает в ISC.AI) решается ОТДЕЛЬНОЙ записью: он затрагивает эксплуатацию, а не только код.

8. **Замены по лицензионному правилу (только MIT/Apache, ТСТ-001)** — обязательны, не обсуждаются:
   - **MediatR 12 → Mediator (martinothamar)** — ~116 обработчиков;
   - **FluentAssertions → Shouldly** — 116 тестов;
   - **QuestPDF → PDFsharp / OpenXml** (PDFsharp в СКИД уже есть) — отчёты переписываются, а не
     переименовываются: у QuestPDF декларативный layout, у PDFsharp низкоуровневый API.

9. **Данные — схема создаётся заново; переноса боевых данных нет.** Боевых записей у СКИД нет (см.
   контекст), поэтому схема `docflow` поднимается миграциями с нуля, а демонстрационные данные при
   необходимости пересоздаются сидом, а не мигрируются. Остаётся единственный организационный вопрос:
   **продолжается ли доработка репозитория `skid` параллельно** — если да, возникнут два расходящихся
   кода, поэтому после переноса репозиторий переводится в архив (см. последствия).

10. **Порядок работ — калибровочный заход первым.** Сначала скелет пакета + ОДИН модуль сквозняком
   (Domain → Data → Application → UI), затем оценка срока пересчитывается по измеренному темпу, и только
   потом остальные модули по одному (правило «сначала скелет, затем по одному модулю»).

## Последствия

- (+) Один продукт для инспектора: один вход, одно меню — «Документы» и «Поручения» рядом с
  «Чат-ассистентом» и «Генератором».
- (+) **Главный выигрыш:** ИИ (чат, грунтованная генерация, анализ, риски) работает по ЖИВЫМ документам и
  поручениям инспекции, а не по отдельной копии корпуса.
- (+) Документооборот остаётся переиспользуемым: следующий отдел подключает `docflow` в свой профиль,
  ничего не копируя.
- (+) Единый неизменяемый аудит (ТБ-030) и единая решётка доступа на оба домена.
- (−) Объём: ~38 тыс. строк переносимого кода; оценка 7–10 недель до калибровочного захода.
- (−) Пока идёт слияние, доработку функциональности разумно вести уже в новом месте — иначе появятся два
  расходящихся кода. Простоя и заморозки ради эксплуатации при этом НЕ требуется: пользователей у СКИД
  пока нет.
- (−) Третья схема данных и третий контекст — рост сложности миграций (смягчение: у каждой схемы своя
  история, как уже сделано для `core`/`inspector`).
- (!) Риск №1 — **отчёты**: замена QuestPDF не механическая; объём и сложность отчётов оцениваются в
  первом же этапе, до принятия срока.
- (!) Риск №2 — **гриф и подразделение в домене документооборота**: проектное решение режима, а не правка
  кода; требует ревью до этапа индексации (иначе в корпус попадут документы с неверной решёткой).
- (+) Риск «перенос боевых данных» **СНЯТ** — данных нет, схема создаётся с нуля. Был третьим по величине
  риском; вместе с ним отпадает и требование обратимого скрипта переноса.
- (!) `SKID.Domain`/`SKID.Application` не опубликованы как библиотеки — переносится исходный код, а не
  пакетная зависимость; после переноса репозиторий СКИД перестаёт быть источником правды по этому коду
  (иначе появится два расходящихся кода — недопустимо).
