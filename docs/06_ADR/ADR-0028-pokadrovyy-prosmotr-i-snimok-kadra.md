## Контекст

Заказчик (25.09.2026): следователю нужно **остановить видео на нужном кадре, пройти по кадрам вперёд-назад и снять
кадр** — как снимок экрана, но пригодный для дела. Сейчас карточка носителя умеет только перемотку по секундам
в браузерном `<video>` (mp4/webm), а mkv/avi/mov/3gp браузер не воспроизводит — их можно лишь скачать.

Что мешает сделать это «в лоб»:

- браузерный `<video>` не знает частоту кадров, а шаг «на один кадр» без неё невозможен; в базе частота кадров
  не хранится (`media.asset` знает только длительность, и та — по последнему кадру раскадровки);
- снимок «из браузера» (canvas) — это кадр после декодирования браузером и только для mp4/webm; для следствия
  нужен кадр **из оригинала** (ТЭ-007) и для **всех** форматов, которые принимает пакет;
- `IFileStorage` отдаёт только поток, а ffmpeg работает с путём: копировать оригинал (до 200 МБ) во временный
  файл на **каждый** шаг кадра нельзя ни по времени, ни по ТБ-064.

Проверено на живом ffmpeg (LGPL-сборка поставки, 25.09.2026): точный поиск `-ss <t>` перед `-i` выдаёт ровно
кадр `N` во всех контейнерах пакета (mp4, mkv, mov, avi, webm, 3gp), в том числе при ненулевом стартовом времени
файла; один кадр 1080p при группе кадров 10 с вырезается за ~170–200 мс; ffmpeg сам поворачивает кадр по метке
контейнера (телефонная съёмка). Метки времени в Matroska округлены до 1 мс, поэтому запрос ровно на `N/fps`
может вернуть кадр `N+1` — запрос делается на полкадра раньше.

## Решение

**Схема работы:**

```
проба ffprobe при индексации → media.asset: frame_rate, frame_width, frame_height, duration_ms (точная)
карточка носителя:
   mp4/webm  → <video> + шаг ±1/fps в браузере (кнопки ◀ ▶, клавиши , и .)
   иначе     → <img src=/media/frames/{id}?t=…> — кадр JPEG, вырезанный сервером из оригинала; те же кнопки/клавиши
«Снимок кадра» → команда → ffmpeg вырезает PNG из ОРИГИНАЛА → новый носитель (фото) в том же деле → индексация лиц
```

1. **Частота кадров — свойство носителя.** Проба ffprobe (`IFrameExtractor.ProbeAsync`) выполняется в конвейере
   индексации перед раскадровкой; `media.asset` получает `frame_rate`, `frame_width`, `frame_height` (размер после
   автоповорота) и **точную** `duration_ms` вместо таймкода последнего кадра выборки. Существующие видео получают
   их при «Переиндексировать»; пока частоты нет, шаг в интерфейсе — 40 мс (25 к/с) с явной пометкой.
   Длительность в пробе (`VideoProbe.Duration`) необязательна: незавершённые Matroska/WebM (оборванная запись,
   MediaRecorder) её не сообщают — тогда `duration_ms` пишется как есть, неизвестной (`null`): оценкой по
   раскадровке она не подменяется, ноль не пишется (он означал бы «кадров нет» и запер бы просмотр); точную
   длительность такого файла позже даёт расшифровка речи (длина звука), если она есть. Оценка по раскадровке
   (таймкод последнего кадра выборки, округлена вниз до её шага) пишется в `duration_ms` только пока частота ещё
   неизвестна, поэтому проверка «момент за концом записи» в эндпоинте и команде снимка выполняется до ffmpeg
   только при известной частоте кадров (длительность точная, от пробы); иначе решает ffmpeg — за концом он кадра
   не отдаёт. Переиндексация со сбойной пробой точную длительность оценкой не перетирает.
2. **Номер кадра — новое понятие, отдельное от индекса раскадровки.** `N = round(t · fps)` считается в одном месте
   (`VideoProbe.FrameIndexAt`); в интерфейсе подпись «кадр № N при F к/с, hh:mm:ss.mmm». Индексы раскадровки
   (`media.frame.index`, «кадр N» в карточке фигуранта и в аудите поиска) — индексы **выборки** при `Media:Video:SampleFps`,
   их смысл, подписи и историю (ТБ-072) не меняем.
3. **Шаг по кадрам.** Для mp4/webm — в браузере: `currentTime = (N + 0,5)/fps` (середина кадра, устойчиво к
   округлению), без обращения к серверу. Для остальных контейнеров — серверный просмотрщик: `GET /media/frames/{assetId}?t=<мс>`
   отдаёт JPEG кадра (наибольшая сторона 1920, качество 2) с теми же проверками, что у файла носителя: аутентификация,
   решётка ТБ-020/021 на строке носителя, сужение по делам `ICaseScope.IsAssetAccessibleAsync`, единый 404, `nosniff`.
   Момент для ffmpeg — `VideoProbe.SeekTimeFor(N, fps)` = `(N − 0,5)/fps`.
4. **Оригинал читается на месте.** Новый нейтральный порт ядра `ILocalFileLocator.TryGetLocalPath` (реализует
   `LocalFileStorage` с той же защитой «под корнем») даёт ffmpeg путь к оригиналу **только на чтение**, без копии.
   Хранилище без локальных путей возвращает `null`, и вызывающий работает через временную копию (`MediaTempFiles`).
   Дискового кэша кадров нет: кадр вырезается по запросу (ДОК-13 §13: «кадры извлекаются по таймкоду при показе»).
5. **Снимок кадра — новый носитель, а не файл в загрузках.** Команда `SnapshotFrameCommand(assetId, t)`:
   право `IMediaAdministration.CanUploadAsync` → носитель доступен и это видео → дело источника
   (`ICaseScope.GetCaseIdForAssetAsync`) → PNG кадра `N` из оригинала без пересжатия и обработки (ТЭ-007), автоповорот
   по метке контейнера — единственное преобразование, и оно названо в реквизитах → `IMediaStore.ReceiveAsync`
   с `Kind = Image`, грифом и подразделением **источника** (равны делу, ТБ-070), `CapturedAt = съёмка источника + t`
   (если известна), `Source = «снимок кадра № N (hh:mm:ss.mmm) из носителя № X»`, `SourceAssetId`/`SourceTimestampMs`
   → привязка к делу источника → фоновая индексация лиц как у загруженного фото. Итог — снимок ищется по лицу, годится
   в эталон фигуранта, уничтожается вместе с делом (ADR-0025: исключительный носитель дела) и снимается с
   биометрии при закрытии (ТБ-074) — без доработок этих сценариев. «Скачать» — вторично: обычная ссылка на оригинал
   нового носителя.
6. **Происхождение — в данных.** `media.asset.source_asset_id` (слабая ссылка, без FK — как `uploaded_by_user_id`) и
   `source_timestamp_ms`. Уничтожение видео снимок **не** трогает и наоборот: у каждого носителя своя запись
   журнала и свой акт (ТБ-064/075); FK с каскадом сделал бы удаление снимка «безмолвным».
7. **Дедупликация (ТНД-002).** Тот же кадр того же оригинала даёт те же байты → `ReceiveAsync` вернёт существующий
   носитель (`Duplicate`), команда привяжет его к делу и сообщит «такой кадр уже есть в деле, носитель № N». Кнопка
   в интерфейсе заблокирована на время команды (двойной щелчок — не гонка уникального индекса).
8. **Аудит (ТБ-030).** Команда — `IAuditableRequest` (`Ingest`, «кто и что запросил»); дополнительно запись с
   `ObjectRef = media:asset:{new}:snapshot`, грифом и подразделением носителя и текстом «кадр № N (hh:mm:ss.mmm) из
   носителя № X; PNG из оригинала, автоповорот по метке контейнера». Просмотр кадров с сервера — событие `View` с
   `ObjectRef = media:frames:{assetId}` под тем же дросселем, что у Range-продолжений видео (одна запись на носитель в
   5 минут): запись на каждый кадр раздула бы журнал и словарь дросселя впустую.
9. **Закрытое дело (ТБ-074).** Снимок в закрытом деле создаётся как и загрузка фото сегодня; индексация лиц при
   политике `PurgeTemplatesOnCaseClosure` отказывает так же, как для загруженного фото. Это существующий пробел
   загрузки (носитель остаётся «загружен» без пояснения), он общий и здесь не расширяется — отдельная задача.
10. **Переходы к кадру.** «К кадру» в таблице лиц и щелчок по фрагменту расшифровки работают и для серверного
    просмотрщика: панель расшифровки получает обратный вызов `OnSeekRequested` помимо `id` элемента проигрывателя.

**Не в этом шаге:** водяной знак на кадре при выдаче (ТБ-076 — общий для всех изображений пакета, пока не
реализован); кэш вырезанных кадров; покадровый просмотр по номеру кадра для VFR-записей (шаг приблизителен).

## Последствия

- Миграция `media`: пять новых nullable-столбцов у `asset`; существующие строки — `null`, заполняются переиндексацией.
- Ядро получает один нейтральный порт (`ILocalFileLocator`), профиль-нейтральный и необязательный; правило
  зависимостей не меняется (`DependencyRulesTests`).
- Каждый шаг кадра для mkv/avi/mov/3gp — один запуск ffmpeg (~0,2 с на 1080p). Проверки доступа защищают от
  чтения чужого материала, а не от перегрузки, поэтому нагрузка ограничена тремя рубежами: (а) общий предел
  одновременных процессов вырезки кадра **и** пробы в интеграции — `Vision:Ffmpeg:MaxConcurrentFrameExtractions`,
  по умолчанию `max(1, ядер/2)`; раскадровка при индексации предела не имеет (фоновая, по одной задаче); ожидание
  свободного процесса — в пределах общего дедлайна 60 с, сверх — ошибка «Сервер занят вырезкой кадров…» с
  указанием предела и ключа, а не бесконечная очередь; (б) лимитер на эндпоинт кадра — политика `media-frames`
  (`MediaFrameRateLimitPolicy`): `ConcurrencyLimiter`, не больше 2 одновременных запросов, очередь 4 (старые —
  первыми), сверх — 429 без тела (ответ не зависит от существования носителя, ТБ-021 соблюдено); ключ партиции —
  субъект, если он аутентифицирован к моменту лимитера, иначе адрес клиента; в хосте `UseRateLimiter` стоит **до**
  `UseAuthentication`, поэтому фактически ключ — адрес клиента (за прокси — через `UseForwardedHeaders`); в
  dev-режиме без аутентификации лимитера нет; (в) интерфейс не запрашивает следующий кадр с сервера, пока не
  загрузился предыдущий (автоповтор клавиши запросов не плодит); при ошибке загрузки — подпись «кадра нет» и откат
  на прежний момент.
- Тесты: проба и вырезка кадра — интеграционные (`Category=Video`, синтетика `testsrc`, шесть контейнеров — mp4, mkv, mov, avi, webm, 3gp, поворот,
  NTSC 29,97); команда снимка — юнит (NSubstitute) + интеграционный `tests/ISC.AI.IntegrationTests/Persistence/MediaSnapshotTests.cs`
  (Testcontainers: привязка к делу источника, гриф/подразделение, происхождение, оригинал читается на месте, дедуп без
  второй строки, аудит на новый носитель, чужой субъект — NotFound; видео без пробы — запасная проба, хвост записи
  достижим, за точной длительностью — отказ до ffmpeg); эндпоинт кадра — резолв/решётка/аудит;
  интерфейс — bUnit.

## Альтернативы

**Снимок из браузера (canvas).** Отвергнуто: кадр после декодирования браузером, только mp4/webm, файл уходит в
загрузки пользователя мимо дела, журнала и решётки.

**Полная копия оригинала на каждый кадр.** Отвергнуто: до 200 МБ на нажатие клавиши и лишние копии материала
дела (ТБ-064). Порт локального пути — минимальное изменение ядра.

**Извлечение всех кадров заранее (кэш).** Отвергнуто: объём (часы видео × 25 к/с), лишние копии материала,
отдельный жизненный цикл при уничтожении. Вырезка по запросу за ~0,2 с достаточна.
