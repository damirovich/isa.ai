## Контекст

Расшифровка (ADR-0026) — фрагменты речи с таймкодами без говорящих. ТЗ [АИС ФТ-5.8.3] и решение Заказчика (вопрос 11,
17.10.2026) требуют разметки реплик «Диктор 1», «Диктор 2» и правки этой разметки сотрудником без изменения дословного
текста. Записи: телефонные звонки (часть, возможно, в стерео — абонент в своём канале; Заказчик не уверен), диктофон,
голосовые сообщения, звук видео.

## Решение

### Модели и лицензии (ТСТ-004) — выбор 22.10.2026

- **Сегментация «где кто говорит»** (v0.1–0.2; с v0.3 не используется — см. ниже) — pyannote/segmentation-3.0, **MIT** (Hugging Face, скачивание с согласием передать
  контакты; ограничений использования нет); файл ONNX — релиз sherpa-onnx `speaker-segmentation-models`
  (`sherpa-onnx-pyannote-segmentation-3-0.tar.bz2`, ~6,6 МБ).
- **«Голосовой отпечаток» говорящего** — CAM++ из 3D-Speaker (`speech_campplus_sv_zh_en_16k-common_advanced`),
  **Apache-2.0** (ModelScope); файл ONNX — релиз sherpa-onnx `speaker-recongition-models` (~27 МБ).
- **Движок** (v0.1–0.2; с v0.3 — `SpeakerEmbeddingExtractor` и своя группировка) — `OfflineSpeakerDiarization` той же sherpa-onnx 1.13.8 (Apache-2.0), что уже распознаёт речь: новых
  зависимостей нет, разделение идёт в том же отдельном процессе.
- **Отвергнуто:** Reverb diarization (некоммерческая лицензия); WeSpeaker (VoxCeleb) и NVIDIA TitaNet (CC-BY-4.0 — не
  MIT/Apache).
- **Пины SHA-256** — в конфигурации, как у модели речи (ТИ-004); у этих файлов в API GitHub хеша нет, поэтому пины
  закреплены в скрипте поставки по первой проверенной выгрузке 22.10.2026 (размеры совпали с API релизов; в архиве
  сегментации — лицензия MIT, © CNRS).
- **Риск качества:** модель отпечатков обучена на китайской и английской речи; на русско-кыргызской и телефонной (8 кГц)
  речи никем не измерена — проверка на пилоте (КИ-10). Модель меняется заменой файла и пина.

### Два режима разметки

1. **Стерео по каналам.** Если у записи два канала и они различаются (у каждого абонента свой), реплики определяются
   громкостью каналов (окна 100 мс; канал громче другого в 4 раза и выше порога тишины — говорит его абонент). Это
   точно и без модели. Каналы-копии (моно, записанное в два канала) распознаются и уходят в режим 2. Анализ делает
   адаптер потоком по файлу 8 кГц, без загрузки записи в память.
2. **Моделью.** Иначе — `OfflineSpeakerDiarization` по всей записи: число дикторов — из настройки
   (`Speech:Speakers:Count`, 0 — определяется само по порогу `Speech:Speakers:Threshold`). Модели нужна вся запись в
   памяти, поэтому запись длиннее `Speech:Speakers:MaxMinutes` (по умолчанию 120 мин) не размечается — расшифровка
   остаётся, а у неё пометка «дикторы не размечены: запись длиннее …». Сбой разметки расшифровку не роняет — та же
   пометка с причиной.

Модели говорящих не заданы в конфигурации — разметки нет, расшифровка как прежде (ничего не ломается).

### Протокол процесса-распознавателя

Новые необязательные ключи `--speaker-segmentation`, `--speaker-embedding` (только вместе), `--speakers N`,
`--speaker-threshold`, `--speaker-max-minutes`. После фрагментов процесс выводит строки реплик
`{"type":"turn","startMs":…,"endMs":…,"speaker":k}`; в строке `done` — `"diarization":"done|skipped|failed"` и при
пропуске или сбое — причина без содержимого записи. Адаптер приписывает каждому фрагменту диктора с наибольшим
перекрытием по времени (без перекрытия — без диктора) и нумерует дикторов по первому появлению: 1, 2, 3…

### Хранение и слой правок (ТЭ-007)

- **Автоматическая разметка** — `media.transcript_segment.speaker` (номер диктора, неизменяемый слой прогона).
- **Правки сотрудника** — слоем поверх:
  - переименовать диктора («Диктор 1 → объект») и объединить дикторов — таблица `media.transcript_speaker`
    (носитель, номер, имя, «слит в», кто и когда правил);
  - перенести реплику к другому диктору — `transcript_segment.speaker_override` (кто и когда).
  Действующий диктор реплики — перенос, иначе автоматический, затем по цепочке объединений; подпись — имя, иначе
  «Диктор N». **Дословный текст не меняется никогда.**
- Повторная расшифровка заменяет фрагменты и разметку целиком — правки прежнего прогона к новым фрагментам не
  относятся и сбрасываются (как и сами фрагменты).
- Гриф и подразделение дикторов — носителя (имя диктора может быть ФИО — та же решётка, ТБ-020).

### Команды и права

- «Переименовать диктора», «Объединить дикторов», «Перенести реплику» — право как у повторной расшифровки (загрузка
  материалов: Следователь и Администратор), носитель под решёткой и в делах субъекта (ТБ-071); недоступный —
  неотличим от несуществующего.
- **Журнал (ТБ-030/032):** каждая правка — `Modify` с номером носителя и дикторов, без имён (имя может быть ФИО).

### Экран и выгрузка (ТФ-МЕД-08/18)

- Панель расшифровки: у каждой реплики — подпись диктора своим цветом; полоса «Дикторы» — имена, «переименовать»,
  «объединить с…»; у реплики — «перенести к диктору…». Пометка, если дикторы не размечены, и почему.
- Режим «Текстом» — абзацы по репликам: подряд идущие фрагменты одного диктора — один абзац с его подписью.
- Выгрузка в Word — по репликам: «Диктор 1 [00:12]: …».

### v0.2 — число говорящих и «Диктор ?» (22.10.2026)

**Проверка на записи из дев-базы** (видео с телефона, 47 с, двухканальный звук с одинаковыми каналами — ушёл модели,
верно): по порогу 0,5 модель выдала 5 дикторов, большая часть рассказа — явно один голос. Причина — «отпечатки» CAM++ на
коротких (0,5–4 с) зашумлённых кусках с эхом нестабильны, и одного человека модель режет на нескольких. Повысить порог
нельзя: при 0,9 два заведомо разных голоса синтетического диалога уже сливаются в одного, а на этой записи всё ещё
5 дикторов — единого порога для обоих случаев нет. С заданным числом 2 разметка правдоподобна (рассказ — Диктор 1,
короткая реплика другого голоса — Диктор 2). **Решение:**

- **Число говорящих задаёт сотрудник** при повторной расшифровке: в полосе «Дикторы» — «Говорящих: авто / 1–6» и
  «Расшифровать заново» (`RetranscribeMediaCommand.Speakers`, 1–20; в журнале запуска — `:speakers=N`, в журнале
  расшифровки — «говорящих задано N»). Число едет с задачей в очереди, в базе не хранится (при перезапуске хоста задача
  и так помечается прерванной). Стерео по каналам — только при «авто» или 2: каналов два, значит и абонентов двое; иное
  число — разметка моделью с этим числом. Порог по умолчанию остаётся 0,5: лишнего диктора сотрудник объединяет в два
  щелчка, а разделить слитого — значит переносить реплики по одной.
- **«Диктор ?»** — подпись реплики, которой диктор не достался (её услышал детектор речи распознавателя, но не модель
  разметки: тихо, коротко). Раньше такая реплика шла без подписи и выглядела сбоем; теперь видна и переносится к нужному
  диктору. Без разметки (запись не размечалась) подписей нет, как прежде.

### v0.3 — разметка по целым репликам, включение и выключение дикторов (22.10.2026)

**Почему.** Заказчику не понравилось, как система определяет дикторов. Опыт на тех же записях: «отпечаток» CAM++ по
целой реплике распознавателя (2–6 с) против отпечатков кусков сегментации pyannote (0,5 с):

| Запись | pyannote + `OfflineSpeakerDiarization` | По целым репликам |
|---|---|---|
| Синтетический диалог, 2 голоса, 14 реплик | верно | верно, 14 из 14 |
| Видео с телефона из дев-базы, 47 с | 5 дикторов, рассказ одного человека порван на 4 | рассказ — один диктор; две короткие реплики другими голосами — отдельно (3) |
| То же, «говорящих: 2» | — | рассказ — Диктор 1, «эң сонун» — Диктор 2 |

Разметка — 0,5 с вместо 1,8 с; у каждой реплики свой отпечаток, поэтому «Диктор ?» при разметке моделью не возникает.

**Как.** После распознавания процесс-распознаватель считает отпечаток CAM++ (`SpeakerEmbeddingExtractor`) каждого
записанного фрагмента — звук читается потоком, в памяти только текущая реплика — и группирует реплики агломеративно со
средней связью по косинусному сходству (`SpeakerClustering`): пока сходство групп выше порога
`Speech:Speakers:Threshold` (по умолчанию **0,4**, допустимо 0,05–0,95) либо до заданного числа говорящих. Реплики короче
0,5 с групп не заводят — примыкают к самой похожей; реплика без отпечатка (слишком коротка для модели) берёт диктора
соседней. Строка `turn` протокола — ровно участок фрагмента, адаптер не меняется. Модель pyannote, ключи
`Speech:Speakers:Segmentation:*` и `--speaker-segmentation` убраны; поставка — один файл CAM++ (~27 МБ).
**Ограничение:** если двое говорят без паузы и распознаватель склеил их в одну реплику, она достаётся одному диктору.

**Включение и выключение.**
- **Общая настройка Администратора** «Размечать дикторов при расшифровке загруженных материалов» — экран «Настройки
  поиска и верификации», переключатель сохраняется сразу (`SetTranscriptSpeakersCommand`; право и журнал «было → стало»
  — как у настроек поиска; отказ без права — тоже в журнале). Хранение — `media.setting`, ключ `transcription.speakers`,
  запасной ключ конфигурации `Media:Transcription:Speakers`; по умолчанию — размечать. Действует на расшифровку при
  загрузке (конвейер читает её, когда сотрудник не выбирал).
- **При «Расшифровать заново»** сотрудник выбирает у кнопки «Дикторы: без дикторов / авто / 1–6 говорящих»
  (`RetranscribeMediaCommand.Speakers` — `SpeakerMarkupRequest`; журнал запуска — `:speakers=off|auto|N`, журнал
  расшифровки — «дикторы не размечались» / «говорящих задано N»). «Без дикторов» — ни каналов стерео, ни модели.
  Выбор числа из полосы «Дикторы» (v0.2) перенесён к кнопке — одно место.
- Без миграций (ключ настроек — строка существующей таблицы).

## Последствия

- Миграция `media` `TranscriptSpeakers`: столбцы фрагментов и носителя, таблица `media.transcript_speaker`.
- Для разметки уже расшифрованных записей — «Расшифровать заново».
- Поставка: два файла моделей (~34 МБ) рядом с моделями речи (`export-speech-models.ps1 -Speakers`; пины закрепляются в
  скрипте после первой проверенной выгрузки), ключи `Speech:Speakers:*`.
- Поиск по расшифровкам и чат по материалам работают с текстом как прежде; дикторы в них не участвуют.
