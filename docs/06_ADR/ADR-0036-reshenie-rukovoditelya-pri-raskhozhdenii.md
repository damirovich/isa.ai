## Контекст

Если эксперт и верификатор разошлись (или кто-то из них сказал «неопределённо»), кандидат получает статус
«неопределённо — к руководителю». ТФ-ВЕР-02 требует, чтобы такой результат попадал в очередь руководителя, но
очереди не было: кандидаты зависали без итога. С автопредложением фигурантов (ADR-0035) их станет больше.

Ограничения: ТБ-073 — «подтверждён» только после независимых положительных решений двух разных сотрудников;
слепота верификатора (ТФ-ВЕР-02) не должна ослабнуть; все решения и отказы — в журнале (ТБ-072).

## Решение

1. **Третья стадия.** `VerificationStage.Supervisor` — решение руководителя. Хранится как обычное решение стадии
   (`media.verification_decision`): уникальный индекс «кандидат × стадия» даёт одно решение руководителя на кандидата.
   Миграция не нужна — стадия хранится числом.
2. **Когда и кто.** Только по кандидату со статусом «неопределённо» (оба решения уже есть) и только **третьим лицом**:
   эксперт и верификатор этого кандидата итог не выносят. Право — новая строка матрицы доступа
   «Верификация — решение при расхождении» (`verification.resolve`), по умолчанию Руководитель и Администратор.
3. **Какой итог.** «Отклонён» — всегда. «Подтверждён» — **только если эксперт или верификатор (другой сотрудник)
   уже сказал «подтверждён»**: тогда у результата два положительных решения разных людей, как требует ТБ-073. Если
   никто из двоих не подтвердил, подтвердить нельзя — только отклонить. «Неопределённо» руководителю недоступно:
   его задача — снять неопределённость. Правило — в модуле (`TwoPersonRule.Resolve`, `CanDecide`,
   `CanSupervisorDecide`), профиль его не ослабляет.
4. **Фигурант.** Руководитель видит фигуранта, которого привязал эксперт, и может выбрать другого фигуранта того же
   дела. При «подтверждён» фигурант обязателен (ТФ-ВЕР-03).
5. **Появление (ТФ-ПЕР-02).** При итоге «подтверждён» создаётся появление: первая подпись — тот, кто подтвердил (эксперт,
   иначе верификатор), вторая — руководитель. Отзыв такого появления подчиняется ADR-0034 (его подписавшие не отзывают).
6. **Слепота не ослабляется.** Общая проекция очереди (`VerificationQueueItem`) остаётся структурно слепой — без чужих
   решений и привязки. Решения сотрудников руководитель получает отдельным запросом (`GetSupervisorReviewQuery`) и
   только когда оба решения уже записаны: иначе сотрудник с правами и руководителя, и верификатора (Администратор)
   увидел бы решение эксперта до своей «слепой» проверки.
7. **Экраны.** В «Верификации кандидатов» — вкладка «Руководитель» (кандидаты «неопределённо»); на странице решения —
   оба решения с обоснованиями, привязанный фигурант, выбор «подтверждён» (недоступен без положительного решения)
   или «отклонён», обоснование обязательно.
8. **Аудит (ТБ-072).** Решение — `media:candidate:{id}:decision:Supervisor` с вердиктами и субъектами эксперта,
   верификатора и руководителя; отказы (нет права, не «неопределённо», сам решал, «подтверждён» без второй подписи) —
   `…:decision-denied`; открытие обзора решений — `media:candidate:{id}:supervisor-review`.

## Последствия

- **Плюсы.** Спорные кандидаты получают итог; правило двух лиц сохраняется буквально; слепота второй проверки не
  ослаблена.
- **Минусы.** Если ни эксперт, ни верификатор не подтвердили, руководитель не может подтвердить сам — нужен новый поиск
  и новая двойная проверка. Это осознанно: одно положительное решение не даёт статуса ни при какой роли.
- **Не сделано.** Метрики расхождений для руководителя (ТФ-ВЕР-05); уведомление руководителю о новом спорном кандидате.
