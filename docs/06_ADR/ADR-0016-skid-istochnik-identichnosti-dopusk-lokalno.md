> ## ✅ Примечание о завершении перехода (2026-08-07)
>
> Переход выполнен (задача [Э4-35](../tasks/Э4-35-слияние-скид-документооборот.md), §6.5). Фактическое
> состояние системы:
>
> - идентичность **ЛОКАЛЬНАЯ**: пароль проверяется по `core.app_user` (Argon2id/PHC — тот же формат,
>   что у СКИД, поэтому перенесённые учётки вошли прежними паролями);
> - из решения **выведены**: проект `ISC.AI.Identity.Skid`, консольный перенос учёток, строка
>   `ConnectionStrings:Skid`, секрет `Database:Passwords:Skid`. Ссылок на БД СКИД в коде
>   и конфигурации не осталось;
> - порт `IExternalIdentityProvider` **сохранён** — это шов под будущий SSO; вход, cookie, штамп
>   безопасности и ревалидация сессий за весь переход не переписывались;
> - учётка по умолчанию заводится засевом на ПУСТОМ реестре с ВРЕМЕННЫМ паролем из конфигурации
>   (решение заказчика 2026-08-07): до смены система никуда не пускает, а смена делает пароль из
>   конфигурации недействительным. Резервный путь — команда хоста `create-account`.
>
> Всё, что ниже, — исторический контекст решения на момент его принятия; читать как запись, а не как
> описание действующей системы.
>
> ## ⚠️ Примечание о частичной замене (2026-08-05)
>
> Принято решение влить СКИД в ISC.AI пакетом модулей документооборота ([ADR-0017](ADR-0017-skid-modul-dokumentooborota-ne-profil.md),
> задача [Э4-35](../tasks/Э4-35-слияние-скид-документооборот.md)). После слияния СКИД перестаёт быть
> **внешней** системой, поэтому:
>
> - **перестают действовать** (с этапом 6 задачи Э4-35): п.1 — чтение чужой БД `public.users`/
>   `public.departments` read-only учёткой `iscai_ro`; п.6 — адаптер `ISC.AI.Identity.Skid` как отдельный
>   проект интеграции. Реестр пользователей переезжает в ISC.AI, порт `IExternalIdentityProvider`
>   сохраняется, но получает локальную реализацию; секрет `Database:Passwords:Skid` и строка
>   `ConnectionStrings:Skid` выводятся;
> - **остаются в силе**: п.2 (привязка по стабильному идентификатору, никогда по имени входа), п.3/4
>   (допуск ведётся отдельно, default-deny, читается на каждую операцию и НЕ выводится из учётки — это
>   режимный инвариант ТБ-012, он не зависит от того, локальна идентичность или нет), п.5 (ревалидация
>   сессий по security stamp), п.7 (троттлинг входа), п.8 (аудит входа fail-closed), п.9/10 (рендер-режим
>   и сокрытие состава модулей от анонимов).
>
> **До завершения этапа 6 запись действует полностью** — сегодня вход работает именно так, как описано ниже.

## Контекст

До Э3-08 контекст доступа выдавала dev-заглушка: вход не разграничен, режимный контроль формально не
действовал (P0-блокер). Документация оставляла выбор провайдера идентификации открытым (ДОК-05
«Открытые вопросы» п.8). У заказчика уже эксплуатируется СКИД — ведомственная система с БД пользователей
(логин, Argon2id-хеш пароля, ФИО, роль, подразделение, блокировка, security stamp), исходный код доступен.
Отдельного IdP/SSO в контуре нет; заводить второй реестр пользователей — двойное ведение и рассинхрон.

## Решение

**СКИД — единственный источник ИДЕНТИЧНОСТИ (кто ты); ISC.AI — единственный источник ДОПУСКА (что тебе можно).**

1. **Вход по учёткам СКИД.** ISC.AI читает `public.users`/`public.departments` БД СКИД **только на
   чтение** (выделенная учётка `iscai_ro`, read-only на уровне GRANT — заявлена в конфиге; фактическую
   выдачу прав выполняет администратор СКИД) и проверяет пароль по Argon2id PHC-строке той же
   библиотекой (Sodium.Core/libsodium), которой СКИД хеширует. API у СКИД нет — прямое чтение БД
   зафиксировано как канал интеграции; стабильность схемы — предмет договорённости. Пароль этого
   подключения — ОБЯЗАТЕЛЬНО отдельный секрет `Database:Passwords:Skid`
   (`ConnectionStringResolver.ResolveExternal`): в отличие от Core/Inspector общий `Database:Password`
   сюда **никогда** не подставляется даже молча — забытый секрет обязан быть явным отказом на старте,
   а не утечкой пароля БД `ISC_AI` на сторонний сервер.
2. **Привязка локального субъекта к внешней учётке — СТРОГО по внешнему идентификатору, никогда по
   имени входа.** СКИД может переиспользовать логин (увольнение → новый сотрудник с тем же login,
   переименование, коллизия однофамильцев) — привязка «по совпадению UserName» отдала бы новому
   человеку допуск прежнего владельца логина в обход default-deny. Если по внешнему id совпадения нет,
   а имя входа уже занято другой локальной учёткой — вход отклоняется явным конфликтом (единый отказ +
   аудит), переподключение выполняет администратор. *(Найдено адверсариальным ревью реализации; было
   обратное — привязка по `ExternalId == … || UserName == …` — до фикса.)*
3. **Допуск — локально и default-deny.** В СКИД понятия грифа/допуска нет. Допуск (потолок грифа +
   разрешённые подразделения) живёт в `core.clearance`; при первом входе локальная учётка создаётся
   **без допуска** — retrieval невозможен, пока администратор не назначит допуск явно (ТБ-012).
4. **Допуск читается на каждую операцию** (`ClearanceAccessReader`), не кэшируется в cookie/сессии:
   отзыв (мягкое удаление записи допуска) или деактивация пользователя действуют для retrieval
   немедленно (ТБ-016). Cookie несёт только идентификацию (id, логин, внешний id, security stamp,
   отметка последней ревалидации) — САМ допуск в клеймы не кладётся.
5. **Сессии — ДВЕ независимые линии ревалидации** (ТБ-014/016), обе через общий
   `ExternalIdentityRevalidator`, чтобы решение не расходилось:
   - **Cookie-уровень** (`CookiePrincipalValidator.OnValidatePrincipal`) — раз в
     `Auth:RevalidationMinutes` минут на каждый HTTP-запрос гасит САМУ cookie при расхождении. Без неё
     блокировка не гасила бы уже выданную cookie: перезагрузка страницы поднимала бы НОВЫЙ Blazor-circuit
     со своим окном ревалидации, продлевая доступ заблокированного пользователя неограниченно.
   - **Circuit-уровень** (`StampRevalidatingAuthenticationStateProvider`) — быстрее реагирует, пока
     конкретная вкладка открыта (Blazor Server держит состояние на сервере).
   - Транзиентная недоступность внешней системы (сеть/БД СКИД) при ревалидации — **НЕ** приравнивается
     к «учётка недействительна» (`RevalidationOutcome.Unavailable` ≠ `Invalid`): иначе кратковременный
     сбой БД СКИД массово разлогинивает всех живых пользователей. Реальный контроль доступа при этом не
     ослабляется — допуск (п.4) читается из своей БД независимо и остаётся fail-closed сам по себе.
   - Отзыв ДОПУСКА действует немедленно всегда (п.4), не завися от окна ревалидации сессии.
6. **Ядро о СКИД не знает.** В `Abstractions` — нейтральный порт `IExternalIdentityProvider`
   (проверка кредов + состояние учётки). Адаптер — отдельный проект `src/integrations/ISC.AI.Identity.Skid`,
   подключает только хост (та же логика, что с профилем). Любой будущий профиль/контур может подставить
   другой источник идентичности, не трогая ядро.
7. **Троттлинг входа на нашей стороне** (fixed-window по IP, 5/мин): в СКИД защиты от перебора нет.
   Причины отказа входа наружу не различаются; при неизвестном логине выполняется холостая
   Argon2-проверка (выравнивание времени — тот же класс утечек, что timing-канал GATE-1). За обратным
   прокси контура IP без настройки — это IP самого прокси (общий лимит на всех); опционален конфиг
   `ForwardedHeaders:KnownProxies` — без него поведение не меняется (заголовку не доверяют).
8. **Вход — аудируемое событие** (ТБ-030, `AuditAction.Login`), запись fail-closed: не записался
   журнал — входа нет. Фиксируются и успех, и отказ (в т.ч. конфликт привязки п.2). Недоступность самой
   внешней системы при попытке входа — отдельная ветка (не аудируется как попытка входа: проверка
   учётных данных не состоялась), пользователь получает нейтральное сообщение «сервис недоступен».
9. **Рендер-режим страниц — ПОКОМПОНЕНТНО, не глобально.** Анонимные страницы (`/login`,
   `/access-denied`, `/Error`, `/not-found`) намеренно остаются статичными (SSR + обычные HTML-формы);
   защищённые страницы модулей объявляют `@rendermode="InteractiveServer"` сами. Если задать интерактивный
   режим глобально на `<Routes>`, анонимный SignalR-негошиейт (`/_blazor`) блокируется фолбэк-политикой
   «только аутентифицированные» (она распространяется на ВСЕ endpoint'ы, включая circuit-хаб) — бесконечные
   401-ретраи на странице входа. Задокументировано Microsoft как известное взаимодействие global fallback
   policy + Blazor render mode; альтернатива «анонимный `/_blazor`» отклонена — она сняла бы фолбэк-защиту
   со всех страниц разом, а не только с хаба.
10. **`MainLayout` не раскрывает состав модулей анонимам.** Название профиля/подзаголовок и `NavMenu`
    рендерятся только внутри `<AuthorizeView><Authorized>` — иначе анонимные страницы, использующие этот
    layout (`/not-found`, `/Error`), выдавали бы структуру режимной системы до входа.

## Последствия

- (+) Один реестр пользователей на два продукта (СКИД и ISC.AI); блокировка в СКИД гасит и ISC.AI
  (в пределах окна ревалидации — до `Auth:RevalidationMinutes` минут).
- (+) Решётка «гриф × подразделение» полностью под контролем режима ISC.AI; default-deny по построению.
- (−) Зависимость от схемы БД СКИД (смягчение: read-only проекция двух таблиц + security stamp).
- (−) Пароль подключения к БД СКИД — ещё один секрет (`Database:Passwords:Skid`, per-name резолв,
  обязателен явно — фолбэка на общий секрет НЕТ).
- (!) Лицензии: Sodium.Core — MIT; нативный libsodium — ISC (пермиссивная, класс MIT/BSD) — фиксируется
  в реестре компонентов (ТСТ-001).
- (!) Роль пользователя СКИД (Admin/Manager/Inspector/Executor) пока НЕ маппится в политики ISC.AI —
  все модули профиля требуют одну политику «аутентифицирован»; ролевые политики — при переходе к
  мультипользовательской фазе Ф3 (ТП-001).
- (!) `DepartmentCode` из СКИД читается при входе, но НИКАК не влияет на допуск — задел на будущее
  (например, подсказка администратору при назначении `DivisionScope`), не источник авторизации; явно
  оговорено в XML-doc `SkidExternalIdentityProvider`, чтобы не создавалось ложного впечатления.
- (!) Временный пароль СКИД (`must_change_password` — выдача/сброс администратором) не принимается для
  входа в ISC.AI: пользователь обязан сначала сменить пароль в самой СКИД. Иначе временный пароль,
  известный администратору СКИД, был бы боковой дверью в ISC.AI под чужой атрибуцией в аудите.
- (!) 2FA — точка расширения, заблокирована неопределённым классом защищённости (ТБ-061, ADR-0009).
- (!) Требует выделенную read-only учётку БД СКИД (`iscai_ro`, `GRANT SELECT` на `public.users`/
  `public.departments`) — организационное действие администратора СКИД, не автоматизируется кодом.
