## Контекст

Шаблон лица — L2-нормированный вектор фиксированной размерности (SFace: 128). Эталонная база — до 1 млн
шаблонов (ТН-005); поиск должен укладываться в p95 ≤ 5 с (ТН-006) и **не пропускать** существующее
совпадение (ЦС-02). Инцидент 26.08.2026 на `core.embedding` показал: HNSW с параметрами по умолчанию
теряет «острова» графа — малые группы непохожих векторов; документ есть, точный скан находит, индексный —
нет, даже при `ef_search=1000`. Лечит только пара `ef_construction=512` при сборке + `ef_search=200` на
транзакцию поиска. Для лиц ситуация ровно такая: редкое лицо среди тысяч чужих — это остров.

## Решение

1. **Метрика — косинусная** (`vector_cosine_ops`, оператор `<=>`), единообразно с ядром; на нормированных векторах эквивалентна скалярному произведению. Оператор запроса обязан совпадать с opclass индекса, иначе seq-scan.
2. **HNSW `m=16, ef_construction=512`** при сборке и `SELECT set_config('hnsw.ef_search', 200, true)` в явной транзакции на каждый поиск — те же значения, что закреплены для ядра после инцидента. Проба полноты после массовой загрузки/миграции/смены модели — по методике платформы (точный топ-K с `enable_indexscan=off` против индексного; критерий — пересечение ≥ K−1 и совпадение топ-1).
3. **Pre-filter решётки в той же строке, что и вектор**: `classification`, `division_id`, `is_current`, `quality_acceptable` денормализованы на `media.face_template` (NOT NULL); `WHERE` floor'а ядра ∧ политика профиля ∧ актуальность ∧ пригодность стоит **до** оператора расстояния — шаблоны вне допуска не участвуют даже в ранжировании; B-tree `(classification, division_id)` рядом с HNSW. Без `AccessContext` — исключение, не поиск без фильтра.
4. **Область поиска — после решётки, не вместо неё**: `FaceSearchQuery.AssetIds` (носители дел субъекта, ТБ-071/ТФ-ПЛ-05) сужает уже отфильтрованный набор; пустая область — пустая выдача.
5. **Размерность — константа сущности** (`FaceTemplate.Dimensions = 128`, тип столбца `vector(128)`), как `EmbeddingEntity.Dimensions` в ядре: смена модели = миграция + полная переиндексация; баллы привязаны к `model_version` (ТО-мат-09).
6. **Режим выдачи — investigation** (ISO/IEC 19795): кандидат-лист фиксированной длины (5..50, по умолчанию 20; ТН-008), порог — индикатор, который пользователь не может ослабить сверх потолка конфигурации (ТФ-ПЛ-06).

Отклонено: post-filter (сначала ANN, затем фильтр) — при узком допуске выдача пустеет и утекает факт наличия; фильтр по делам через `IAccessPolicy` (синхронный, одноконтекстный, `IN` на тысячи id в предикате) — вместо него явная область `AssetIds`.

## Изменения v0.2 (02.11.2026)

**Что обнаружено.** Пункт 3 выполняется по смыслу выдачи (недоступный шаблон в неё не попадает), но не по
порядку работы индекса: обход HNSW отдаёт `ef_search` ближайших по **всей** таблице, а `WHERE` решётки,
области, актуальности и пригодности применяется уже к ним. Отклонённый post-filter, по сути, и происходит,
как только планировщик выбирает HNSW. Проба 02.11.2026 (PostgreSQL 16.14, pgvector 0.8.3, `m=16`,
`ef_construction=512`, `ef_search=200`; рядом с пробой — шаблоны вне области, три искомых — в области):

| Таблица и область | Путь, выбранный планировщиком | Найдено искомых |
|---|---|---|
| 19 тыс.; область до ~10 % строк | B-tree по носителю + сортировка (точно) | 3 из 3 |
| 19 тыс.; область 26 % и 95 %; 1 000 шаблонов вне области ближе искомых | HNSW | **0 из 3, выдача пуста** |
| 8,3 тыс.; область 96 %; 300 шаблонов вне области | HNSW | **0 из 3, выдача пуста** |
| то же, итеративный обход pgvector 0.8 (`strict_order`) | HNSW | 3 из 3, ~5 мс |
| 49 тыс.; 31 тыс. шаблонов вне области ближе искомых; итеративный обход с пределами по умолчанию | HNSW | 0 из 3 |
| то же, `max_scan_tuples=100000`, `scan_mem_multiplier=4` | HNSW | 2 из 3 |
| то же, точный перебор | без индекса | 3 из 3, 9,5 мс |

Жизненный случай — тот же человек во многих кадрах длинных видео закрытого дела, дела ОТМ или чужого
подразделения: его шаблоны занимают все `ef_search` мест, и поиск по открытым делам отвечает «лица нет».
Точный перебор по 1 млн шаблонов (ориентир ТН-005, таблица 597 МБ) занял 90–120 мс с двумя параллельными
исполнителями PostgreSQL и 225–245 мс без них — в пределах ТН-006 даже для поиска по десяти эталонам
(ADR-0046).

**Принято:**

7. **Точный перебор, пока шаблонов-кандидатов не больше предела** `Media:Search:ExactScanLimit` (по
   умолчанию 1 000 000 — объём эталонной базы по ТН-005): в транзакции поиска обход индексом выключается
   (`SET LOCAL enable_indexscan = off`, как в ядре по ADR-0051 п. 6); отбор по B-tree битовыми картами
   остаётся. Кандидат-лист — точный топ-K области после решётки. Решает оценка числа строк таблицы из
   каталога (`pg_class.reltuples`, без чтения таблицы); если таблица больше предела или ещё не
   анализировалась — подсчёт кандидатов с фильтрами запроса, обрываемый на «предел + 1».
8. **Выше предела — HNSW с итеративным обходом** pgvector 0.8+ (`hnsw.iterative_scan = strict_order`,
   `hnsw.max_scan_tuples = 100000`, `hnsw.scan_mem_multiplier = 8`): индекс продолжает обход, пока не
   наберёт topK строк, прошедших фильтр. Режим приближённый — после массовой загрузки и смены модели
   обязательна проба полноты (п. 2). Версия pgvector читается из `pg_extension`; на версии ниже 0.8
   остаётся прежний обход — это ограничение, поэтому на сервере нужен pgvector 0.8.4+ (справочник).
9. **Предел — параметр воспроизводимости**: попадает в запись аудита поиска рядом с `ef_search` (ТБ-072).
   `0` выключает точный перебор (только индекс) — допустимо лишь вместе с пробой полноты на рабочем объёме.

Отклонено в v0.2: только итеративный обход без точного перебора — приближённый (2 из 3 в пробе) и зависит
от версии pgvector на сервере; точный перебор при любом объёме — на многих миллионах шаблонов и десяти
эталонах не уложится в ТН-006; «свои» частичные HNSW-индексы на подразделение или дело — не закрывают
области «выбранные дела», плодят индексы и требуют миграций при каждом новом подразделении.

## Последствия

- (+) GATE-4 доказывает решётку на настоящем pgvector (три теста: допуск/подразделение/актуальность/пригодность, fail-closed без контекста, порог после решётки).
- (+) Урок инцидента не повторяется: параметры зафиксированы в конфигурации сущности и в поисковом сервисе.
- (−) `ef_construction=512` удорожает сборку индекса (`maintenance_work_mem` по размеру графа) — учитывать при массовой загрузке.
- (+) v0.2: на объёме ТН-005 кандидат-лист области — точный, а не приближённый: совпадение в деле не теряется из-за кадров того же человека вне области.
- (−) v0.2: время поиска растёт с числом шаблонов линейно (~0,1–0,25 с на 1 млн на машине разработки) — подтвердить нагрузочным тестом ТН-006 на оборудовании Заказчика (ЭС4); при нехватке — снижать предел только вместе с пробой полноты.
- (!) Требование к серверу: исправный pgvector (0.8.4+ — для итеративного обхода выше предела) и `maintenance_work_mem` под размер графа. На 10.10.0.115 индекс ядра с этой парой параметров работает (инцидент 26.08.2026 закрыт миграцией `HnswIslandRecall`), миграция `InitialMedia` накатывается штатно.
