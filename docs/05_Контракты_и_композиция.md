## 1. Принципы и границы

**1.1. Назначение слоя контрактов.** Проект `ISC.AI.Abstractions` содержит **только интерфейсы и базовые типы, без реализаций** (ТО-прог-04). Это вершина графа зависимостей: ядро (`ISC.AI.AI`, `ISC.AI.Persistence`, `ISC.AI.Ingestion`, `ISC.AI.Documents`) и профиль (`ISC.AI.Profile.Inspector.*`) ссылаются внутрь, на `Abstractions`, и не зависят друг от друга напрямую (ТС-002, ТС-003). Ядро не знает о существовании профиля «Инспектор».

**1.2. Декларативность профиля.** Профиль описывает себя **манифестом** `IProfile` (ТС-006): какие модули он публикует, какие сервисы и контексты данных регистрирует, какие модели по ролям привязывает, откуда берёт промпты, в каком порядке инициализируется. Хост не содержит знаний о конкретном профиле — он работает с ним только через контракты (ТС-004).

**1.3. Единственная точка композиции.** Знание о том, какой профиль загружен, есть только у хоста `ISC.AI.Web` (ТС-004, ТО-прог-06). На Э0 эта связь отсутствует (проект профиля не подключён к хосту) и реализуется на Э2.

**1.4. Инвариант как часть контракта.** Для контрактов, несущих режимные свойства, инвариант — не рекомендация, а обязательство реализации, проверяемое автоматическим тестом: для несущих режимных инвариантов извлечения и грунтовки — блокирующими gate-критериями GATE-1/GATE-2 (раздел 7.4 ТЗ), для прочих контрактов — соответствующими интеграционными тестами. Нарушение инварианта безопасности — блокирующий дефект. Такие инварианты документируются в коде особенно тщательно (ТД-003) и сопровождаются ссылкой на пункт ТЗ/модели угроз (ТД-004).

**1.5. Соответствие именования коду.** Эскизы сигнатур используют корневое пространство имён `ISC.AI.Abstractions` и его подпространства (`Profiles`, `Modules`, `AI`, `Retrieval`, `Grounding`, `Ingestion`, `Documents`, `Security`). Конкретные имена типов, неймспейсы и членов — предмет согласования при черновой реализации контрактов на Э1; ниже приведён рабочий эскиз.

## 2. Состав контрактов платформы (ТО-прог-04)

Перечень соответствует ТО-прог-04. Ниже для каждого контракта: **назначение** → **эскиз сигнатуры** → **инвариант(ы)**.

### 2.1. `IProfile` — манифест профиля

**Назначение.** Корневой контракт сменной доменной вертикали (ТС-006). Идентифицирует профиль, перечисляет его модули и описывает, как профиль регистрирует свои сервисы, контексты данных, привязки моделей и источники промптов в контейнере хоста, а также задаёт порядок инициализации (ТО-прог-04, ТО-прог-05). Хост вызывает методы манифеста на старте в фиксированной последовательности.

```csharp
namespace ISC.AI.Abstractions.Profiles;

/// <summary>
/// Манифест сменной доменной вертикали (профиля) ISC.AI.
/// Описывает идентификацию профиля, перечень его модулей и порядок
/// регистрации сервисов, контекстов данных, привязок моделей и источников
/// промптов в контейнере хоста. Реализуется ровно одним профилем,
/// подключаемым хостом <c>ISC.AI.Web</c> (ТС-004, ТС-006, ТО-прог-04/05).
/// </summary>
public interface IProfile
{
    /// <summary>Стабильный технический идентификатор профиля (например, "inspector").</summary>
    string Id { get; }

    /// <summary>Человекочитаемое наименование профиля для интерфейса (например, "ИнспекторAI").</summary>
    string DisplayName { get; }

    /// <summary>
    /// Реестр модулей профиля (ТС-007). Источник навигации и политик доступа
    /// при построении меню хостом. Порядок элементов определяет порядок в меню.
    /// </summary>
    IReadOnlyList<IModule> Modules { get; }

    /// <summary>
    /// Поставщики привязок моделей по ролям (keyed): draft / analysis / embeddings
    /// (ТО-прог-03). Применяются хостом на шаге keyed-регистрации.
    /// </summary>
    IReadOnlyList<IModelContributor> ModelContributors { get; }

    /// <summary>
    /// Регистрация прикладных сервисов профиля в контейнере (бизнес-логика модулей,
    /// провайдеры промптов <see cref="IPromptProvider"/>, рендереры и т. п.).
    /// Вызывается хостом до построения приложения. Не должна регистрировать
    /// контексты данных как долгоживущие scoped-сервисы (для них — фабрика, ТС-008).
    /// </summary>
    void RegisterServices(IServiceCollection services, IConfiguration configuration);

    /// <summary>
    /// Регистрация контекстов данных профиля через фабрику
    /// (<see cref="IDbContextFactory{TContext}"/>), а не как scoped-сервис (ТС-008).
    /// Профиль регистрирует свой доменный контекст (схема <c>inspector</c>);
    /// универсальный контекст ядра (схема <c>core</c>) регистрирует хост (ТО-инф-01).
    /// </summary>
    void RegisterDataContexts(IServiceCollection services, IConfiguration configuration);

    /// <summary>
    /// Жёстко заданный порядок шагов инициализации профиля (ТО-прог-05):
    /// обнаружение → регистрация сервисов → регистрация контекстов (фабрика) →
    /// keyed-модели → построение навигации из реестра модулей →
    /// подключение аутентификации/авторизации. Возвращает шаги для исполнения хостом.
    /// </summary>
    IReadOnlyList<ProfileInitStep> InitializationOrder { get; }
}
```

**Инвариант.**
- **И-PROFILE-1 (единственность).** В одном развёртывании хост подключает **ровно один** `IProfile` (ТС-004, ТС-009 (б)). Подключение нуля или более одного профиля — нарушение, обнаруживаемое архитектурным тестом ТС-009.
- **И-PROFILE-2 (порядок).** Инициализация выполняется строго в последовательности ТО-прог-05; перестановка шагов недопустима (например, навигация строится только после регистрации модулей, авторизация подключается последней).
- **И-PROFILE-3 (нейтральность ядра).** Манифест не «протекает» в ядро: ядро не ссылается на тип профиля (ТС-002, ТС-003, ТС-009 (а)).

### 2.2. `IModule` — единица интерфейса

**Назначение.** Описывает функциональную единицу профиля, отображаемую в интерфейсе (ТС-007): её маршрут, пункт меню, тип Razor-компонента (Blazor Server) и требуемую политику доступа. Из набора модулей хост строит навигацию (ТО-прог-05).

```csharp
namespace ISC.AI.Abstractions.Modules;

/// <summary>
/// Единица интерфейса профиля (модуль): маршрут, пункт меню, тип
/// Razor-компонента и требуемая политика доступа. Источник навигации и
/// привязки авторизации в хосте (ТС-007, ТО-прог-05).
/// </summary>
public interface IModule
{
    /// <summary>Стабильный технический идентификатор модуля (например, "generator").</summary>
    string Id { get; }

    /// <summary>Маршрут модуля (например, "/generator"); основа регистрации страницы.</summary>
    string Route { get; }

    /// <summary>Заголовок пункта меню для интерфейса (например, "Генератор документов").</summary>
    string MenuTitle { get; }

    /// <summary>Необязательный значок/иконка пункта меню (имя из набора иконок интерфейса).</summary>
    string? MenuIcon { get; }

    /// <summary>
    /// Тип корневого Razor-компонента модуля. Хост сопоставляет маршрут с этим
    /// компонентом при построении навигации. Тип обязан быть Razor-компонентом.
    /// </summary>
    Type ComponentType { get; }

    /// <summary>
    /// Имя требуемой политики авторизации (ASP.NET Core Authorization).
    /// Доступ к маршруту разрешается только при выполнении политики
    /// (роль/допуск/подразделение по решётке ТБ-002, ТБ-011). Пустое значение
    /// недопустимо: анонимный доступ запрещён (ТБ-010).
    /// </summary>
    string RequiredPolicy { get; }
}
```

**Инвариант.**
- **И-MODULE-1 (нет анонимного доступа).** Каждый модуль обязан объявлять непустую политику доступа `RequiredPolicy`; маршрут без авторизации недопустим (ТБ-010, ТБ-011). Это согласуется с тем, что фактический режимный фильтр данных применяется глубже — на этапе извлечения (ТБ-020); UI-политика не заменяет его, а дополняет.
- **И-MODULE-2 (корректность компонента).** `ComponentType` — Razor-компонент; иначе модуль не публикуется (ошибка композиции на старте, а не во время навигации).

### 2.3. `IModelContributor` — keyed-регистрация моделей

**Назначение.** Поставщик привязки «роль модели → конкретный клиент» (ТО-прог-02, ТО-прог-03). Связка задаётся **keyed-регистрацией** по роли: `draft` (быстрая генерация/форматирование), `analysis` (анализ и сверка НПА, длинный контекст), `embeddings` (векторизация ru/ky). Ядро не знает названий моделей — оно разрешает клиента по ключу-роли.

```csharp
namespace ISC.AI.Abstractions.AI;

/// <summary>
/// Канонические роли моделей (keyed). Конкретные веса, размер и квантизация
/// задаются конфигурацией под бюджет VRAM; ядро оперирует только ролью (ТО-прог-03).
/// </summary>
public enum ModelRole
{
    /// <summary>Быстрая генерация и форматирование документов.</summary>
    Draft,
    /// <summary>Анализ и сверка НПА; длинный контекст.</summary>
    Analysis,
    /// <summary>Векторизация текста (эмбеддинги) для семантического поиска (ru/ky).</summary>
    Embeddings
}

/// <summary>
/// Поставщик keyed-регистрации моделей по ролям. Регистрирует
/// <c>IChatClient</c> (для Draft/Analysis) и <c>IEmbeddingGenerator</c>
/// (для Embeddings) в контейнере с ключом-ролью. Конкретное название модели
/// задаётся конфигурацией и не известно ядру (ТО-прог-02/03).
/// </summary>
public interface IModelContributor
{
    /// <summary>Роль, для которой поставщик регистрирует клиента.</summary>
    ModelRole Role { get; }

    /// <summary>
    /// Регистрирует клиента модели в контейнере под ключом <see cref="Role"/>
    /// (keyed-сервис). Параметры подключения к vLLM (адрес loopback/внутренний,
    /// имя модели) берутся из конфигурации (ТБ-044, ТО-прог-01/03).
    /// </summary>
    void Register(IServiceCollection services, IConfiguration configuration);
}
```

**Инвариант.**
- **И-MODEL-1 (полнота ролей).** Для работоспособности профиля должны быть зарегистрированы все используемые им роли; отсутствие требуемой роли выявляется на старте, а не при первом запросе.
- **И-MODEL-2 (разрешение по ключу).** Потребитель получает клиента **только по ключу-роли** (`[FromKeyedServices(ModelRole.Analysis)]` и т. п.); прямые ссылки на конкретную модель в ядре запрещены (ТО-прог-02).

### 2.4. `IPromptProvider` — задачные промпты профиля

**Назначение.** Предоставляет **задачные** промпты профиля, хранимые файлами-шаблонами в прикладном слое профиля (не в UI и не в коде; ТО-лнг-03). Системная часть промпта с правилом грунтовки размещается в **ядре** и через этот контракт **не предоставляется** и не может быть переопределена (ТБ-041).

```csharp
namespace ISC.AI.Abstractions.AI;

/// <summary>
/// Поставщик задачных промптов профиля. Промпты хранятся файлами-шаблонами
/// в прикладном слое профиля и загружаются по ключу; подстановка значений —
/// шаблонизатором (ТО-лнг-03). Системная часть (правило грунтовки) задаётся
/// ядром и через этот контракт не предоставляется (ТБ-041).
/// </summary>
public interface IPromptProvider
{
    /// <summary>
    /// Возвращает шаблон задачного промпта по ключу (например, "generator.act").
    /// Бросает исключение, если шаблон не найден: молчаливая подмена
    /// пустым/произвольным текстом недопустима.
    /// </summary>
    PromptTemplate GetTaskPrompt(string promptKey);
}
```

**Инвариант.**
- **И-PROMPT-1 (приоритет системного промпта).** Итоговый промпт собирается как **системный (ядро) + задачный (профиль) + данные** (ТБ-041, ТО-лнг-03). Профиль не может отключить или ослабить системную часть (правило грунтовки); если задачный промпт пытается переопределить системные правила, приоритет — за ядром.

### 2.5. Порт моделей: `IChatClient` и `IEmbeddingGenerator`

**Назначение.** Доступ к моделям — через **нейтральные абстракции** `Microsoft.Extensions.AI` (ТО-прог-02): `IChatClient` для генерации/анализа (роли `draft`, `analysis`) и `IEmbeddingGenerator` для векторизации (роль `embeddings`). Платформа использует эти стандартные интерфейсы как порт и не вводит собственный клиент модели; конкретная реализация (адаптер к vLLM) живёт в ядре `ISC.AI.AI`, а её выбор задаётся keyed-регистрацией (см. 2.3).

```csharp
// Используются стандартные контракты Microsoft.Extensions.AI:
//   Microsoft.Extensions.AI.IChatClient            — генерация и анализ (draft/analysis)
//   Microsoft.Extensions.AI.IEmbeddingGenerator<TInput, TEmbedding> — векторизация (embeddings)
//
// Потребление — строго по keyed-роли (ТО-прог-02/03):

/// <summary>
/// Пример потребления модели анализа НПА. Клиент разрешается по ключу-роли
/// <see cref="ModelRole.Analysis"/>; конкретная модель ядру не известна (ТО-прог-02/03).
/// </summary>
public sealed class NpaAnalysisService(
    [FromKeyedServices(ModelRole.Analysis)] IChatClient chat,
    [FromKeyedServices(ModelRole.Embeddings)]
        IEmbeddingGenerator<string, Embedding<float>> embedder)
{
    // ... вызовы chat.GetResponseAsync(...) и embedder.GenerateAsync(...)
    // выполняются после RAG-извлечения с фильтром доступа (ТО-мат-01, ТБ-020)
    // и проходят грунтовку до выдачи (ТБ-040).
}
```

**Инвариант.**
- **И-AI-1 (нейтральность).** Ядро зависит только от `IChatClient`/`IEmbeddingGenerator`, но не от конкретного провайдера или названия модели (ТО-прог-02, ТСТ-003 — переносимость).
- **И-AI-2 (порядок в конвейере).** Вызов генерирующей модели всегда следует за извлечением с фильтром доступа (ТО-мат-01) и предшествует грунтовке вывода (ТБ-040); модель не получает фрагменты выше допуска пользователя, так как фильтр применён ранее в `IRetriever` (ТБ-020).
- **И-AI-3 (защита артефактов).** Промпты/ответы — носители сведений; их полнотекстовая запись в технологические логи в открытом виде запрещена (ТБ-043). Контракт сам логирование не выполняет; реализации-обёртки обязаны соблюдать ТБ-043.

### 2.6. `IRetriever` — извлечение с обязательным фильтром доступа

**Назначение.** Извлекает релевантные фрагменты корпуса (чанки/документы) по эмбеддингам для RAG (ТО-мат-01). Это **несущий режимный контроль**: извлечение всегда выполняется в контексте субъекта с допуском, и фильтрация по грифу/подразделению применяется **на стороне БД, до возврата результатов** (ТБ-020).

```csharp
namespace ISC.AI.Abstractions.Retrieval;

/// <summary>
/// Извлечение релевантных фрагментов корпуса для RAG (ТО-мат-01).
/// ИНВАРИАНТ БЕЗОПАСНОСТИ (ТБ-020): фильтрация по грифу и подразделению
/// применяется на стороне БД ДО возврата результатов; пользователю не
/// возвращаются векторы/чанки/документы выше его допуска. Без установленного
/// субъекта с допуском извлечение не выполняется (ТБ-012).
/// ИНВАРИАНТ FAIL-CLOSED (ТБ-021): при отсутствии/неопределённости атрибутов
/// допуска или грифа доступ запрещается, а не разрешается.
/// </summary>
public interface IRetriever
{
    /// <summary>
    /// Возвращает фрагменты, релевантные запросу и РАЗРЕШЁННЫЕ контексту доступа.
    /// </summary>
    /// <param name="query">Текст запроса для семантического поиска.</param>
    /// <param name="access">
    /// Контекст доступа субъекта (роль, допуск, подразделение). ОБЯЗАТЕЛЕН.
    /// Передача отсутствующего/неполного контекста ведёт к отказу (fail-closed, ТБ-021),
    /// а не к выдаче без фильтра (ТБ-012).
    /// </param>
    /// <param name="topK">Желаемое число фрагментов (после применения фильтра доступа).</param>
    /// <param name="filter">
    /// Необязательные доменные ограничения (тип документа, период и т. п.).
    /// Не может ослабить фильтр доступа; по умолчанию возвращаются только
    /// действующие редакции (ТФ-НПА-02, ТО-инф-04).
    /// </param>
    Task<IReadOnlyList<RetrievedChunk>> RetrieveAsync(
        string query,
        AccessContext access,
        int topK,
        RetrievalFilter? filter = null,
        CancellationToken cancellationToken = default);
}
```

**Инвариант (несущий, gate-критерий GATE-1).**
- **И-RET-1 (фильтр на стороне БД, ТБ-020).** Фрагменты выше допуска не возвращаются **ни в каком виде**; фильтр применяется на стороне БД до выдачи модели. Хранилище эмбеддингов несёт атрибут грифа/подразделения и подчиняется решётке доступа **при любом обращении**, а не только через штатный retriever.
- **И-RET-2 (fail-closed, ТБ-021).** При отсутствии или неопределённости атрибутов допуска/грифа — доступ **запрещён** (пустой результат/отказ), а не разрешён. Отсутствие субъекта с допуском (ТБ-012) делает извлечение невозможным.
- **И-RET-3 (неразличимость, ТБ-022).** Реализация не раскрывает **наличие** документов выше допуска через метаданные, счётчики/агрегаты, ранжирование, подсказки и — что отдельно проверяется — через **различие во времени ответа и в тексте ошибки** (timing/oracle). Стратегия фильтрации (pre-/post-filter) обосновывается отдельным ADR (ДОК-06, ТБ-022) и не должна скрыто терять полноту в пределах допуска.
- **И-RET-4 (изоляция грифов, ТБ-023).** Материалы разного грифа не смешиваются в индексе без разграничения; способ изоляции проверяется тестом (подпроверка GATE-1).

> Проверка инварианта — интеграционный тест **GATE-1** (7.4 ТЗ): подготовленный документ заведомо выше допуска должен быть **неотличим** от случая «документ отсутствует». Невыполнение — блокирующий дефект.

### 2.7. `IGroundingValidator` — валидатор грунтовки

**Назначение.** После генерации проверяет, что **каждая ссылка/цитата на НПА** в выводе модели присутствует в фактически извлечённых RAG-фрагментах (ТБ-040). Грунтовка — **контракт, а не опция**: ссылки «по памяти» запрещены, неподтверждённые ссылки помечаются как непроверенные и не выдаются как готовые.

```csharp
namespace ISC.AI.Abstractions.Grounding;

/// <summary>
/// Валидатор грунтовки вывода модели против фактически извлечённых фрагментов.
/// ИНВАРИАНТ БЕЗОПАСНОСТИ (ТБ-040): ссылка на НПА, отсутствующая в извлечённых
/// фрагментах, НЕ выдаётся как подтверждённая — она помечается как непроверенная.
/// Генерация правовых ссылок «по памяти» недопустима. Метод грунтовки строже
/// строкового совпадения (нормализация цитат, привязка к норме/редакции, ТО-мат-02);
/// фиксируется отдельным ADR (ДОК-06) и проверяется на Evals (КИ-01).
/// </summary>
public interface IGroundingValidator
{
    /// <summary>
    /// Сверяет ссылки вывода с извлечёнными фрагментами и возвращает результат,
    /// в котором каждая ссылка помечена как подтверждённая либо непроверенная.
    /// Реализация НЕ удаляет и НЕ «исправляет» текст модели молча — она
    /// классифицирует ссылки, чтобы интерфейс мог отделить их визуально (ТЭ-003)
    /// и не выдать вывод как проверенный без отметки HITL (ТБ-042, ТЭ-002).
    /// </summary>
    GroundingResult Validate(
        GeneratedOutput output,
        IReadOnlyList<RetrievedChunk> retrievedContext);
}
```

**Инвариант (несущий, gate-критерий GATE-2).**
- **И-GRND-1 (запрет неподтверждённых, ТБ-040).** Ни одна ссылка, отсутствующая в извлечённых фрагментах, не может быть представлена как подтверждённая. Неподтверждённые ссылки явно маркируются и не выдаются как готовые.
- **И-GRND-2 (HITL, ТБ-042/ТЭ-002).** Результат, содержащий правовые утверждения, не выдаётся как юридически значимый без отметки о необходимости проверки человеком; ответственность за корректность несёт сотрудник.

> Проверка инварианта — Eval **GATE-2** (7.4 ТЗ): вывод со ссылкой, отсутствующей в извлечённых фрагментах, отклоняется/маркируется и не выдаётся как проверенный. Невыполнение — блокирующий дефект.

### 2.8. `IIngestionPort` — конвейер загрузки

**Назначение.** Порт загрузки документов в корпус: подготовка, чанкинг, векторизация и индексация (ТО-мат-03, ТО-инф-07). Работает **fail-closed**: документ/чанк без явно установленных грифа и подразделения **не индексируется** (ТБ-024), а полный набор обязательных метаданных заполняется для каждого чанка (ТО-инф-03).

```csharp
namespace ISC.AI.Abstractions.Ingestion;

/// <summary>
/// Порт конвейера загрузки документов в корпус (чанкинг, векторизация, индексация).
/// ИНВАРИАНТ БЕЗОПАСНОСТИ (ТБ-024, ТО-инф-03): для КАЖДОГО чанка обязан быть
/// заполнен полный набор обязательных метаданных, в т. ч. ГРИФ и ПОДРАЗДЕЛЕНИЕ;
/// запись без явно установленного грифа/подразделения ОТКЛОНЯЕТСЯ и не попадает
/// в векторное хранилище. Гриф по умолчанию — максимально ограничительный
/// (fail-closed), а не открытый; обязателен шаг подтверждения грифа оператором.
/// Операция идемпотентна: повторная загрузка не создаёт дублей (ТНД-002).
/// </summary>
public interface IIngestionPort
{
    /// <summary>
    /// Принимает документ с метаданными и индексирует его чанки.
    /// Если гриф или подразделение не установлены явно — возвращает отказ
    /// и НЕ индексирует ничего (ТБ-024). Источник вызывает порт только после
    /// подтверждения грифа оператором.
    /// </summary>
    /// <param name="request">
    /// Документ и его обязательные метаданные (тип, дата, редакция и её статус,
    /// подразделение, гриф, источник, идентификатор нормы — ТО-инф-03).
    /// Поля грифа и подразделения — обязательные (NOT NULL в хранилище).
    /// </param>
    Task<IngestionResult> IngestAsync(
        IngestionRequest request,
        CancellationToken cancellationToken = default);
}
```

**Инвариант (несущий).**
- **И-ING-1 (полнота метаданных, ТО-инф-03).** Чанк индексируется только при полном наборе обязательных метаданных; добавление полей грифа/подразделения «задним числом» недопустимо — они `NOT NULL`.
- **И-ING-2 (fail-closed, ТБ-024).** Отсутствие явного грифа/подразделения → **отклонение**, а не индексация с открытым грифом по умолчанию. Гриф по умолчанию — максимально ограничительный.
- **И-ING-3 (идемпотентность, ТНД-002).** Повторная загрузка того же источника не создаёт дублей.

> Проверка — интеграционный тест ingestion (ТБ-024): отсутствие в индексе чанков с неопределённым грифом. Это не отдельный GATE; кроме того, fail-closed загрузка входит в обязательные условия организационного режим-гейта (ТБ-063, акт ПОДГ-06).

### 2.9. `IDocumentRenderer` — рендеринг и экспорт документов

**Назначение.** Порт связывания шаблона документа с данными и нормами НПА и экспорта результата в `.docx` (ТФ-ГЕН-03, ТФ-РЕД-03). Канал экспорта — **режимный**: каждый экспортируемый материал, содержащий сведения ограниченного доступа, автоматически маркируется грифом и учётными реквизитами (ТБ-033).

```csharp
namespace ISC.AI.Abstractions.Documents;

/// <summary>
/// Порт рендеринга документов: связывание шаблона профиля с данными и нормами,
/// экспорт в .docx (ТФ-ГЕН-03, ТФ-РЕД-03).
/// ИНВАРИАНТ БЕЗОПАСНОСТИ (ТБ-033): экспортируемый материал, содержащий сведения
/// ограниченного доступа, АВТОМАТИЧЕСКИ маркируется грифом и учётными реквизитами
/// (гриф, учётный номер, исполнитель) в теле документа и в метаданных файла.
/// Гриф результата наследуется как МАКСИМУМ грифов извлечённых фрагментов
/// (производный носитель, ТБ-032). Факт экспорта/печати фиксируется в аудите (ТБ-030).
/// </summary>
public interface IDocumentRenderer
{
    /// <summary>
    /// Рендерит документ по шаблону и данным и экспортирует его в .docx.
    /// Маркировка грифа обязательна и не может быть отключена параметрами вызова.
    /// Возвращает поток/дескриптор файла вместе с фактическим грифом результата.
    /// </summary>
    Task<RenderedDocument> RenderToDocxAsync(
        DocumentRenderRequest request,
        CancellationToken cancellationToken = default);
}
```

**Инвариант.**
- **И-DOC-1 (обязательная маркировка, ТБ-033).** Маркировка грифа и учётных реквизитов — обязательная и неотключаемая; отсутствует возможность экспортировать режимный материал без грифа.
- **И-DOC-2 (наследование грифа, ТБ-032).** Гриф результата = максимум грифов извлечённых фрагментов.
- **И-DOC-3 (проект, требующий проверки, ТЭ-002).** Сгенерированный документ помечается как проект, требующий проверки человеком, до утверждения.

## 3. Порядок композиции в ISC.AI.Web (ТО-прог-05/06)

Единственная точка композиции — хост `ISC.AI.Web` (ТС-004). Хост подключает проект профиля и выполняет инициализацию в порядке ТО-прог-05. На Э0 этого нет: хост ссылается только на проекты ядра (`Abstractions`, `AI`, `Documents`, `Persistence`, `Ingestion`) и не ссылается на `ISC.AI.Profile.Inspector`; точка композиции отсутствует (ТО-прог-06). Подключение и реализация — рабочий этап **Э2**.

### 3.1. Шаги композиции

Последовательность строго фиксирована (ТО-прог-05):

| № | Шаг | Что делает хост | Связь с ТЗ |
|---|---|---|---|
| 1 | **Обнаружение профиля** | Хост определяет и создаёт **ровно один** `IProfile` (через ссылку на проект профиля и его регистрацию). | ТС-004, ТС-006, ТС-009 (б) |
| 2 | **RegisterServices** | Вызов `profile.RegisterServices(...)` — регистрация прикладных сервисов, провайдеров промптов, рендереров профиля. | ТО-прог-04/05 |
| 3 | **AddDbContextFactory обоих контекстов** | Регистрация **через фабрику** (`AddDbContextFactory`), а не как scoped: универсальный контекст ядра (схема `core`) — хостом; доменный контекст профиля (схема `inspector`) — через `profile.RegisterDataContexts(...)`. Каждая схема — своя история миграций. | ТС-008, ТО-инф-01/06 |
| 4 | **Keyed-модели** | Применение `profile.ModelContributors`: keyed-регистрация `IChatClient`/`IEmbeddingGenerator` по ролям `draft`/`analysis`/`embeddings`. | ТО-прог-02/03 |
| 5 | **Навигация из реестра модулей** | Построение навигации/маршрутов из `profile.Modules` (маршрут, пункт меню, тип компонента, политика). | ТС-007, ТО-прог-05 |
| 6 | **AddAuthentication / AddAuthorization** | Подключение аутентификации и политик авторизации (роль/допуск/подразделение по решётке ТБ-002); анонимный доступ запрещён; конфигурация без небезопасных значений по умолчанию. | ТБ-010/011, ТО-прог-05 |

> Порядок не переставляется: контексты регистрируются до моделей и навигации; навигация строится после регистрации модулей; авторизация подключается последней, опираясь на политики модулей. Режимный фильтр данных (ТБ-020) реализуется не в этом порядке композиции, а в слое извлечения (`IRetriever`) и проверяется отдельно (GATE-1).

### 3.2. Эскиз минимального Program.cs

Эскиз целевого состояния (Э2). Иллюстрирует порядок ТО-прог-05; конкретные провайдеры аутентификации, строки подключения и регистрация профиля уточняются на Э1/Э2. На Э0 файл `Program.cs` содержит только шаблон Blazor Server без композиции профиля.

```csharp
using ISC.AI.Abstractions.Profiles;
using ISC.AI.Web.Components;
// using ISC.AI.Profile.Inspector;  // подключается на Э2: ссылка хоста на профиль (ТО-прог-06)

var builder = WebApplication.CreateBuilder(args);
var config = builder.Configuration;
var services = builder.Services;

// Blazor Server (ТО-прог-01).
services.AddRazorComponents()
        .AddInteractiveServerComponents();

// --- Точка композиции профиля (ТО-прог-05/06) ---

// Шаг 1. Обнаружение профиля: ровно ОДИН профиль (ТС-004, ТС-009 (б)).
IProfile profile = new InspectorProfile();   // единственный подключённый профиль
services.AddSingleton(profile);

// Шаг 2. Регистрация прикладных сервисов профиля (RegisterServices).
profile.RegisterServices(services, config);

// Шаг 3. Контексты данных — ЧЕРЕЗ ФАБРИКУ, оба (ТС-008, ТО-инф-01).
//   core — универсальная схема ядра (документы, чанки, эмбеддинги, аудит, пользователи);
//   inspector — доменная схема профиля. Регистрируется самим профилем:
services.AddDbContextFactory<CoreDbContext>(o =>
    o.UseNpgsql(config.GetConnectionString("Core"),
        npg => npg.MigrationsHistoryTable("__ef_migrations", "core")));
profile.RegisterDataContexts(services, config);   // регистрирует InspectorDbContext (схема inspector)

// Шаг 4. Keyed-модели по ролям draft/analysis/embeddings (ТО-прог-02/03).
foreach (var contributor in profile.ModelContributors)
    contributor.Register(services, config);

// Шаг 6 (регистрация политик до build). Аутентификация и авторизация (ТБ-010/011).
services.AddAuthentication(/* провайдер по политике заказчика, уточняется Э1 */)
        /* .Add... */;
services.AddAuthorizationBuilder()
        // Политики собираются из требований модулей профиля (роль/допуск/подразделение).
        .SetFallbackPolicy(new AuthorizationPolicyBuilder()
            .RequireAuthenticatedUser()      // анонимный доступ запрещён (ТБ-010)
            .Build());

var app = builder.Build();

if (!app.Environment.IsDevelopment())
{
    app.UseExceptionHandler("/Error", createScopeForErrors: true);
    app.UseHsts();
}
app.UseHttpsRedirection();          // HTTPS внутри контура (ТБ-010)

app.UseAuthentication();            // Шаг 6 (pipeline)
app.UseAuthorization();
app.UseAntiforgery();

app.MapStaticAssets();

// Шаг 5. Навигация/маршруты из реестра модулей профиля (ТС-007, ТО-прог-05).
// Razor-компоненты модулей подключаются из сборки профиля; каждый маршрут
// защищён политикой модуля (IModule.RequiredPolicy).
app.MapRazorComponents<App>()
   .AddInteractiveServerRenderMode()
   .AddAdditionalAssemblies(profile.GetType().Assembly);   // сборка профиля с модулями

app.Run();
```

> Эскиз намеренно не показывает реализацию `InspectorProfile`, `CoreDbContext`, `InspectorDbContext` — они относятся к ядру/профилю, не к контрактам. Имена и провайдер аутентификации — предмет согласования (Э1/Э2).

### 3.3. Архитектурный тест (ТС-009)

Корректность композиции защищается автоматическим архитектурным тестом, падающим при нарушении правил (ТС-009; прогон в CI):

- **(а)** ядро (`ISC.AI.*`, кроме хоста и профиля) **не ссылается** на проект профиля `ISC.AI.Profile.Inspector*` (ТС-002, ТС-003);
- **(б)** хост подключает **ровно один** профиль (И-PROFILE-1);
- **(в)** профиль не нарушает направление зависимостей (зависит внутрь, к `Abstractions`).

Тест размещается в проекте `ISC.AI.IntegrationTests` (или отдельном арх-тесте) и является условием приёмки шва композиции на Э2 (ПР-001/ПР-002).

## 4. Стиль XML-doc комментариев (ТД-003)

Контракты в `Abstractions` документируются **особенно тщательно** (ТД-003): назначение порта, ожидаемое поведение реализации и **инварианты безопасности** со ссылкой на пункт ТЗ. Комментарии — на русском языке, по существу (ТД-001). Ниже — эталон стиля для контракта с инвариантом безопасности.

```csharp
/// <summary>
/// Извлечение релевантных фрагментов корпуса НПА для RAG (ТО-мат-01).
/// </summary>
/// <remarks>
/// <para>
/// <b>Назначение.</b> Порт принимает запрос и контекст доступа субъекта и
/// возвращает фрагменты, релевантные запросу и разрешённые этому субъекту.
/// </para>
/// <para>
/// <b>Инвариант безопасности (ТБ-020).</b> Фильтрация по грифу и подразделению
/// применяется НА СТОРОНЕ БД, ДО возврата результатов. Реализация обязана
/// исключить возврат фрагментов выше допуска в любом виде — включая метаданные,
/// агрегаты, ранжирование и текст/время ошибки (ТБ-022).
/// </para>
/// <para>
/// <b>Fail-closed (ТБ-021).</b> Если контекст доступа отсутствует или атрибуты
/// грифа/допуска не определены — доступ ЗАПРЕЩАЕТСЯ (пустой результат/отказ),
/// а не разрешается. Без субъекта с допуском извлечение не выполняется (ТБ-012).
/// </para>
/// <para>
/// <b>Проверка.</b> Интеграционный тест GATE-1 (раздел 7.4 ТЗ): материал выше
/// допуска неотличим от случая «документ отсутствует». Невыполнение —
/// блокирующий дефект приёмки.
/// </para>
/// </remarks>
/// <param name="access">
/// Контекст доступа субъекта (роль, допуск, подразделение). ОБЯЗАТЕЛЕН;
/// <see langword="null"/> или неполный контекст → отказ (fail-closed, ТБ-021).
/// </param>
/// <returns>Фрагменты, релевантные запросу и разрешённые контексту доступа.</returns>
/// <exception cref="AccessContextRequiredException">
/// Бросается, если контекст доступа не задан (соблюдение ТБ-012).
/// </exception>
Task<IReadOnlyList<RetrievedChunk>> RetrieveAsync(
    string query, AccessContext access, int topK,
    RetrievalFilter? filter = null, CancellationToken cancellationToken = default);
```

**Правила оформления комментариев (для всего слоя `Abstractions`):**
- Для всех публичных типов и членов — `/// <summary>…` на русском, по существу: что делает и зачем, контракт, предусловия/постусловия, исключения (ТД-001).
- Включена генерация файла документации `GenerateDocumentationFile=true`; отсутствие XML-doc на публичном API — предупреждение, повышаемое до ошибки сборки по согласованию (ТД-002, CS1591).
- Инвариант безопасности описывается явно, с указанием **защищаемого свойства**, **угрозы** и **пункта ТЗ/модели угроз** (ТД-003/ТД-004): для `IRetriever` — ТБ-020/021/022/023; для `IGroundingValidator` — ТБ-040; для `IIngestionPort` — ТБ-024/ТО-инф-03; для `IDocumentRenderer` — ТБ-033/ТБ-032.
- Нетривиальная логика реализаций (чанкинг, ранжирование, компоновка промпта) комментируется в слое реализации, поясняя **почему** так сделано (ТД-005); сами контракты остаются декларативными.
- Комментарии не содержат сведений ограниченного доступа; примеры — обезличенные (ТД-007).
- Каждый значимый каталог/модуль сопровождается кратким `README`/заголовочным комментарием (ТД-006).

## 6. Открытые вопросы (уточняется с заказчиком, Э1)

Перечисленные ниже решения влияют на сигнатуры и реализацию контрактов; фиксируются на рабочем этапе Э1 (часть — отдельными ADR в ДОК-06):

1. **Состав и сигнатуры контрактов.** Точные имена типов, пространств имён и членов в `Abstractions` (эскизы раздела 2) согласуются при черновой реализации контрактов (Э1, ТО-прог-04).
2. **Стратегия фильтрации векторного поиска** (pre-filter / post-filter) для `IRetriever` — обосновывается отдельным ADR (ТБ-022, ДОК-06) с тестом полноты/утечки.
3. **Метод грунтовки** для `IGroundingValidator` (нормализация цитат, привязка к норме/редакции, пороги) — фиксируется ADR (ТО-мат-02, ДОК-06) и порогами Evals (КИ-01).
4. **Модель целостности на границе схем** `core`/`inspector` (единица работы, компенсация, кросс-контекстные транзакции) — ADR (ТО-инф-06); влияет на способ регистрации контекстов в `IProfile.RegisterDataContexts`.
5. **Состав обязательных метаданных** в `RetrievedChunk`/`IngestionRequest` — увязывается с ER-моделью ДОК-04 (ТО-инф-03); поля грифа и подразделения — `NOT NULL`.
6. **Структура `AccessContext`** (модель допуска и подразделений, решётка «гриф × роль × подразделение») — определяется моделью угроз ДОК-03 и реестром грифов (ТБ-002).
7. **Роли и привязки моделей** (`draft`/`analysis`/`embeddings`): конкретные модели, размер, квантизация под бюджет VRAM, выбор эмбеддера ru/ky — бенчмарк и ADR (ТО-прог-03, ТО-лнг-02).
8. **Провайдер аутентификации хоста** и набор политик авторизации (`IModule.RequiredPolicy`) — определяются политикой заказчика и классом защищённости (ТБ-010…016, ТБ-061).
9. **Тип шаблонизатора и формат шаблонов промптов** для `IPromptProvider` (ТО-лнг-03) и шаблонов документов для `IDocumentRenderer` (ТФ-ГЕН-02).
10. **Способ обнаружения профиля** в хосте (прямая ссылка на проект профиля против декларативного обнаружения) — решается на Э2 с учётом инварианта «ровно один профиль» (ТС-009).
